每个 token 的全局 KV cache 只占 890 字节，约为 DeepSeek-V4-Flash 的四分之一、DeepSeek-V1 的四百三十七分之一。按 1M = 1,000,000 token、1 GB = 10⁹ bytes 计算，全局 KV 从 V1 的 389.12 GB 降到 V4.1-Flash 的 0.89 GB。这里比较的是全局 KV，不包括模型权重、SWA 和工作区，也不意味着历史模型都能实际服务 1M 上下文。这个数字说明了状态存储的进步；它能转化成多少吞吐和成本收益，还要看具体负载。

2026 年 9 月，DeepSeek 发布了这份 51 页技术报告。本文跟着一次长任务请求，依次看首次输入如何计算、状态如何保存、缓存失效后如何续接，再讨论训练与部署之间的权衡。文中的性能数据均来自作者报告，未做独立复现；“作者分析”部分提出的是工程判断与待验证假设。

## 为什么这篇报告重要

长上下文 agent 的输入会在工具调用中逐渐累积。举一个假设的 coding session：系统 prompt 2K + 仓库上下文 100K + 历史工具输出 200K + 当前输入 5K = 307K token。客户端再次发送这些历史，不代表服务端再次计算全部历史：命中的 prefix KV 可以复用，只有未命中的输入需要 prefill。冷缓存、多分支和缓存失效会放大输入计算；高命中率则会把压力转向新 suffix、状态加载和输出生成。[vLLM 的前缀缓存说明](https://docs.vllm.ai/en/latest/design/prefix_caching/)给出了这种复用机制。

后面一直沿用这个 coding session。第一次输入假设没有缓存；下一轮工具调用回来，服务端匹配到一段旧前缀 `P`，后面接着未命中的新输入 `S`。`P` 不一定覆盖上一轮全部内容，前缀是否一致、缓存是否仍在，都影响命中边界。

| 请求走到哪里 | 要解决的问题 | 对应设计 |
|:---|:---|:---|
| 第一次读入长 prompt | 全部输入是否都要走完 40 层？ | CED 缩短主体 prefill 路径 |
| 保存并读取历史状态 | 哪些层共用 KV，每次读取哪些位置？ | CSA2、层级索引与 FP4 |
| 任务暂停后再次调用 | 全局 KV 还在，局部 SWA 已过期，怎样续接？ | Encoder 有界回放、Decoder 初始化 |
| 开始生成回答 | 当前 token 经过哪些层，怎样减少每步开销？ | 两半主干共同 decode，配合高效算子与 DSpark |

这条路径也把“少算”“少存”和“更便宜地恢复”分开了。它们作用在同一次请求上，却不是同一笔收益。

长上下文部署同时受计算、内存容量和数据搬运约束。Prefill 往往有较大的计算需求，decode 在一些批量和硬件配置下更受带宽约束，但不存在适用于所有模型与负载的单一瓶颈。尤其需要分开三本账：

1. **运行时 KV cache**（HBM）：约束服务实例能保留多少运行中请求的状态
2. **持久化 KV cache**（SSD / Host Memory）：影响可保留前缀的范围，收益还取决于复用模式与淘汰策略
3. **数据传输带宽**（PCIe / NVLink / RDMA）：与数据量、争用和调度一起影响 KV 加载延迟

DeepSeek 从 V1 到 V4.1-Flash，每一代都在压缩 KV cache，而且压缩手段在不断进化：

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/kv-cache-evolution.svg?v=20260910-review1" title="全局 KV 的跨代变化" caption="基于 Figure 1b；横轴使用对数刻度。只比较每 token 全局 KV，不代表模型总内存。" />

| 模型 | 时间 | 全局 KV Cache (bytes/token) | 压缩手段 |
|:-----|:-----|:---------------------------|:--------|
| DeepSeek-V1 | 2023.11 | 389,120 | 标准 MHA |
| DeepSeek-V3.2 | 2025.12 | 48,068 | MLA (Multi-head Latent Attention) |
| DeepSeek-V4-Flash | 2026.04 | 3,514 | CSA + HCA 混合 + FP8 |
| **DeepSeek-V4.1-Flash** | **2026.09** | **890** | **纯 CSA2 + FP4 + CED** |

890 B/token 是这份报告所展示的架构与质量约束下的结果。跨代倍率也不能直接用来推断未来还有多少压缩空间。

## 架构全景：CED + CSA2 为核心的双轴优化

DeepSeek-V4.1-Flash 是多模态 MoE 模型，主干参数 552B，另有 196B Engram 参数；prefill/decode 每 token 的激活参数约 8B/16B。总参数、激活计算量、部署时权重驻留预算是三个不同口径：不同 token 可能访问不同专家，稀疏激活不等于只需存储当前激活的专家。[MoE 的内存与计算需求](https://huggingface.co/blog/moe)需要分别估算。

它的核心架构创新可以沿两个轴来理解：

- **纵轴（层间）**：Causal Encoder-Decoder (CED) 把 40 层 Transformer 分成 20 层 encoder + 20 层 decoder，decoder 的全局 KV 从 encoder 投影而来，长 prompt 的 prefill 计算接近减半
- **横轴（层内）**：Compressed Sparse Attention 2 (CSA2) 跨层共享全局 KV 和 indexer K，配合 Hierarchical Sparse Indexer 限制深层 indexer 的搜索范围；首个 Full indexer 仍扫描全部可见位置

<Figure src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/figure3-overall-architecture.png" alt="DeepSeek-V4.1-Flash 整体架构图" />

> 来源：原论文 Figure 3，PDF 第 7 页

这张架构图值得仔细看：

- **Encoder（左）**：底部两层用纯 SWA，上面三组各 6 层用 CSA2（压缩率 m=2），每组第一层 Full Mode，其余 Reuse Mode
- **Decoder（右）**：五组各 4 层用 CSA2（压缩率 m=1），第一组 Full + Reuse，后四组 Reindex + Reuse
- **连接点**：CED 桥，decoder 的全局 KV 从 encoder 最后一层（第 20 层）的 hidden state 投影而来
- **辅助组件**：Single-Pass mHC、Engram（两个模块分别在 layer 1 和 14）、DSpark（投机解码）、Hierarchical Sparse Indexer

长 prompt 的主体在 prefill 时只经过 encoder，decoder 还要做投影相关处理和末尾窗口回放；decode 时两半都参与当前 token 的计算。因此 8B/16B 是两阶段的激活口径，不能理解为整个 prefill 完全不运行 decoder。输入很长、输出相对短的负载更能体现这一不对称设计的价值。

## 首次输入：CED 怎样缩短长 Prompt 的计算路径

传统 decoder-only 模型在 prefill 时，通常要让全部输入经过每一层。用 N×L 个 token-layer 可以粗略表示需要处理的位置数，但它不等于 attention FLOPs：每层算子、稀疏模式、序列长度都会影响工作量。下面用这个简化计数解释 CED 跳过了什么。

回到前面的冷缓存请求：307K token 都需要被读入，但不必都走完 40 层。对于输入远长于输出的调用，长 prompt 穿过整个主干是显著开销。CED 把 decoder 的全局 KV 生成与 decoder 自身的逐层前向分离，使 prompt 主体在 encoder 结束后就可以建立 decoder 所需的共享全局状态。

CED 延续了 [YoCo](https://arxiv.org/abs/2405.05254) 的跨层 KV 复用与 prefill 提前退出思路，并对 KV 生成的结构和计算深度作了调整。因此它与前序工作存在明确联系。本文关注报告 §2.2 的具体数据路径，以及它与 CSA2 共享、SWA 回放的组合。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/ced-data-flow.svg?v=20260910-review1" title="CED：Prefill 与 Decode 的不同路径" caption="长 prompt 主体经过 Encoder；Decoder 用末尾窗口初始化 SWA。生成新 token 时两半都参与。依据 §2.2、§3.2.2。" />

下面是 decoder 全局 KV 来源的简化表达；实际存储还受 CSA2 的跨层共享规则约束，并非每层都保存独立副本：

```
C_l = H_{L/2} * W_l^{KV}    // 全局 KV 从 encoder 最后一层投影
Z_l = H_{L/2} * W_l^{Z}     // 压缩权重也从 encoder 投影
```

这意味着：
- **Prefill**：encoder 处理输入并生成 decoder 全局 KV 所需的表示；decoder 不再完整处理全部 prompt，但仍回放末尾窗口以初始化自己的 SWA。
- **Decode**：encoder 与 decoder 都处理新 token；decoder 读取共享全局 KV，并计算本层 query 和 SWA 状态。

用 N=1,000,000、L=40、窗口 128 作简化计数：全长处理为 4000 万 token-layer；CED 路径为 `1,000,000×20 + 128×20 = 2000.256 万`。这个算例说明长 prompt 主体约少走半个主干，不是精确 FLOPs 或时延测量，未单列投影、共享、索引、通信等开销。

<Callout>
报告称长 prompt 的总 prefill 计算接近减半。token-layer 只是解释其来源的粗略计数；两种路径对 N 和 L 的渐近阶数没有改变，不能把常数因子优化写成复杂度阶数变化。
</Callout>

Decoder 每层仍有从自身 hidden states 生成的 SWA KV。它不进入 prefix cache，因此每次 prefill 都需要初始化；Bounded Replay 将这一步限制为最近一个窗口。Encoder 的 SWA 则有独立的短期缓存与 miss 恢复路径，后文会分开说明。

## 保存历史：CSA2 让哪些状态跨层共享

Encoder 已经处理了长 prompt，接下来要留下可供后续 query 读取的历史表示。对这个 coding session 而言，CSA2 决定这些表示如何压缩、哪些层共享它们；稀疏索引再决定每次读哪一部分。

KV cache 的大小可以沿三个乘性维度压缩：

1. **Entry 维度**（每个 head 的 KV 大小）：GQA / MLA 通过共享或压缩 head 来减少
2. **Sequence 维度**（每层存多少 token 的 KV）：CSA 通过 m:1 压缩来减少
3. **Layer 维度**（多少层需要独立存 KV）：跨层共享来减少

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/csa2-compression-dimensions.svg?v=20260910-review1" title="全局 KV 的三个压缩维度" caption="条目表示、序列条目数、独立缓存层数共同影响容量；稀疏选择约束读取范围。依据 §2.3。" />

此前的方法分别探索缓存压缩、跨层共享和稀疏选择。CSA2 的组合特点是将共享 main KV、共享 indexer K 与是否重新选位置分开控制。与 V4 相比，它去掉 HCA 分支，采用 CSA2；这里的 HCA 是对重压缩条目全集做 attention，并非未压缩的 dense MHA。这使不同层可以共享表示，同时保留重新选择关注位置的能力。

还要区分“存多少”与“读多少”：sequence 压缩和跨层共享减少保留的表示；sparse selection 决定当前 query 读取哪些位置。没有选中某个位置，不等于立刻把它从缓存中永久淘汰，但压缩后的表示也不能视作保留了全部原始细节。

压缩率 m 表示每 m 个相邻 token 形成一个压缩条目。Encoder 使用 m=2，decoder 使用 m=1；后者不做 sequence 压缩，但仍做跨层共享和稀疏选择。这是报告采用的配置，不足以单独证明所有 encoder 都可以容忍同样的压缩、所有 decoder 都需要相同分辨率。

### CSA2 的三种模式

<Figure src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/figure4-csa2-modes.png" alt="CSA2 三种操作模式对比" />

> 来源：原论文 Figure 4，PDF 第 10 页

每个 CSA2 层被静态分配为三种模式之一，它们的区别在于如何获取 main KV、indexer K 和 Top-K indices：

**Full Mode**（完整计算）：
- 计算自己的 main KV 和 indexer Q
- 从 main KV 投影得到 indexer K
- 运行 indexer 产生新的 Top-K indices（选 512 个 position）
- 建立新的共享 main KV / indexer K；其他模式仍计算自己的 query、SWA、FFN 和 hidden states
- 计算成本最高：需要跑完整的 KV 生成、indexer 打分、sparse attention 三步

**Reindex Mode**（重新索引）：
- 复用最近一个 Full Mode 层的 main KV 和 indexer K（不重新计算 KV）
- 但用自己的 indexer Q 重新打分，产生新的 Top-K indices
- 缓存共享，但 sparse selection 可以变化，不同层可以关注全局上下文的不同部分
- 计算成本中等：省掉了 KV 生成，只跑 indexer 打分 + sparse attention

**Reuse Mode**（完全复用）：
- 复用 main KV 和 Top-K indices（来自最近的 Full 或 Reindex 层）
- 不计算 indexer Q，不做任何打分，直接用已有的 sparse selection
- 省去重新索引；本层的 sparse attention、SWA、FFN 等计算仍然存在
- 这是绝大多数层的模式，20 层 decoder 里有 15 层是 Reuse Mode

具体的层分配如下：

**Encoder**（20 层，CSA2 压缩率 m=2）：
- Layer 1-2：纯 SWA（只有局部窗口注意力）
- Layer 3-20：三组 x 6 层 CSA2，每组配置为 Full + 5xReuse

**Decoder**（20 层，CSA2 压缩率 m=1）：
- 第一组（4 层）：Full + 3xReuse
- 后四组（各 4 层）：Reindex + 3xReuse

这样，20 层 decoder 中有 1 层 Full、4 层 Reindex、15 层 Reuse。一次 query 经过这些层时，有的层重新挑选历史位置，有的层沿用上一组选好的位置；共享缓存并不意味着跳过本层的 attention。Reuse 层的具体 kernel 数量放到后面的部署部分讨论。

三种模式在所有层中都保留各自的 global Q 和 SWA KV。共享的是 main KV 和 indexer K，这两个占了全局 KV cache 的大头。

### 对比 V4 的 CSA + HCA 混合

[V4 报告 §2.3.2](https://arxiv.org/html/2606.19348v1)的 HCA 将序列重压缩后，对压缩条目的全集做 attention。V4.1-Flash 去掉这一分支，以 CSA2 和跨层共享降低全局 KV 占用；不能将其描述为简单删除未压缩的 dense attention。

CSA2 在预训练中直接使用稀疏注意力，没有 dense warm-up。这表明该训练配方能适应稀疏模式，但不等于证明稀疏选择没有信息损失。后文的层级候选限制是在 post-training 才引入，两者的训练阶段需要区分。

另一个简化是去掉原 CSA 的重叠压缩与绝对位置编码，并从 **main KV 投影得到 indexer K**，而非从 hidden states 再走一条独立压缩路径。这也解释了为什么两种缓存可以一起跨层共享。

## Hierarchical Sparse Indexer：限制深层搜索范围

CSA2 的 Reindex Mode 虽然省了 main KV 的计算，但 indexer 仍然需要对全部 causally visible 的 KV positions 打分。对于极长上下文（比如 100 万 token），这个打分成本是线性的，构成了一个瓶颈。

<Figure src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/figure5-hierarchical-indexer.png" alt="Hierarchical Sparse Indexer 机制" />

> 来源：原论文 Figure 5，PDF 第 11 页

Hierarchical Sparse Indexer 的解法很直观，但效果显著：

1. Decoder 的第一个 Full Mode 层对全序列做 Top-K 选择（选 512 个 position），这步是线性的，必须扫描全部 causally visible positions
2. 同时做 blockwise 候选选择：把全序列按每块 8 个 position 分块，以块内最大的 indexer score 作为块分数，再选分数最高的最多 2048 个 block，收集它们覆盖的 position 形成一个 **candidate pool**（最多 16,384 个位置）
3. 后续所有 Reindex Mode 层只在这个 candidate pool 内做 Top-K 选择，不需要回到原始的 N 个 position

这把后续 indexer 的搜索空间从 O(N) 降到了 `O(候选池大小)`，而候选池大小是固定的（16,384），与上下文长度无关。对于 1M token 的上下文来说，这是从 100 万降到 1.6 万，**约 61 倍的搜索空间缩减**。

候选池的假设是：初始层的打分能为深层保留足够有用的位置。这个假设可能在某些检索任务中失效，所以候选池缩小约 61 倍是搜索范围的变化，不是端到端加速倍率，也不是质量无损保证。

层级候选限制在 **post-training 引入**，训练与推理使用相同限制，让模型适应受限搜索域。它并非从预训练第一天就存在；其覆盖率与失误边界仍需评测。

## FP4 主 KV Cache：工程权衡的精细操作

V4.1-Flash 将 main KV 从 FP8 改为 FP4，并在 post-training 做量化感知训练（QAT）。包括 scale、对齐和其他缓存条目后的真实存储量，要按布局计算，不能只根据数据位宽断言总占用精确减半。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/fp4-format-comparison.svg?v=20260910-review1" title="Indexer 与 Main KV：两种 FP4 口径" caption="Indexer Q/K 使用 MXFP4；main KV 参考 NVFP4，使用 E2M1 与每 16 channels 一个 E4M3 scale，省去二级全局 scale。" />

报告 §2.4.4 区分了两种格式：indexer 的 FP4 Q/K 使用 **MXFP4**；main KV 使用 **E2M1 + 每 16 channels 一个 E4M3 scale**，参考 NVFP4 但省去二级全局 scale。[NVIDIA 格式说明](https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/)中，标准 MXFP4 的分块是 32 元素、E8M0 scale；标准 NVFP4 是 16 元素、E4M3 scale，另有全局 FP32 scale。

E2M1 包含 1 bit 符号、2 bit 指数、1 bit 尾数。对 main KV 而言，每块 `16×4+8=72 bit`，即含分块 scale 后平均 4.5 bit/channel，尚未计入对齐。推理时在 attention 前反量化，因而该存储格式不要求硬件原生执行同格式矩阵乘法；这不等于所有平台已有高性能 kernel，也不意味着反量化没有开销。

为什么能省二级 scale？这需要一个定量分析：

- 在报告观测到 RMSNorm 权重最大幅度约为 1 的条件下，512-channel KV latent 的 L2 norm 上界约为 sqrt(512) ≈ 22.6
- RoPE 是正交变换，保持了这个 norm，旋转不改变向量长度
- E2M1 格式配合 E4M3 per-block scale，可以表示的最大 magnitude 是 448 x 6 = 2688
- 训练中实际观察到的 KV cache 最大 magnitude 只有约 10
- 2688 vs 10，有超过 200 倍的余量

这些分析与观测支持在该模型的数值范围内省去二级 scale；它们不是任意模型、任意分布都不会溢出的证明。

FP4 不是免费的，需要 QAT（quantization-aware training），在 post-training 阶段引入。量化策略是**在 RoPE 之后做**（而不是之前）。为什么？因为 attention 计算直接消费 RoPE 后的 KV，如果在 RoPE 之前量化，需要在推理时先反量化、再 RoPE、再 attention，多了一步。实验表明 RoPE 前量化只带来微小的精度提升，不值得这个额外开销。

SWA KV 保持 FP8。全局 KV 的长序列存储收益和短窗口 SWA 的精度权衡不同；移出持久化存储也不意味着 SWA 在运行时没有显存与带宽成本。

## 再次调用：全局 KV 命中，SWA 过期怎么办

现在让这个 coding session 暂停一段时间再继续。**假设前缀 `P` 的全局 KV 仍命中，但 Encoder SWA 的短期检查点已过期**。这时只加载全局 KV 还不能直接续算，因为局部窗口状态也参与后续计算。是否必须为了它重新跑一大段历史，是缓存策略能否省下空间的关键。

报告 §3.2.1 说，V4 的持久化 KV 中 SWA 接近一半。V4 曾提出 Zero SWA Caching，但精确恢复开销过高，生产部署仍保留持久化 SWA。V4.1-Flash 将短期缓存和有界回放结合，才使去掉持久化 SWA 更可行。

多层 SWA 的依赖会向更早位置扩展。`L×n_win` 描述精确恢复所需的回放 token 范围，不是 token-layer 总计算量。对于 CED 的半个主干，相应层数是 L/2。Bounded Replay 把范围截到最近 `n_win=128` 个 token，这些 token **仍经过相关网络层**。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/swa-bounded-replay.svg?v=20260910-review1" title="有界回放缩短的是序列范围" caption="精确恢复的依赖跨层向前扩展；Bounded Replay 仅回放末尾窗口，但保留相关网络层计算。依据 §3.2.2。" />

Encoder 与 Decoder 的策略分别是：

| 状态 | 缓存策略 | 恢复路径 |
|:---|:---|:---|
| 全局 KV | SSD 持久化；前缀命中后复用 | 未命中的 suffix 生成新全局 KV |
| Encoder SWA | Host DRAM 短期保留检查点，分钟级 TTL | miss 时回放 cached prefix 的最后 128 token，再处理新 suffix |
| Decoder SWA | 不进入 prefix cache | 每次 prefill 都将 prompt 末尾 128 token 的 encoder 输出送入 decoder 初始化 |

把表中的恢复策略接回同一个请求 `P + S`，逻辑顺序如下（说明数据依赖，不要求部署实现串行执行）：

1. **取回 `P` 的全局 KV。** 已命中的历史表示继续复用，未命中的 `S` 尚待计算。
2. **恢复 Encoder，再处理 `S`。** 将 `P` 的末尾最多 128 个 token 纳入回放，与新 suffix 一起处理；旧 token 只重建 SWA，不重算或覆盖已有全局 KV；新 token 同时产生全局 KV 和 SWA。
3. **初始化 Decoder。** 取整个 `P + S` 末尾最多 128 个 token 的 encoder 输出，送入 decoder 各层建立其 SWA。若 `S` 不足 128 token，这段窗口还会覆盖 `P` 的末尾；它与上一步的“旧前缀末尾”不是同一边界。
4. **转入生成。** 当前 token 经过 encoder 和 decoder，读取共享全局 KV，并更新局部状态，继续这个 coding session。

若 Encoder SWA 检查点仍命中，第二步可直接从检查点续算新 suffix；第三步仍然要做，因为 Decoder SWA 从不进入 prefix cache。若连全局 KV 都未命中，则相应输入仍需重新 prefill，不能套用这里的恢复捷径。（§3.2.1-3.2.2，PDF 第 19-20 页）

用于短期检查点的 DRAM 池约占 host DRAM 的 10%，这是报告的部署配置。其他服务需要结合活跃会话数量、命中率和恢复开销选择容量。

截断后的状态与精确恢复不等价。报告称内部实验几乎未观察到响应质量下降，并在 post-training 中模拟 Decoder 的同样回放以适应部署。不能把这个有限评测结果扩展成所有缓存恢复点都无损。

### 作者分析：缓存该留多久，取决于复用与恢复代价

保留状态的预期收益，可以定性理解为“未来命中概率 × 避免的恢复成本”，再与容量占用和搬运成本比较。全局 KV 有长尾复用价值；Encoder SWA 主要服务活跃会话；Decoder SWA 则由短回放初始化。恢复变便宜，才允许更积极地释放状态。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/cache-lifecycle.svg?v=20260910-review1" title="三类状态，三种生命周期" caption="全局 KV 长期保留、Encoder SWA 短期保留、Decoder SWA 每次初始化。容量提升不会自动变成等比例命中率提升。" />

全局 KV 压到约 1/4，再移出原来接近一半的持久化 SWA，报告的同负载持久化 footprint 约降至 V4-Flash 的 1/8。这个分解说明存储收益的来源，不能直接推导总体 serving 成本下降 8 倍。

## 继续生成：mHC、Engram、DSpark 分别省在哪里

状态准备好以后，请求进入输出阶段。CED 不再让当前 token 提前退出，encoder 与 decoder 都要参与计算；CSA2 则继续控制历史状态的共享和读取。在这条路径上，mHC 减少激活读写，Engram 提供可预取的条件记忆，DSpark 尝试用一次验证接受多个候选 token。前两者也参与 prefill，并非生成阶段专属。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/component-overview.svg?v=20260910-review1" title="三个效率组件分别减少什么开销" caption="mHC 降低激活读写流量；Engram 提供条件记忆；DSpark 调度草稿验证。依据 §2.4.1-2.4.3。" />

### Single-Pass mHC 和 Mega-mHC

mHC 的全称是 **Manifold-Constrained Hyper-Connections**。它在相邻 Transformer block 间维护多个残差流，并约束连接映射。这里的性能指标是 activation memory traffic，即激活读写流量：传统实现为 `(4n+4)d`，不是驻留激活显存容量。

V4.1-Flash 引入 **Single-Pass mHC**：核心 trick 是把 input mixing 的系数依赖从当前 block 改为前一个 block。也就是说，当前 block 用的 mixing 系数是上一个 block 已经算好的，这打破了 compute → coefficient → mix 的数据依赖链，让三步可以融合为一步。代价是 mixing 系数滞后一步，但实验表明这个一步之差在 deep network 中几乎没有可测量的性能损失。

部署阶段的 Mega-mHC 将残差更新、系数计算与 input mixing 融合为单个 kernel，把中间两遍方案的 `(3n+2)d` 读写流量降到 `(2n+2)d`。这是报告给定算子计数下的流量下界，不能据此承诺整网显存或时延减半。

### Engram：196B 的条件记忆

Engram 是基于 N-gram 的条件记忆模块。可以先把它理解为由 token ID 确定地址的大型查表系统，但完整模块还包括 tokenizer compression、多头 hash、上下文门控和多分支集成，不能简化为查完 embedding 后直接相加。

确定性寻址允许提前知道需要读取哪些条目，有利于预取和计算重叠。实际延迟仍受存储位置、带宽、争用和调度影响，不能保证恒定延迟或完美隐藏搬运。

关键参数：
- 196B 参数均匀分布在两个模块中
- N-gram orders `{2, 3, 4}`；每个 order 有 8 个 hash heads，合计 embedding 维度 2048
- 每个 head 索引约 16M 条目，table size 选择互质的质数
- 放在 layer 1 和 layer 14（zero-indexed），平衡 pipeline 阶段间的内存占用

在推理时，Engram 用确定性寻址，可以从 host memory 通过 RDMA 预取，第一个模块的预取与第一个 Transformer block 的计算重叠。

### DSpark：投机解码

DSpark 是一个基于半自回归 draft + 置信度调度验证的投机解码模块。投机解码的基本思路是：用一个小模型（drafter）快速生成多个候选 token，然后用大模型验证。如果候选正确，就跳过了大模型的多步生成；如果不正确，回退到大模型自己生成。吞吐量提升取决于 drafter 的准确率和验证的开销。

DSpark 的 drafter 由三个 Transformer block 组成，sliding window 128 token，一次前向传播为 5 个 draft position 同时生成 base logits，这是"半自回归"的含义：5 个位置并行生成而不是一个一个生成。轻量的 Markov head 建模 draft token 之间的依赖关系；另一个 confidence head 预测每个位置的条件接受概率，再据此估计候选前缀的存活概率。

DSpark 区别于标准投机解码的关键设计是 **confidence-scheduled verification**：它不使用固定长度的 draft-verify 循环，而是根据 confidence head 的预测估计 prefix survival probability（前缀存活概率）来动态选择验证长度。调度器结合预估的系统吞吐量曲线，为每个请求选择最优的验证长度，目标是最大化系统级的 token throughput 而不是单个请求的 acceptance rate。

与 V3 的 MTP（Multi-Token Prediction）不同，DSpark 不在 backbone pre-training 期间联合训练。它的训练分两个阶段：首先在 backbone pre-training 结束后，冻结 backbone，单独训练 DSpark 模块；然后在 post-training 期间与 backbone 同时训练，但不把 DSpark 目标的梯度回传到 backbone。这个设计让 DSpark 能跟随模型的演化策略（RL 过程中模型行为在变），同时支持在线 serving 和 RL/OPD 的 rollout 加速，实际收益需要分别测量草稿接受率、验证开销和不同负载下的吞吐。

V4.1-Flash 的架构虽然概念上复杂，但推理时的 kernel 流极其精简。这不是偶然，是架构设计和推理系统协同优化的结果。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/inference-architecture.svg?v=20260910-review1" title="EPD 的 E 是视觉编码" caption="部署阶段与 CED 模型分层是两套边界。阶段可独立扩缩容，硬件选型与端到端收益仍需实测。依据 §3.2。" />

### EPD 三级解耦

报告 §3.2 的 **Encoder-Prefill-Decode (EPD)** 指“视觉编码 → prompt prefill → token decode”。这里的 Encoder 是 **vision encoder**，不是 CED 的前 20 层语言主干。

- **E：视觉编码**。把图片处理成视觉特征；纯文本请求没有这一步图像处理。
- **P：Prefill**。运行 CED encoder 的输入处理、全局 KV 投影，以及 decoder SWA 短回放。
- **D：Decode**。encoder 与 decoder 逐 token 前向；main attention 读取所选 KV 与本层 SWA，首个 Full indexer 的全范围扫描需另计。

三个阶段可以独立扩缩容，从而减少不同负载间的资源干扰。但解耦还引入状态传输与调度成本，不能保证完全消除排队或证明某种异构 GPU 配置最便宜。具体硬件选择要按各阶段的算力、带宽、内存和通信需求测量。

### Kernel 极简化

CSA2 Reuse Mode 层（占大多数）的推理 kernel 数量极少：

| 阶段 | Kernel 数 |
|:-----|:---------|
| Prefill（Reuse Mode 层） | 15 |
| Decode（Reuse Mode 层） | 11 |

报告列出了 FlashMLA、Mega-Gate、Mega-mHC、DeepGEMM、TileKernels、DeepSelect 等协同优化。应按各层模式理解这些实现：例如 Reuse 跳过重新索引，不能把所有索引 kernel 都算进每一个 Reuse 层。

减少 kernel 数通常有利于减少 launch 和中间读写开销，但仅凭数量不能判断 overhead 已可忽略或 GPU 达到理论利用率。需要 profiler、批量大小、硬件与端到端时延共同验证。

### 持久化与运行时开销分别算

报告中的全局 KV 以完整 prefix 为粒度，在 SSD 侧采用 LRU 管理，目标保留期为 72 小时以上；Encoder SWA 在 host DRAM 保存 prompt/output 末尾检查点，使用分钟级 TTL。Decoder SWA 不进入 prefix cache。保留时间属于具体服务配置，命中率还取决于流量与淘汰，不能仅由 TTL 推出。

| 指标 | 报告结果 | 不能直接推出什么 |
|:---|:---|:---|
| 全局 KV / token | 3514 B → 890 B，约 3.95 倍 | 全模型内存缩小 3.95 倍 |
| 同负载持久化 KV footprint | 约为 V4-Flash 的 1/8 | 命中率提高 8 倍 |
| CED 长 prompt prefill 计算 | 相比完整通过两半主干接近减半 | 任意请求端到端时延减半 |
| Reuse 层 decode kernels | 11 个 | launch overhead 消失 |

### 容量算例：只算明确分配给全局 KV 的预算

假设**整个服务实例**扣除权重、SWA、工作区后，还有 40 GB 可分配给全局 KV。每个独立 session 含 1,000,000 token，不考虑跨 session 共享和额外分配开销：

| 模型 | 每个 session 全局 KV | 40 GB 下的理论容量 | 完整 session 上限 |
|:---|---:|---:|---:|
| V4-Flash | 3.514 GB | 11.38 | 11 |
| V4.1-Flash | 0.890 GB | 44.94 | 44 |

比值来自 `3514/890≈3.95`。若预算改为 40 GiB，理论容量分别约 12.22 和 48.26，不能混用两种单位。这个算例没有证明单卡 H100 能装下模型，也没有给出实际并发吞吐；专家分片、卸载和传输都需要另行设计。

### 作者分析：优化目标应是每个验收通过任务的成本

Agent 任务会经历多次模型调用、工具操作和失败重试。单次 KV 或 tokens/s 无法回答“一件事做成要花多少钱”。更有用的指标是：一批尝试的模型、工具、重试与验收成本之和，除以验收通过的任务数，并同时报告成功率与 P50/P95 完成时延。若没有任务验收通过，则不能给出有限的每成功任务成本。

最小测量方案可以固定任务集与 scaffold，比较冷缓存、热缓存，以及 low/high/max effort。记录未缓存输入量、输出量、账单、成功率与时延。若能控制自建部署，再拆出“全局 KV 命中而 Encoder SWA 失效”的恢复场景；API 黑盒无法观测该状态时，不应声称已经测到它。

架构节省的预算可能被更长推理或更多并行分支消耗。只有在同任务质量与时延要求下比较，才能知道容量收益是否转化成实际经济收益。

## 训练基础设施

V4.1-Flash 的架构创新对训练基础设施提出了独特的挑战。

### CSA2 的分布式训练支持

CSA2 的跨层 KV 共享在 pipeline parallelism 中造成了特殊问题：共享 attention 组件的层可能被分配到不同的 pipeline stage，传统的 stage-local 执行模式不适用。

DeepSeek 用三个机制解决：

1. **Shadow indexers**：在每个参与共享的 pipeline stage 放置一个轻量的 indexer 副本（shadow）。虽然 indexer K 在逻辑上属于一个 Full Mode 层（owner），但在物理上，每个需要使用这些共享参数的 pipeline stage 都持有一份可执行的 replica。Owner 负责优化和 checkpointing，shadow 的参数通过梯度聚合和参数同步保持一致。这样 pipeline scheduler 不需要把共享层当成特殊单元来处理，每个 stage 看到的都是本地的、完整的计算图。
2. **Pipeline payload extensions**：source 与 consumer 跨 pipeline stage 时，把共享 KV、indexer K、Top-K 等状态编入现有点对点通信路径，保持与 context parallel 分区一致。复用通信路径不等于已经证明额外通信完全被 bubble 隐藏。
3. **Micro-batch-level shared-state management**：运行时跟踪每个微批次的共享状态及其 forward、recompute、backward 消费者，在最后一次使用后释放。不同微批次可并行执行，但不因此共享彼此的样本 KV；这是生命周期管理，不是跨微批次复用样本状态。

### 多模态训练优化

V4.1-Flash 在 45T 多模态数据上训练，序列长度最长 1M token。这带来了严重的 I/O 和内存压力。

**Balanced image sharding**：单个超长的 image-dense 序列可能耗尽一个节点的 I/O 和 CPU 资源。解法是把每个序列的图片按 CP rank 做负载均衡分片，每张图只读取一次。关键的判断条件是一个简单的不等式：

```
N × ρ / B_IO < N × C / B_GPU  ⟺  ρ < (B_IO / B_GPU) × C
```

其中 N 是 token 数，ρ 是每 token 的原始字节数，C 是每 token 的计算量，B_IO 是文件系统吞吐（bytes/s），B_GPU 在这个式子中表示 GPU 计算吞吐（FLOPs/s），不是显存带宽。因为 N 可以约掉，这个判断只取决于 per-token 的 IO 量和计算量的比值。对于 ρ 较大的 vision-module 配置（高分辨率、大 patch），存储吞吐才会成为瓶颈；对于生产规模的模型，通常是 compute-bound 的。

**Communication-computation overlap for ViT**：vision encoder 的对比学习阶段需要跨 data-parallel rank 做 all-gather。DeepSeek 利用了一个对称性，text features 只需要 gathered visual features 的梯度，反之亦然，安排 all-gather 与计算重叠。具体来说，调度是：

```
Forward(V) → (Forward(T) ‖ AllGather(V)) → ∇_Text
           → (Backward(T) ‖ AllGather(T)) → ∇_Vision → Backward(V)
```

其中 `‖` 表示重叠执行。Visual features 在 text forward 期间 gather，text features 在 text backward 期间 gather。报告描述了在其配置下隐藏通信的调度方式；其他配置仍需验证重叠程度。

**End-to-end parallelism**：vision encoder 从 LLM 的参数树中独立出来，每个训练步分为 vision encoder forward、LLM forward/backward、vision encoder backward 三个阶段，视觉处理不干扰 LLM 的 text-only 并行策略。

### 大规模 Agent Task 合成

DeepSeek 把每个训练任务形式化为一个三元组：(problem, environment, verification system)，在两个维度评估质量，difficulty（确保任务非平凡，不是靠简单模式匹配就能完成的）和 correctness（确保三个组件之间没有关键缺陷，比如 problem 描述和 verification 预期不一致）。用 difficulty 和 correctness 作为 reward signal，迭代训练模型的任务构建和质量检验能力。同时，他们还监控 RL 任务的全生命周期，每当一个任务被用于新的 RL run，产生的 trajectory 都会被重新审计，为任务质量提供持续反馈。

**General Agent 环境构建**：收集内部员工和外部合作者使用 DeepSeek 模型的真实工作流反馈。重点关注两类数据：negative feedback（模型失败的案例）和 model failure cases（输出不满足用户预期的情况）。基于这些真实交互，构建 mock 版本的真实工具和系统，以近似重现失败时的交互条件。然后重建失败场景，让 RL 在这些真实失败的近似重现上做 targeted training。

**Coding Agent 环境构建**：这部分的自动化程度最高。从两个来源获取任务，内部编码 session（高复杂度的真实任务）和公共 GitHub 仓库（满足 star 数阈值的项目）。环境构建完全由 multi-agent pipeline 完成：
1. 一个 **feasibility agent** 判断项目是否可在容器内构建和运行、是否可以自动化验证
2. 一个 **design agent** 选择合适的 commit 作为起点，设计多个实现方向，并为每个方向构建 fail-to-pass 和 pass-to-pass 的评测点
3. 一个独立的 **quality-inspection agent** 审查环境正确性、任务描述和评测点之间的一致性、以及"可 hack 性"（agent 是否可以通过取巧方式通过测试而不真正解决问题）
4. 如果 inspection 不通过，一个 **repair agent** 修复发现的问题、调整评测点的难度、去掉过于简单或过于困难的测试
5. 最后，多个独立的 solving agent 尝试完成任务，它们的 trajectory 和 quality-inspection 结果一起进入任务质量的最终评估

### DSec：百万级沙盒平台

随着 agent 训练环境的数量从 V3 到 V4.1 快速增长，DeepSeek 构建了 **DeepSeek Elastic Compute (DSec)**，一个生产级的沙盒平台。

DSec 的设计选择非常务实：

- **放宽全局一致性的调度**：DSec 按 scale unit 对计算节点分片，并使用多个独立的 placement engine 副本，依据近期资源测量做近似分配。最终由每个计算节点执行本地 admission control，超过阈值则拒绝新 placement。这是用本地资源约束支撑最终一致性的系统选择，不是对 Kubernetes 所有场景的性能判断。
- **NUMA-aware 隔离**：worker VM 绑定单个 NUMA domain，容器的 CPU 和内存分配限制在 VM 本地资源中，以控制内存压力、内核锁争用和故障范围。报告称，在可比工作负载下，出现可测端到端退化前的单节点容器密度从约 1,000 提高到 2,500 以上。
- **Latency-Sensitive 调度**：高密度部署下，后台任务可能干扰正在评估的 agent。DSec 引入 LS（Latency-Sensitive）执行类，对非 LS 任务使用 `SCHED_IDLE` 降低调度优先级，并用 core scheduling 确保同一优先级的任务才共享超线程，消除来自 sibling hyperthread 的干扰。
- **eBPF 网络策略**：这是最后一道防线，用于遏制 agent 的 reward hacking 行为

<Callout>
报告描述了 RL 中暴露的 reward hacking 与隔离问题，包括 XFS/AppArmor 相关访问绕过、从 package mirror 泄漏答案、破坏系统二进制文件等。DSec 采用逐沙盒 AppArmor profile 与细粒度 eBPF 网络策略等防御。如果 agent 使环境崩溃，系统会将其记为 **failed trajectory**，并向 RL 框架发送 repercussion，使这类破坏进入训练反馈。
</Callout>

### 可控推理力度

V4.1-Flash 在 RL 阶段引入了一个 scalar effort level b（范围 1-100）作为显式条件信号，控制模型的推理深度。

核心机制是一个与 effort level 相关的 **指数 token penalty**：

```
r_len = -min(C_max, k(b) * l / L_norm)
k(b) = k_0 * exp(-(b - b_min) / tau)
```

effort 越高，token penalty 系数 k(b) 越小（指数衰减），同等长度的惩罚更小，允许模型选择更长的推理链。反之，低 effort 会对长输出施加重惩罚，迫使模型精简回答。

这个设计的工程价值在于：**一个 checkpoint 可以通过改变 b 值来适配不同的成本-质量需求**。不需要维护多个模型副本，不需要为不同的 tier 分别训练，同一个模型在推理时通过 prompt 中的一个数字就能切换行为模式。API 层面暴露了三个 tier：low (b=50)、high (b=75)、max (b=100)。

Figure 9 展示了 effort 从 25 到 100 的完整曲线，结果很有启发性：
- 8 个 reasoning benchmark 的平均 Pass@1 从 67.1%（effort=25）提升到 76.3%（effort=100），提升了 9.2 个百分点
- DeepSWE v1.1 从 66.0% 到 74.2%，Terminal-Bench v2.1 从 82.4% 到 90.6%
- 大部分增益集中在 effort 60-80 范围，60-80 这个区间恢复了 maximum setting 的大部分准确率，同时只用了不到一半的 token budget
- Effort 100 相比 80 带来的边际改善很小（1.6-1.8x 的 trajectory 延长换来 2-3 个百分点），maximum tier 适合用于最难的任务
- 有趣的是，effort control 学到的行为从 single-response reasoning 任务平滑地迁移到了 long-horizon agentic 任务，在 agent 场景中，effort level 控制的是整个 trajectory 的探索和验证深度，而不仅仅是单步回复的长度

这提供了一个成本与质量的控制旋钮，但不保证某个档位适合所有同类任务，也不保证 max 一定成功。应用应在自己的任务集上选择满足验收与时延要求的最低合适档位，记录提升 effort 后的额外费用和成功率增益。

### 异步 Post-Training 基础设施

RL rollout 的 long-tail 问题是训练效率的主要瓶颈，少数极长的 rollout 会拖慢整个 batch 的完成时间，导致 GPU 空闲等待。V4.1-Flash 的 post-training 基础设施支持异步 sample 生成：rollout 和训练共享物理设备，分时执行。这意味着不需要单独的 rollout 集群和 training 集群，在 training phase，GPU 跑梯度更新；在 rollout phase，同一批 GPU 跑模型推理生成 trajectory。

几个有意思的工程细节：
- **Sample-level dispatch**：经过对 batch-level 和 prompt-level dispatch 的实验后，最终选择 sample-level，每当新完成的 sample 数达到 GRPO group size，就 dispatch 下一个 prompt。Batch-level 粒度太粗，导致训练 metrics 剧烈波动；prompt-level 粒度则容易在 long-tail sample 上卡住。报告在其工作负载下选择了 Sample-level；不能将此视为所有训练系统的最优粒度。
- **Token-level interruption**：rollout 可以在任意 token boundary 暂停，KV cache 和 expert routing state 都 persist 到存储。当新 checkpoint 准备好后，从断点恢复生成，不需要 re-prefill 已经生成的 prefix。这对 long-horizon agent 场景特别重要，一个 100K token 的 coding agent rollout 如果因为 checkpoint 更新而从头开始，浪费的计算量是巨大的。
- **Concatenated routing-replay**：跨 checkpoint 的 sample（前半段用 checkpoint A 生成，后半段用 checkpoint B 生成），拼接每段的 expert routing 决策而不是用新 checkpoint 重算旧段的 routing。这保持了 MoE routing 的一致性。
- **Over 40 teacher models for OPD**：on-policy distillation 阶段使用超过 40 个异构 teacher model。Teacher 可能和 student 架构完全不同，full-vocabulary OPD 只需要 output logits 对齐，不需要内部结构匹配。基础设施支持在训练过程中动态切换 teacher 配置，包括每个 dataset 使用不同的 teacher、并发限制不同的 teacher 以平衡成本。

### 异步的代价：长度偏差与策略陈旧

异步生成让训练不必等待所有长尾样本，但完成顺序会改变采样分布。短样本更早返回，早期训练 batch 因而偏短；跨 checkpoint 的 trajectory 又混有旧策略生成的片段。保存 KV、回放 routing 解决的是恢复与路由记录问题，不会自动消除这些统计偏差。

报告 §5.2.2 给出了对应控制：按 dataset 设置并发，丢弃部分早返回短样本以调节长度分布；通过调度约束 off-policy 程度，并对过旧 token 的 loss 做 mask。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/async-training-tradeoffs.svg?v=20260910-review1" title="异步训练：效率收益伴随新的偏差" caption="短样本先到与轨迹跨 checkpoint 分别带来分布偏差和策略陈旧；需要采样控制与 loss masking。依据 §5.2.2。" />

**作者分析：** 等待减少后，正确性压力转移到“训练数据是否仍代表目标分布”。判断异步方案不能只看 GPU 利用率，还应观察样本长度、任务构成、策略陈旧程度及对应质量变化。

### 作者分析：让训练适应部署时的近似

这篇报告中的三种取舍可以放在一起看：FP4 QAT 适应数值误差，后训练中的层级候选限制适应搜索域缩小，Decoder SWA 回放适应状态截断。训练与部署采用一致约束，是让这些效率优化可用的重要条件，但不是所有边界都无损的保证。

值得增加的压力测试，是把关键信息放在 block 边界、候选池容易遗漏的位置、缓存恢复点附近，再比较冷启动与不同恢复位置下的结果。报告 §6 已把长上下文稀疏检索和 SWA 恢复边界列为后续工作；这里提出的是验证方案，不是本文完成的实验。

Multi-agent 初步实验显示了令人鼓舞的结果。DeepSeek 使用 DeepSeek Harness 的 Agent Team 模式，一个 lead agent 可以通过 `spawn_teammate` 创建 named persistent teammates，每个 teammate 在独立的 fresh/fork 模式下工作，共享同一个代码仓库，通过 `send_message` 进行异步通信。

训练中，Agent Team 将任务质量、协作 bonus 与 latency penalty 结合。系统把执行事件及协作依赖表示为 DAG，以模型估计的 prefill/decode 时间与实测工具耗时估计路径延迟，再惩罚关键路径。其目标是奖励有效并行，同时减少训练奖励对服务排队波动的依赖；它并不是端到端实际延迟或总费用的替代测量。

### 作者分析：多 agent 要分别比较时间预算与费用预算

并行能缩短一些可拆任务的关键路径，但会增加分支探索、汇总和沟通，也可能产生重复工作与共享仓库冲突。因此需要两组评测：固定截止时间下比较成功率；固定 token 或费用预算下再比较成功率。前一组回答“能否更早做成”，后一组回答“是否更划算”。当前论文实验不能替代后一组证据。

对不可拆的串行任务，多开 agent 未必缩短关键路径；对可独立验证的子任务，委派可能有用。模型侧节省的预算是否应该投入更多分支，应由这些任务结构与验收结果决定。

## 工程启示与局限

这份报告把架构、训练和部署放在同一个约束下设计：减少需存储的全局状态，限制深层搜索范围，并降低局部状态的恢复代价。对部署而言，这扩大了长上下文服务的容量空间，但实际收益仍需要权重布局、带宽、批量、缓存命中和 SLA 的联合测量。

硬件兼容性也要分层理解：main KV 在 attention 前反量化是格式层面的设计选择；框架是否支持、kernel 是否高效、整机吞吐是否达标是后续问题。已有 V4 的跨平台实践不能直接证明 V4.1-Flash 已在同平台完成验证。Effort 提供了行为控制，也不保证成本或质量恒定。

报告 §6 提到尚未充分刻画的稀疏检索与 SWA 恢复边界，并承认最困难的多模态任务与领先闭源系统仍有差距。本文的结论分为三个证据层级：

## 总结与个人观点

**第一，长上下文 Agent 的重要问题之一是状态成本。** 全局 KV 如何压缩、活跃状态留多久、过期后如何恢复，会共同影响容量与延迟。890 B/token 展示了一个具体设计的结果，没有证明已达到工程极限；更值得跟踪的是它如何改变可服务的任务与负载范围。

**第二，部署近似需要训练适应与边界测试一起支撑。** 量化、候选限制、短窗口恢复分别引入不同误差。平均 benchmark 的结果支持继续使用和探索这些方法，但不能代替对检索遗漏、缓存恢复点和组合误差的验证。

**第三，效率改进应最终回到任务验收。** 数据与环境工程可以在成熟后训练配方下提供改进空间，异步调度则需要控制长度偏差与策略陈旧。无论优化的是 KV、rollout 还是多 agent 协作，都应同时比较成功率、完成时间与费用，才知道节省的计算是否变成了实际价值。
