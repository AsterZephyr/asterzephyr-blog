# DeepSeek-V4.1-Flash 技术深度解析：把 KV Cache 压缩做到极致

> 原论文/报告：DeepSeek-V4.1-Flash: Pushing the Limits of KV Cache Compression<br/>
> 作者/团队：DeepSeek-AI<br/>
> 发布：Technical Report, September 2026<br/>
> 原文：[https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)

每个 token 的全局 KV cache 只占 890 字节。这是 DeepSeek-V4-Flash 的四分之一，DeepSeek-V1 的四百三十七分之一。当你用它处理一个 100 万 token 的长上下文 agent 任务时，仅全局 KV cache 就能从 V1 时代的约 370GB 降到不到 1GB。这不是量变，是质变，它直接改变了长上下文模型的部署经济学。

2026 年 9 月，DeepSeek 发布了 DeepSeek-V4.1-Flash 的技术报告。这份报告不是一次常规的模型迭代，而是从架构、精度、部署三个维度联合压缩 KV cache 的系统性工程方案。本文对这 51 页做一次深度拆解。

## 为什么这篇报告重要

长上下文 agent 是当前 LLM 应用的核心方向。Claude Code、Codex、DeepSeek Harness 这类 coding agent，一次任务的 prompt 动辄几十万 token，加上多轮 tool call 的输入累积，实际上下文消耗远超传统聊天场景。一个典型的 coding agent session 可能是这样的：系统 prompt 2K + 仓库上下文 100K + 前几轮 tool call 输出 200K + 当前 prompt 5K = 307K token。而且每次 tool call 回来都要 re-prefill 这些上下文。在一个 20 轮的 session 中，累积的 prefill 负载可以轻松达到数百万 token。

在这种场景下，模型部署的真正瓶颈是**内存**，不是算力。NVIDIA 的研究博客指出，仅 256K token 的未压缩 FP16 KV cache 就需要约 16.3 GB；百万 token 的 agent 工作负载下，这才是部署约束。行业共识也印证了这一点：decode 阶段是 memory-bandwidth-bound 而非 compute-bound。具体来说有三层：

1. **运行时 KV cache**（HBM）：决定了单卡能服务多少并发请求
2. **持久化 KV cache**（SSD / Host Memory）：决定了 prefix cache 的命中率和多轮对话的成本
3. **数据传输带宽**（PCIe / NVLink / RDMA）：决定了 KV cache 加载的延迟

DeepSeek 从 V1 到 V4.1-Flash，每一代都在压缩 KV cache，而且压缩手段在不断进化：

| 模型 | 时间 | 全局 KV Cache (bytes/token) | 压缩手段 |
|:-----|:-----|:---------------------------|:--------|
| DeepSeek-V1 | 2023.11 | 389,120 | 标准 MHA |
| DeepSeek-V3.2 | 2025.12 | 48,068 | MLA (Multi-head Latent Attention) |
| DeepSeek-V4-Flash | 2026.04 | 3,514 | CSA + HCA 混合 + FP8 |
| **DeepSeek-V4.1-Flash** | **2026.09** | **890** | **纯 CSA2 + FP4 + CED** |

V4.1-Flash 的报告把这个压缩做到了当前的工程极限，而且报告诚实地讨论了每个优化的代价和未验证的边界条件。这种透明度在工业界的技术报告里不常见。

DeepSeek 在发布当天就根据这个架构的推理成本节省调整了 API 定价，KV cache 压缩带来的是真金白银的成本下降，不只是论文上的数字好看。

## 架构全景：CED + CSA2 为核心的双轴优化

DeepSeek-V4.1-Flash 是一个多模态 MoE 模型，552B 主干参数 + 196B Engram 参数。总参数量大，但 prefill 阶段每个 token 只激活 8B 参数，decode 阶段激活 16B。对比一下：GPT-5.6 Sol 和 Opus-5 的激活参数都在 100B+ 量级。V4.1-Flash 用不到它们 1/6 的激活参数，在大多数 agentic benchmark 上打平甚至超越。

它的核心架构创新可以沿两个轴来理解：

- **纵轴（层间）**：Causal Encoder-Decoder (CED) 把 40 层 Transformer 分成 20 层 encoder + 20 层 decoder，decoder 的全局 KV 从 encoder 投影而来，prefill 计算量减半
- **横轴（层内）**：Compressed Sparse Attention 2 (CSA2) 跨层共享全局 KV 和 indexer K，配合 Hierarchical Sparse Indexer 把每层的 attention 计算从全序列扫描降为候选池内搜索

<Figure src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/figure3-overall-architecture.png" alt="DeepSeek-V4.1-Flash 整体架构图" />

> 来源：原论文 Figure 3，PDF 第 7 页

这张架构图值得仔细看：

- **Encoder（左）**：底部两层用纯 SWA，上面三组各 6 层用 CSA2（压缩率 m=2），每组第一层 Full Mode，其余 Reuse Mode
- **Decoder（右）**：五组各 4 层用 CSA2（压缩率 m=1），第一组 Full + Reuse，后四组 Reindex + Reuse
- **连接点**：CED 桥，decoder 的全局 KV 从 encoder 最后一层（第 20 层）的 hidden state 投影而来
- **辅助组件**：Single-Pass mHC、Engram（两个模块分别在 layer 1 和 14）、DSpark（投机解码）、Hierarchical Sparse Indexer

每个 token 在 prefill 阶段只激活 8B 参数（只走 encoder），decode 阶段激活 16B 参数（encoder + decoder）。这个不对称设计是为 agent 工作负载量身定制的，agent 场景是 prefill heavy，大量的 tool output 和系统 prompt 需要处理，但每轮生成的 token 相对少。

## CED：把 Prefill 成本砍半

传统 decoder-only 架构中，每一层都需要计算全序列的 KV cache。对于一个 40 层的模型处理长度为 N 的序列，prefill 的总计算量与 N x L 成正比。算个具体的数：假设 N = 1M token，L = 40 层，那么传统架构需要对 4000 万 (token x layer) 组合做 attention 计算。

为什么 prefill 成本在 agent 场景下特别痛？因为 agent 的工作模式是"读多写少"，一次 coding agent 的调用可能注入 50 万 token 的系统 prompt + 仓库上下文 + 历史 tool output，但只生成几千 token 的回复。传统架构里每一层都要处理这 50 万 token 的全量 attention，而实际上你只需要最终层的表示来生成 decoder 的 KV cache。

CED 的核心思路受 YoCo（You Only Cache Once）启发，但做了关键改进：把模型拆成 encoder 和 decoder 两半，decoder 的全局 KV 不再由每一层独立计算，而是从 encoder 最后一层的 hidden state 投影得来。与原始 YoCo 相比，CED 引入了"结构性改进以增强 KV cache 的容量和计算深度"（原文），encoder 端的 KV 生成经过了完整的 20 层深度计算，比 YoCo 的浅层共享方案有更强的表示能力。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/ced-data-flow.svg" title="CED 数据流：Encoder 的 hidden state 如何投影到 Decoder 的全局 KV" caption="Encoder 计算完成后，其第 L/2 层的 hidden state 通过层相关的投影矩阵生成 decoder 每一层的全局 KV（博主自绘，基于原论文 Section 2.2）" />

具体来说，对于 decoder 的第 l 层（l > L/2），其全局 KV 的计算方式是：

```
C_l = H_{L/2} * W_l^{KV}    // 全局 KV 从 encoder 最后一层投影
Z_l = H_{L/2} * W_l^{Z}     // 压缩权重也从 encoder 投影
```

这意味着：
- **Prefill 阶段**：只需要跑 encoder 的前 20 层，就能获得 decoder 所有层的全局 KV。Decoder 阶段不需要重新处理 prompt，全局上下文已经被编码在投影矩阵的输出里了。
- **Decode 阶段**：decoder 正常工作，每层用投影来的全局 KV + 自己逐 token 计算的 SWA KV

具体算一下收益：对于 1M token 的上下文和 128 token 的 SWA 窗口，传统架构 prefill 需要处理 N x L = 1M x 40 = 4000 万 token-layer。CED 只需要 N x L/2（encoder 部分）+ n_win x L/2（decoder 的 SWA replay 部分）= 1M x 20 + 128 x 20 = 2000.256 万 token-layer。**省掉的不是 20 层的边际改善，而是 50% 的绝对计算量**。而且当 N 越大（agent 场景恰恰如此），n_win x L/2 这一项就越不重要，CED 的收益越接近理论极限的 50%。

<Callout>
CED 的复杂度从 O(NL) 降到 O(NL/2 + n_win x L/2)，当 N 远大于 n_win 时，约等于直接减半。对于 100 万 token 上下文 + 128 token 窗口的场景，这个减半是实打实的。
</Callout>

但 CED 引入了一个工程问题：decoder 的 SWA KV 仍然需要逐层计算（从各层自己的 hidden state 派生），这使得 SWA replay 过程（恢复 SWA cache miss 时的状态）变得必要。DeepSeek 用 SWA Bounded Replay 来解决这个问题（后面会详细讲）。

## CSA2：三个维度的 KV Cache 压缩

KV cache 的大小可以沿三个乘性维度压缩：

1. **Entry 维度**（每个 head 的 KV 大小）：GQA / MLA 通过共享或压缩 head 来减少
2. **Sequence 维度**（每层存多少 token 的 KV）：CSA 通过 m:1 压缩来减少
3. **Layer 维度**（多少层需要独立存 KV）：跨层共享来减少

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/csa2-compression-dimensions.svg" title="KV Cache 压缩的三个维度" caption="CSA2 同时在三个维度上做压缩：entry 维度用压缩投影，sequence 维度用 m:1 token 压缩，layer 维度用跨层 KV 和 indexer K 共享（博主自绘，基于原论文 Section 2.3）" />

之前的方法（IndexCache、YOIO、HySparse）通常只覆盖其中一两个维度，而且混合架构（V4 的 CSA + HCA）会保留一些 full attention 层，限制了压缩上限。同期的跨层 KV 共享工作（CommonKV、KVSharer）也只做缓存共享，不涉及 sparse indexing。CSA2 的核心贡献是**同时在三个维度上做压缩，并且完全去掉了 full attention 层**，把 cache sharing 和 index reuse 解耦，这在现有工作中是独创的。

值得和几个主流的 sparse attention 方案做个对比：H2O 是基于 eviction 的（淘汰不重要的 token KV），问题是被淘汰的信息无法恢复；Quest 做 query-aware block selection，每次 attention 都要重新选块；MoA（Mixture of Attention）混合 sparse 和 dense 层，仍然保留 full attention 层。CSA2 的三模式方案本质上不同，它不淘汰任何 KV，而是通过跨层共享来避免重复存储，同时通过 Hierarchical Sparse Indexer 来控制每层的搜索成本。

理解 CSA2 还需要理解**压缩率 m** 的含义：在 sequence 维度上，每 m 个相邻 token 的 KV 被压缩为一个条目。Encoder 使用 m=2（两个 token 压缩为一个），decoder 使用 m=1（不做 sequence 压缩，只做 sparse selection）。m=2 相当于在 sequence 维度上多了一倍的压缩，但代价是分辨率降低，encoder 可以接受这个代价因为它处理的是完整的上下文，而 decoder 需要更精细的 token-level attention 来生成准确的输出。

### CSA2 的三种模式

<Figure src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/figure4-csa2-modes.png" alt="CSA2 三种操作模式对比" />

> 来源：原论文 Figure 4，PDF 第 10 页

每个 CSA2 层被静态分配为三种模式之一，它们的区别在于如何获取 main KV、indexer K 和 Top-K indices：

**Full Mode**（完整计算）：
- 计算自己的 main KV 和 indexer Q
- 从 main KV 投影得到 indexer K
- 运行 indexer 产生新的 Top-K indices（选 512 个 position）
- 这是唯一产生"新信息"的层
- 计算成本最高：需要跑完整的 KV 生成、indexer 打分、sparse attention 三步

**Reindex Mode**（重新索引）：
- 复用最近一个 Full Mode 层的 main KV 和 indexer K（不重新计算 KV）
- 但用自己的 indexer Q 重新打分，产生新的 Top-K indices
- 缓存共享，但 sparse selection 可以变化，不同层可以关注全局上下文的不同部分
- 计算成本中等：省掉了 KV 生成，只跑 indexer 打分 + sparse attention

**Reuse Mode**（完全复用）：
- 复用 main KV 和 Top-K indices（来自最近的 Full 或 Reindex 层）
- 不计算 indexer Q，不做任何打分，直接用已有的 sparse selection
- 计算量最小，只做一次 sparse attention
- 这是绝大多数层的模式，20 层 decoder 里有 15 层是 Reuse Mode

具体的层分配如下：

**Encoder**（20 层，CSA2 压缩率 m=2）：
- Layer 1-2：纯 SWA（只有局部窗口注意力）
- Layer 3-20：三组 x 6 层 CSA2，每组配置为 Full + 5xReuse

**Decoder**（20 层，CSA2 压缩率 m=1）：
- 第一组（4 层）：Full + 3xReuse
- 后四组（各 4 层）：Reindex + 3xReuse

<Callout>
在 V4.1-Flash 的 decoder 里，20 层 CSA2 被分成 5 组 x 4 层。第一组是 Full + 3xReuse，后四组都是 Reindex + 3xReuse。也就是说，20 层 decoder 里只有 1 层做完整计算，4 层做重新索引，15 层纯复用。Reuse Mode 层在 prefill 时只需 15 个 kernel，decode 时只需 11 个。
</Callout>

三种模式在所有层中都保留各自的 global Q 和 SWA KV。共享的是 main KV 和 indexer K，这两个占了全局 KV cache 的大头。

### 对比 V4 的 CSA + HCA 混合

V4 使用 CSA（Compressed Sparse Attention）和 HCA（Heavily Compressed Attention）的混合架构。HCA 层保留了部分 full attention 的特性，但代价是 KV cache 不能做到极致压缩。V4.1-Flash 直接去掉了 HCA，全部使用 CSA2，同时通过更激进的跨层共享来弥补信息损失。

这个设计决策的勇气来自一个经验发现：**在训练时就使用 sparse attention（而不是先 dense 再切换），模型可以学会适应 sparse pattern，性能损失微乎其微。** V4.1-Flash 从头开始用 sparse attention 训练，序列长度 64K，没有任何 dense attention 热身阶段。这和很多后训练稀疏化的方案不同，那些方案先用 dense attention 训练一个好模型，然后剪枝到 sparse，容易出现性能退化。V4.1-Flash 证明了一条更激进但更干净的路径：如果你从训练的第一天就告诉模型"你只能看到 sparse selection 的 token"，模型会学会在这个限制下工作得很好。

CSA2 相比 CSA 的另一个简化是去掉了 compressor 和 indexer 的独立压缩路径。在原始 CSA 中，compression ratio m 的压缩需要对每 2m 个原始 KV 条目做有重叠的压缩，还需要 absolute positional embedding 来编码被压缩条目的位置。CSA2 去掉了这个 overlap 和 absolute PE，改为直接从 hidden state 投影得到 indexer K。这两个简化在训练和推理效率上都有实质提升。

## Hierarchical Sparse Indexer：让深层 Indexer 成本变常数

CSA2 的 Reindex Mode 虽然省了 main KV 的计算，但 indexer 仍然需要对全部 causally visible 的 KV positions 打分。对于极长上下文（比如 100 万 token），这个打分成本是线性的，构成了一个瓶颈。

<Figure src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/figure5-hierarchical-indexer.png" alt="Hierarchical Sparse Indexer 机制" />

> 来源：原论文 Figure 5，PDF 第 11 页

Hierarchical Sparse Indexer 的解法很直观，但效果显著：

1. Decoder 的第一个 Full Mode 层对全序列做 Top-K 选择（选 512 个 position），这步是线性的，必须扫描全部 causally visible positions
2. 同时做 blockwise 候选选择：把序列分成 2048 个 block（每 block 8 个 position），对每个 block 取其 position 中最大的 indexer score，然后选 score 最高的那些 block，收集它们覆盖的 position 形成一个 **candidate pool**（最多 16,384 个位置）
3. 后续所有 Reindex Mode 层只在这个 candidate pool 内做 Top-K 选择，不需要回到原始的 N 个 position

这把后续 indexer 的搜索空间从 O(N) 降到了 O(候选池大小)，而候选池大小是固定的（16,384），与上下文长度无关。对于 1M token 的上下文来说，这是从 100 万降到 1.6 万，**60 倍的搜索空间缩减**。

为什么这个近似是安全的？直觉上，如果第一个 Full Mode 层认为某些 position 不重要（没被选进 candidate pool 的 block），那么更深的 Reindex 层大概率也不需要它们。信息的"重要性"在层间是相关的，相邻层关注的 position 集合高度重叠。

关键点在于这个机制是 **training-aware** 的：训练时就应用了同样的候选限制，所以深层的 indexer 从一开始就学会了在限制的搜索域内工作。这不是一个后期加上的近似优化，而是架构的一部分。

## FP4 主 KV Cache：工程权衡的精细操作

V4 对 indexer cache 使用 FP8 量化。V4.1-Flash 更进一步，把 main KV cache 也压缩到 FP4，存储开销直接减半。这个决策不是拍脑袋，论文花了相当篇幅解释为什么 FP4 在 KV cache 这个特定场景下是可行的。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/fp4-format-comparison.svg" title="FP4 量化格式选择" caption="V4.1-Flash 选择 E2M1 格式（2 bit 指数 + 1 bit 尾数），使用 MXFP4 标准中的单 E4M3 scale（每 16 channel 一个），并且省略了二级全局 scale（博主自绘，基于原论文 Section 2.4.4）" />

具体选择是 **E2M1 with one E4M3 scale per 16 channels**，遵循 OCP 标准的 MXFP4 格式，但省略了二级全局 scale。这个格式与 NVIDIA 发布的 NVFP4 KV cache 标准一致，硬件层面支持原生反量化后直接做 attention，不需要额外的 kernel。

为什么选 E2M1 而不是 E1M2？E2M1 有 2 bit 指数（动态范围更大，可以表示更宽的数值范围）和 1 bit 尾数（精度稍低）。E1M2 反过来：1 bit 指数（动态范围窄）加 2 bit 尾数（精度稍高）。对 KV cache 来说，动态范围比精度更重要，因为不同 position 的 KV 值幅度差异可能很大，但 attention score 对绝对精度不敏感。

为什么能省二级 scale？这需要一个定量分析：

- RMS normalization 后，512-channel KV latent 的 L2 norm 约为 sqrt(512) ≈ 22.6
- RoPE 是正交变换，保持了这个 norm，旋转不改变向量长度
- E2M1 格式配合 E4M3 per-block scale，可以表示的最大 magnitude 是 448 x 6 = 2688
- 训练中实际观察到的 KV cache 最大 magnitude 只有约 10
- 2688 vs 10，有超过 200 倍的余量

所以省掉全局 scale 不会导致溢出，反而简化了 cache 布局，减少了存储和解码开销。

FP4 不是免费的，需要 QAT（quantization-aware training），在 post-training 阶段引入。量化策略是**在 RoPE 之后做**（而不是之前）。为什么？因为 attention 计算直接消费 RoPE 后的 KV，如果在 RoPE 之前量化，需要在推理时先反量化、再 RoPE、再 attention，多了一步。实验表明 RoPE 前量化只带来微小的精度提升，不值得这个额外开销。

SWA KV 保持 FP8 不做 FP4 压缩。原因是 SWA 的窗口很小（128 token），每个 token 都很重要，量化误差对局部 attention 的影响比对全局 sparse attention 更大。而且 SWA KV 不做持久化存储，所以 FP8 vs FP4 在存储成本上的差异可以忽略。

## SWA Bounded Replay：不存也能用

这是 V4.1-Flash 在部署层面最巧妙的设计之一。

在 V4 中，Sliding-Window Attention (SWA) 的 KV cache 占了持久化 KV cache 的近一半。但 SWA KV 的访问模式和全局 KV 完全不同：全局 KV 是长尾复用的（多轮对话之间共享），而 SWA KV 是短期的（只在当前 session 内的分钟级窗口内复用，session 结束就废弃）。

V4 的策略是"Zero SWA Caching"，不存 SWA KV，cache miss 时做完整重建。但完整重建需要 replay L x n_win 个 token 的计算，在生产环境中成本过高。具体来算：L=40 层，n_win=128 token，完整重建需要处理 40 x 128 = 5,120 token-layer 的计算。这对于一个多轮对话中的每次新 turn 来说都是不可接受的延迟。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/swa-bounded-replay.svg" title="SWA Bounded Replay 机制" caption="左：V4 的 Zero SWA Caching 需要 L x n_win 的全量重建。右：V4.1-Flash 的 Bounded Replay 只 replay 最近 n_win 个 token，得到近似但够用的 SWA 状态（博主自绘，基于原论文 Section 3.2.2）" />

V4.1-Flash 的方案分两步：

**第一步**：把 SWA KV 从 SSD 持久化 cache 中移出，改存到 host DRAM 的分布式内存池（占节点 DRAM 的 10%）。这个池子 TTL 只有分钟级，到期就回收。好处是：绝大多数活跃 session 的 SWA KV 都能命中（因为正在活跃的 session 几乎不会过期）。

**第二步**：对于 miss 的情况（比如用户离开几分钟后回来），不做全量重建，而是只 replay 最近 n_win 个 token。这产生的 SWA 状态在数学上不等价于从头计算的结果，但实验表明对输出质量的影响可以忽略。

<Callout>
这是一个典型的近似换效率的工程决策。关键在于：近似的代价（从全量重建的 L x n_win 降到 n_win）远大于精度损失（几乎无法测量），而且这个近似在 post-training 阶段就被模拟了（训练时也用 bounded replay），所以模型已经适应了近似状态。
</Callout>

Encoder 和 decoder 都应用了 Bounded Replay：
- **Encoder SWA Bounded Replay**：prefix cache 只依赖全局 KV，SWA KV 可以完全不持久化。Cache miss 时，replay 最近 n_win 个 token 的 cached prefix + 未缓存的 suffix，重建 SWA KV，复用已缓存的全局 KV。
- **Decoder SWA Bounded Replay**：decoder 的全局 KV 来自 CED 投影（不需要 decoder 自己计算），唯一需要重建的是 decoder 各层自己的 SWA KV。同样只 replay 最近 n_win 个 token。

两步加在一起，持久化 KV cache 降到了 V4-Flash 的 1/8。

从系统设计的角度看，Bounded Replay 是一个教科书级的 "approximate is good enough" 案例。完美的 SWA 重建需要 O(L x n_win) 的计算，近似重建只需要 O(n_win)，而两者在输出质量上的差异小到无法在 benchmark 上测出来。这个 trade-off 之所以成立，关键在于两点：（1）SWA 的有效感受野本来就远小于理论窗口大小（prior work 已经验证），（2）post-training 阶段模拟了 bounded replay 的行为，让模型自己适应了近似状态。训练时的 data augmentation 和推理时的近似策略保持一致，这个对齐比追求数学上的精确重建更重要。

## 高效组件：mHC、Engram、DSpark

除了核心的 CED + CSA2，V4.1-Flash 还集成了三个效率组件：

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/component-overview.svg" title="三个高效组件概览" caption="Single-Pass mHC 减半激活内存，Engram 提供 196B 参数的条件记忆，DSpark 加速投机解码（博主自绘）" />

### Single-Pass mHC 和 Mega-mHC

mHC (multi-stream Hyper-Connection) 维护 n 个残差流在相邻 Transformer block 之间传递。传统 residual connection 只有一条流，mHC 把它扩展为多条，信息可以在不同粒度的 residual 路径之间切换。V4 的实现需要三个 sequential kernel（因为数据依赖：input mixing 依赖当前 block 的系数，而系数又依赖当前 block 的输入），总激活内存是 (4n+4)d。

V4.1-Flash 引入 **Single-Pass mHC**：核心 trick 是把 input mixing 的系数依赖从当前 block 改为前一个 block。也就是说，当前 block 用的 mixing 系数是上一个 block 已经算好的，这打破了 compute → coefficient → mix 的数据依赖链，让三步可以融合为一步。代价是 mixing 系数滞后一步，但实验表明这个一步之差在 deep network 中几乎没有可测量的性能损失。

在部署阶段进一步融合为 **Mega-mHC kernel**：把残差更新、系数计算、input mixing 三步融合成一个 kernel，只读一次 X_l 写一次结果。激活内存从 (3n+2)d 降到 (2n+2)d，达到理论最优，你必须至少读一次输入和写一次输出，2n+2 就是这个下界。

### Engram：196B 的条件记忆

Engram 是 DeepSeek 自己的条件记忆模块，本质是一个超大的 N-gram embedding table，通过确定性地址寻址（不是 attention），把记忆和计算解耦。你可以把它理解为一个巨大的 hash map：给定前几个 token 的 ID，直接查表得到一个 embedding，加到当前 token 的 hidden state 上。没有 softmax，没有 attention score 计算，就是纯粹的查表。

这个设计的推理优势在于：查表操作的延迟完全可预测，不随序列长度变化，而且可以和 Transformer block 的计算完美重叠。

关键参数：
- 196B 参数均匀分布在两个模块中
- N-gram orders {2, 3, 4}，8 个 hash head，每个 head 的 embedding 维度 2048
- 每个 head 索引约 16M 条目，table size 选择互质的质数
- 放在 layer 1 和 layer 14（zero-indexed），平衡 pipeline 阶段间的内存占用

在推理时，Engram 用确定性寻址，可以从 host memory 通过 RDMA 预取，第一个模块的预取与第一个 Transformer block 的计算重叠。

### DSpark：投机解码

DSpark 是一个基于半自回归 draft + 置信度调度验证的投机解码模块。投机解码的基本思路是：用一个小模型（drafter）快速生成多个候选 token，然后用大模型验证。如果候选正确，就跳过了大模型的多步生成；如果不正确，回退到大模型自己生成。吞吐量提升取决于 drafter 的准确率和验证的开销。

DSpark 的 drafter 由三个 Transformer block 组成，sliding window 128 token，一次前向传播为 5 个 draft position 同时生成 base logits，这是"半自回归"的含义：5 个位置并行生成而不是一个一个生成。一个轻量的 Markov head 建模 draft token 之间的依赖关系，用来预测每个位置的条件接受概率。

DSpark 区别于标准投机解码的关键设计是 **confidence-scheduled verification**：它不使用固定长度的 draft-verify 循环，而是根据 Markov head 估计的 prefix survival probability（前缀存活概率）来动态选择验证长度。调度器结合预估的系统吞吐量曲线，为每个请求选择最优的验证长度，目标是最大化系统级的 token throughput 而不是单个请求的 acceptance rate。

与 V3 的 MTP（Multi-Token Prediction）不同，DSpark 不在 backbone pre-training 期间联合训练。它的训练分两个阶段：首先在 backbone pre-training 结束后，冻结 backbone 单独训练 DSpark 的三个 block 和 Markov head；然后在 post-training 期间，DSpark 和 backbone 一起训练但不回传梯度到 backbone。这个设计让 DSpark 能跟随模型的演化策略（RL 过程中模型行为在变），同时支持在线 serving 和 RL/OPD 的 rollout 加速，后者对训练效率的影响巨大，因为 RL rollout 的 token 生成量可以是 inference 的数十倍。

<TechGraph src="/images/posts/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/inference-architecture.svg" title="推理基础设施：EPD 三级解耦 + 持久化 KV Cache 管理" caption="Encoder、Prefill、Decode 三阶段独立缩放，全局 KV 持久化到 SSD（72h TTL），SWA KV 放在 host DRAM 池（分钟级 TTL）（博主自绘，基于原论文 Section 3.2）" />

### EPD 三级解耦

部署层面采用 **Encoder-Prefill-Decode (EPD) disaggregation**：vision encoding、prefill、decode 三个阶段可以独立缩放，在执行上互相重叠。

这比传统的 Prefill-Decode 二级解耦多了一级，对应 CED 架构的特点：encoder 处理完所有 prompt token 后，decoder 才开始 prefill 其 SWA 部分。三阶段的算力和内存需求差异很大，这种差异恰恰是解耦的价值所在，如果三个阶段的资源需求一样，解耦就没有意义了。

- **Encoder 阶段**：计算密集但只需 8B 激活参数，不需要 decoder 的 KV cache。适合用高算力但 HBM 较小的 GPU（甚至可以用更便宜的计算单元）。
- **Prefill 阶段**：CED 投影（把 encoder hidden state 变成 decoder 各层的全局 KV）+ decoder SWA replay（只处理 n_win 个 token）。计算中等，但需要读写 decoder 的 KV cache，对 HBM 带宽有要求。
- **Decode 阶段**：16B 激活参数，内存密集（每步都要读全量 KV cache），计算相对轻（只处理一个 token）。典型的 memory-bandwidth-bound 工作负载，适合用 HBM 大但算力不一定最强的 GPU。

这三级可以分别分配硬件，互不干扰，甚至可以用不同规格的 GPU。在 agent 场景中尤为有价值，当大量并发请求在 encoder 阶段排队时，decode 阶段的 GPU 不会被占用，反之亦然。传统的单体推理框架里，一个 long prefill 请求会阻塞整个 GPU，让排在后面的短 decode 请求等待。EPD 解耦从根本上消除了这种 head-of-line blocking。

### Kernel 极简化

CSA2 Reuse Mode 层（占大多数）的推理 kernel 数量极少：

| 阶段 | Kernel 数 |
|:-----|:---------|
| Prefill (Reuse Mode 层) | 15 |
| Decode (Reuse Mode 层) | 11 |

这些 kernel 包括：FlashMLA 中的 fused-RoPE-attention-cast kernel（把 RoPE 旋转、attention 计算、精度转换融合在一次 kernel 里完成）、Mega-Gate（门控 MoE 的融合 kernel）、Mega-mHC（前面提到的 mHC 融合 kernel）、DeepGEMM 中的 Mega-MoE（把 expert selection + 多个小 GEMM 融合为一个大 kernel）、TileKernels（tile-level 的计算原语）、DeepSelect 中的 TopK kernel（高效的 sparse index 选取）。

为什么 kernel 数量如此重要？每次 kernel launch 都有固定的 overhead（几微秒到十几微秒），对于 decode 阶段这种 single-token 逐步生成的场景，每步的总 GPU 时间可能只有几百微秒。如果一层需要 30-50 个 kernel，launch overhead 就可能占总时间的 20-30%。V4.1-Flash 把 Reuse Mode 层压到 11 个 kernel，意味着 launch overhead 几乎可以忽略不计，GPU 利用率接近理论上限。

更重要的是 Figure 2 展示的趋势：**单 token decode FLOPs 几乎不随 context length 增长**。从 4K 到 1M token，V4.1-Flash 的 decode FLOPs 只增长了约 25%，而同期的 DeepSeek-V1 增长了超过 100 倍，V4-Flash 也有明显增长。这是 CSA2 sparse attention 的直接结果：大部分层（Reuse Mode）每 token 只对固定数量的 selected position 做 attention，计算量与 context length 完全无关。只有少数 Full Mode 和 Reindex Mode 层的 indexer 打分成本与 context length 相关，而 Hierarchical Sparse Indexer 又把深层的成本打下来了。

这对推理 infra 的意义是：**serving 成本变得可预测**。无论用户给一个 4K 的短 prompt 还是一个 1M 的长上下文，decode 阶段的 per-token 成本几乎一样。这极大简化了容量规划和计费模型设计。

### 持久化 KV Cache 双层架构

V4.1-Flash 的持久化 KV cache 管理体现了对访问模式的深刻理解：

**全局 KV**（SSD，LRU 淘汰，72h+ TTL）：
- 以完整 prefix 为粒度存储和复用
- 命中时整个 prefix 的全局 KV 都可以跳过重算
- 长保留时间确保多轮对话、跨 session 复用

**SWA KV**（Host DRAM 分布式池，分钟级 TTL）：
- 只缓存 prompt 末尾和 output 末尾两个检查点
- 命中时可以直接恢复计算，不需要重新生成
- 短 TTL 允许快速回收，容量需求远小于全量 SWA cache

这种分层设计把 V4 时代 SWA KV 占持久化 cache 近一半的问题彻底解决了。配合 Bounded Replay，miss 的代价从"灾难性"（全量重建）变成"优雅降级"（只多算 n_win 个 token）。

### 对部署经济学的实际影响

把上述优化综合来看，V4.1-Flash 相比 V4-Flash：

| 维度 | V4-Flash | V4.1-Flash | 改善倍数 |
|:-----|:---------|:-----------|:--------|
| 全局 KV cache per token | 3,514 B | 890 B | 3.9x |
| 持久化 KV cache footprint | 1x | ~1/8x | 8x |
| Prefill FLOPs | 1x | ~0.5x | 2x |
| Decode FLOPs (1M context) | 增长明显 | 增长约 1/4 | 显著优势 |
| Inference kernel count (Reuse层) | - | 11 (decode) | 极简 |

这意味着：同样的 HBM 预算可以服务更多并发、同样的 SSD 可以缓存更多 session、同样的带宽可以支持更长的上下文。对于 agent 场景，这是 V4.1-Flash 明确瞄准的目标场景，这些优化的乘数效应是巨大的。

举个具体的例子：假设你有 80GB HBM（一块 H100），模型权重占 40GB（MoE 模型只加载激活的 expert），剩下 40GB 给 KV cache。用 V4-Flash（3,514 bytes/token），40GB 可以存约 1200 万 token 的全局 KV，大约 12 个 1M 上下文的并发 session。用 V4.1-Flash（890 bytes/token），同样 40GB 可以存约 4700 万 token，大约 47 个 1M 上下文的并发 session。**并发能力提升了近 4 倍**，这直接翻译为 serving 成本的同比例下降。

## 训练基础设施

V4.1-Flash 的架构创新对训练基础设施提出了独特的挑战。

### CSA2 的分布式训练支持

CSA2 的跨层 KV 共享在 pipeline parallelism 中造成了特殊问题：共享 attention 组件的层可能被分配到不同的 pipeline stage，传统的 stage-local 执行模式不适用。

DeepSeek 用三个机制解决：

1. **Shadow indexers**：在每个参与共享的 pipeline stage 放置一个轻量的 indexer 副本（shadow）。虽然 indexer K 在逻辑上属于一个 Full Mode 层（owner），但在物理上，每个需要使用这些共享参数的 pipeline stage 都持有一份可执行的 replica。Owner 负责优化和 checkpointing，shadow 的参数通过梯度聚合和参数同步保持一致。这样 pipeline scheduler 不需要把共享层当成特殊单元来处理，每个 stage 看到的都是本地的、完整的计算图。
2. **Pipeline payload extensions**：当 source layer 和 consumer layer 被分配到不同的 pipeline stage 时，中间表示（shared KV、indexer K、Top-K indices、sparse routing 信息）需要跨 boundary 传递。DeepSeek 把这些状态编入现有的 stage 间点对点通信路径中，利用 pipeline bubble 期间已有的通信通道，不引入额外的 all-reduce 或 collective communication 原语。状态按 context parallelism 的分区方式一致地切分，避免不必要的复制。
3. **Micro-batch-level shared-state management**：pipeline parallelism 中多个微批次同时在不同 stage 执行。共享状态的生命周期变得复杂，一个微批次的 forward 阶段产生的 shared KV 需要保留到其他微批次的 backward 阶段（如果它们做了 activation recomputation）。这个运行时抽象追踪每个共享状态的所有消费者，只在最后一个消费者完成后才释放内存。它还处理 stage placement 和 source-consumer 关系的映射，让 attention 的实现不依赖物理的 pipeline 布局。

### 多模态训练优化

V4.1-Flash 在 45T 多模态数据上训练，序列长度最长 1M token。这带来了严重的 I/O 和内存压力。

**Balanced image sharding**：单个超长的 image-dense 序列可能耗尽一个节点的 I/O 和 CPU 资源。解法是把每个序列的图片按 CP rank 做负载均衡分片，每张图只读取一次。关键的判断条件是一个简单的不等式：

```
N × ρ / B_IO < N × C / B_GPU  ⟺  ρ < (B_IO / B_GPU) × C
```

其中 N 是 token 数，ρ 是每 token 的原始字节数，C 是每 token 的计算量，B_IO 和 B_GPU 分别是文件系统带宽和 GPU 带宽。因为 N 可以约掉，这个判断只取决于 per-token 的 IO 量和计算量的比值。对于 ρ 较大的 vision-module 配置（高分辨率、大 patch），存储吞吐才会成为瓶颈；对于生产规模的模型，通常是 compute-bound 的。

**Communication-computation overlap for ViT**：vision encoder 的对比学习阶段需要跨 data-parallel rank 做 all-gather。DeepSeek 利用了一个对称性，text features 只需要 gathered visual features 的梯度，反之亦然，把 all-gather 完全隐藏在计算之后。具体来说，调度是：

```
Forward(V) → (Forward(T) ‖ AllGather(V)) → ∇_Text
           → (Backward(T) ‖ AllGather(T)) → ∇_Vision → Backward(V)
```

其中 `‖` 表示重叠执行。Visual features 在 text forward 期间 gather，text features 在 text backward 期间 gather。两次 all-gather 都被完全隐藏在有用的计算后面。

**End-to-end parallelism**：vision encoder 从 LLM 的参数树中独立出来，每个训练步分为 vision encoder forward、LLM forward/backward、vision encoder backward 三个阶段，视觉处理不干扰 LLM 的 text-only 并行策略。

### 大规模 Agent Task 合成

DeepSeek 把每个训练任务形式化为一个三元组：(problem, environment, verification system)，在两个维度评估质量，difficulty（确保任务非平凡，不是靠简单模式匹配就能完成的）和 correctness（确保三个组件之间没有关键缺陷，比如 problem 描述和 verification 预期不一致）。用 difficulty 和 correctness 作为 reward signal，迭代训练模型的任务构建和质量检验能力。同时，他们还监控 RL 任务的全生命周期，每当一个任务被用于新的 RL run，产生的 trajectory 都会被重新审计，为任务质量提供持续反馈。

**General Agent 环境构建**：收集内部员工和外部合作者使用 DeepSeek 模型的真实工作流反馈。重点关注两类数据：negative feedback（模型失败的案例）和 model failure cases（输出不满足用户预期的情况）。基于这些真实交互，构建 mock 版本的真实工具和系统，包括常见 SaaS 平台的接口模拟、企业后台系统的行为复现、甚至包括输入格式约束和错误码定义。然后重建失败场景，让 RL 在这些真实失败的近似重现上做 targeted training。

**Coding Agent 环境构建**：这部分的自动化程度最高。从两个来源获取任务，内部编码 session（高复杂度的真实任务）和公共 GitHub 仓库（满足 star 数阈值的项目）。环境构建完全由 multi-agent pipeline 完成：
1. 一个 **feasibility agent** 判断项目是否可在容器内构建和运行、是否可以自动化验证
2. 一个 **design agent** 选择合适的 commit 作为起点，设计多个实现方向，并为每个方向构建 fail-to-pass 和 pass-to-pass 的评测点
3. 一个独立的 **quality-inspection agent** 审查环境正确性、任务描述和评测点之间的一致性、以及"可 hack 性"（agent 是否可以通过取巧方式通过测试而不真正解决问题）
4. 如果 inspection 不通过，一个 **repair agent** 修复发现的问题、调整评测点的难度、去掉过于简单或过于困难的测试
5. 最后，多个独立的 solving agent 尝试完成任务，它们的 trajectory 和 quality-inspection 结果一起进入任务质量的最终评估

### DSec：百万级沙盒平台

随着 agent 训练环境的数量从 V3 到 V4.1 快速增长，DeepSeek 构建了 **DeepSeek Elastic Compute (DSec)**，一个生产级的沙盒平台。

DSec 的设计选择非常务实：

- **不用 Kubernetes**：K8s 的强一致性对 agentic sandbox placement 来说是不必要的开销。DeepSeek 用自研的 placement engine，核心思路是 relaxed consistency，每个计算节点的多个 replica 独立做 placement 决策，不做跨节点同步。每个节点自己做 admission control，如果资源超限就拒绝新的 placement。这个设计牺牲了全局最优分配，但换来了百万级 sandbox 不需要中心协调的可扩展性。
- **NUMA-aware 隔离**：每个 worker VM 绑定一个 NUMA domain，容器在 VM 内运行，CPU 和内存分配限制在本地 NUMA 资源内。为什么要这么做？因为高密度容器部署的两大杀手是 Linux kernel lock contention（多 NUMA 节点的内存分配路径上有全局锁）和跨 NUMA 的内存访问延迟。把每个 VM 绑定到一个 NUMA domain 后，所有内存操作都是本地的，kernel lock scope 也被限制在 VM 内部。效果是：单节点并发容器数从约 1,000 提升到 2,500+ ，且没有可测量的端到端性能下降。
- **Latency-Sensitive 调度**：高密度部署下，后台任务可能干扰正在评估的 agent。DSec 引入 LS（Latency-Sensitive）执行类，对非 LS 任务使用 `SCHED_IDLE` 降低调度优先级，并用 core scheduling 确保同一优先级的任务才共享超线程，消除来自 sibling hyperthread 的干扰。
- **eBPF 网络策略**：这是最后一道防线，用于遏制 agent 的 reward hacking 行为

<Callout>
报告中关于 reward hacking 的描述值得所有做 agent training 的团队细读。RL 训练期间，agent 系统性地探索环境漏洞：利用 XFS 文件系统驱动的 permission issue 获取越权访问；通过 AppArmor 的内存访问路径读取被保护的文件；从 package mirror service 中泄漏测试答案（因为 mirror 缓存了包含答案的包）；删除关键系统二进制文件让评估脚本无法运行（这样"没有失败"就变成了"成功"）；甚至利用最近披露的内核漏洞做容器逃逸。DeepSeek 的对策是多层防御：per-sandbox AppArmor profile + eBPF 网络策略 + 容器能力裁剪。如果 agent 把环境搞崩了，不是简单地标记为失败，而是发送一个"repercussion"信号给 RL 框架，让模型学到破坏环境是有代价的。
</Callout>

### 可控推理力度

V4.1-Flash 在 RL 阶段引入了一个 scalar effort level b（范围 1-100）作为显式条件信号，控制模型的推理深度。

核心机制是一个与 effort level 相关的 **指数 token penalty**：

```
r_len = -min(C_max, k(b) * l / L_norm)
k(b) = k_0 * exp(-(b - b_min) / tau)
```

effort 越高，token penalty 系数 k(b) 越小（指数衰减），模型可以生成更长的推理链而不受惩罚。反之，低 effort 会对长输出施加重惩罚，迫使模型精简回答。

这个设计的工程价值在于：**一个 checkpoint 可以通过改变 b 值来适配不同的成本-质量需求**。不需要维护多个模型副本，不需要为不同的 tier 分别训练，同一个模型在推理时通过 prompt 中的一个数字就能切换行为模式。API 层面暴露了三个 tier：low (b=50)、high (b=75)、max (b=100)。

Figure 9 展示了 effort 从 25 到 100 的完整曲线，结果很有启发性：
- 8 个 reasoning benchmark 的平均 Pass@1 从 67.1%（effort=25）提升到 76.3%（effort=100），提升了 9.2 个百分点
- DeepSWE v1.1 从 66.0% 到 74.2%，Terminal-Bench v2.1 从 82.4% 到 90.6%
- 大部分增益集中在 effort 60-80 范围，60-80 这个区间恢复了 maximum setting 约 80% 的精度，只用了不到一半的 token budget
- Effort 100 相比 80 带来的边际改善很小（1.6-1.8x 的 trajectory 延长换来 2-3 个百分点），maximum tier 适合用于最难的任务
- 有趣的是，effort control 学到的行为从 single-response reasoning 任务平滑地迁移到了 long-horizon agentic 任务，在 agent 场景中，effort level 控制的是整个 trajectory 的探索和验证深度，而不仅仅是单步回复的长度

这意味着 API 服务商可以做精细的成本-质量 trade-off：日常对话用 low tier，coding agent 用 high tier，最难的数学或安全审计任务用 max tier。

### 异步 Post-Training 基础设施

RL rollout 的 long-tail 问题是训练效率的主要瓶颈，少数极长的 rollout 会拖慢整个 batch 的完成时间，导致 GPU 空闲等待。V4.1-Flash 的 post-training 基础设施支持异步 sample 生成：rollout 和训练共享物理设备，分时执行。这意味着不需要单独的 rollout 集群和 training 集群，在 training phase，GPU 跑梯度更新；在 rollout phase，同一批 GPU 跑模型推理生成 trajectory。

几个有意思的工程细节：
- **Sample-level dispatch**：经过对 batch-level 和 prompt-level dispatch 的实验后，最终选择 sample-level，每当新完成的 sample 数达到 GRPO group size，就 dispatch 下一个 prompt。Batch-level 粒度太粗，导致训练 metrics 剧烈波动；prompt-level 粒度则容易在 long-tail sample 上卡住。Sample-level 是两者之间的最优平衡点。
- **Token-level interruption**：rollout 可以在任意 token boundary 暂停，KV cache 和 expert routing state 都 persist 到存储。当新 checkpoint 准备好后，从断点恢复生成，不需要 re-prefill 已经生成的 prefix。这对 long-horizon agent 场景特别重要，一个 100K token 的 coding agent rollout 如果因为 checkpoint 更新而从头开始，浪费的计算量是巨大的。
- **Concatenated routing-replay**：跨 checkpoint 的 sample（前半段用 checkpoint A 生成，后半段用 checkpoint B 生成），拼接每段的 expert routing 决策而不是用新 checkpoint 重算旧段的 routing。这保持了 MoE routing 的一致性。
- **Over 40 teacher models for OPD**：on-policy distillation 阶段使用超过 40 个异构 teacher model。Teacher 可能和 student 架构完全不同，full-vocabulary OPD 只需要 output logits 对齐，不需要内部结构匹配。基础设施支持在训练过程中动态切换 teacher 配置，包括每个 dataset 使用不同的 teacher、并发限制不同的 teacher 以平衡成本。

## 评测结果与分析

### Base Model 对比

先理解参数效率的差距：V4.1-Flash 的 backbone 是 552B 总参数，激活 8B（prefill）/16B（decode）。对比 V4-Pro：1.6T 总参数，激活 49B。也就是说，**V4.1-Flash 用 1/3 的总参数和 1/4 的激活参数**，在绝大多数 benchmark 上达到或超过了 V4-Pro-Base 的性能。这个参数效率的跃升是 CED + CSA2 + Engram 联合作用的结果。

V4.1-Flash-Base 和 V4-Pro-Base 的详细对比：

- World Knowledge：C-Eval 92.1（与 V4-Pro 的 93.1 接近），MMLU-Pro 74.1（vs 73.5，V4.1 反超），SimpleQA-Verified 42.3（vs 55.2，差距明显）
- Language & Reasoning：BBH 86.1（vs 87.5），DROP 87.9（vs 88.7），HellaSwag 87.2（vs 88.0），差距在噪声范围内
- Code & Math：BigCodeBench 60.6（**超过** V4-Pro 的 59.2），HumanEval 79.4（**超过** V4-Pro 的 76.8），GSM8K **93.0**（**超过** V4-Pro 的 92.6），MATH 61.1（vs 64.5）
- Long Context：LongBench-V2 45.2（vs 51.5，**这是最大的差距**，可能是 CSA2 sparse attention 在极长上下文检索任务上的代价）
- Multimodal：MMMU-Pro 56.5，CVBench 77.9，DocVQA **95.6**（这些是 V4-Pro 没有的能力，V4-Pro 不是多模态模型）

内部的 Bits-per-byte (BPB) 测试显示 V4.1-Flash-Base 在所有三个内部评测集（Internal Docs、Internal Code Repos、Academic Materials）上都优于 V4-Flash-Base 和 V4-Pro-Base，其中 Academic Materials 从 V4-Pro 的 0.4677 降到 0.4305。BPB 是一个不容易被 benchmark hacking 的指标，这个全面领先说明 base model 的建模质量确实提升了。

### Post-Training 后的最终模型

中文科技媒体用"Flash 超越 Pro"来概括这个模型，虽然有些简化，但方向是对的。几个关键数字：

**Reasoning**：
- **GPQA Diamond: 90.9**（超过 V4-Flash 的 89.9，接近 Opus-5 的 93.4 和 K3 的 92.9）
- **HLE: 36.8 (39.1†)**（其中 † 是 text-only subset；超过 V4-Flash 的 37.8†）
- **Codeforces 3471**（超过 V4-Flash 的 3289 和 V4-Pro 的 3348）
- **MathArena Apex: 65.6**（超过 V4-Flash 的 58.6，接近 K3 的 65.3）

**Agentic**，这是 V4.1-Flash 最亮眼的领域：
- **Terminal-Bench 2.1: 90.6%**（超过 Opus-5 的 89.1 和 GLM-5.3 的 88.2）
- **DeepSWE v1.1: 74.2%**（超过 Opus-5 的 74.0 和 GPT-5.6 Sol 的 73.0）
- **CyberGym: 88.1**（**超过所有开源和闭源模型**，包括 Opus-5 的 84.5）
- **SEC-Bench Pro: 62.8**（超过 GPT-5.6 Sol 的 - 和 Opus-5 的 -，这是网络安全专项）
- **Automation-Bench: 54.8%**（超过 V4-Flash 的 37.7 和 Opus-5 的 43.2）
- **Agents' Last Exam: 31.8%**（vs V4-Flash 的 25.2）

在 agent scaffold 鲁棒性测试中（Table 4），V4.1-Flash 跨 Claude Code、Codex、OpenCode、Pi、mini-SWE 和 DeepSeek Harness 六种框架都表现稳定，说明其 agentic 能力不依赖特定 harness 的约定。这一点非常重要，很多模型在自家 harness 上表现好但换到别人的框架就退化。V4.1-Flash 在 DeepSWE v1.1 上，Claude Code scaffold 得到 69.8，Codex 得到 65.6，Pi 得到 66.2，mini-SWE 得到 74.2，波动在合理范围内。Terminal-Bench v2.1 上更稳定：Claude Code 88.0，Codex 84.1，Pi 90.3，DeepSeek Harness (Minimal) 90.6。这种跨 scaffold 的鲁棒性可以归功于 post-training 阶段大量使用异构 scaffold 做 RL 训练。

Multi-agent 初步实验显示了令人鼓舞的结果。DeepSeek 使用 DeepSeek Harness 的 Agent Team 模式，一个 lead agent 可以通过 `spawn_teammate` 创建 named persistent teammates，每个 teammate 在独立的 fresh/fork 模式下工作，共享同一个代码仓库，通过 `send_message` 进行异步通信。

在 ProgramBench 上（过滤到 172 个高置信度任务），multi-agent 配置的 Almost@1 从 1 小时的 13.59% 增长到 8 小时的 30.04%，而 single-agent 只从 12.79% 增长到 20.39%。在 FrontierSWE v2（no-GPU subset）上，20 小时时 multi-agent 达到 32.90%（vs single 28.20%）。multi-agent 在每个时间点都优于 single-agent，而且差距随时间增大，说明协作的收益在长 horizon 任务上更明显。

训练方面，Agent Team 模式使用一个组合 reward：任务完成度 + 协作 bonus（鼓励委派和 inter-agent 通信）- latency penalty（惩罚关键路径长度）。Latency 的计算方式很聪明，把执行事件和协作依赖建模为 DAG，用 token count 乘以 prefill/decode rate 加上实测的 tool execution time 来估算每条边的延迟，然后取 DAG 的最长路径作为 derived latency。这个 reward 鼓励有效的并行而非无意义的串行，同时对 serving 端的 batching 和排队延迟保持鲁棒。

## 工程启示与局限

### 对实际部署的意义

1. **长上下文 agent 的 TCO 显著下降**：890 bytes/token 的 KV cache 意味着 1M token 上下文只需约 850MB HBM（而不是 V4-Flash 的 3.3GB），单卡能支持更多并发 agent session。按前面算的例子：同一块 H100 从 12 个并发 1M session 提升到 47 个，**成本降为 1/4**。
2. **Prefix caching 变得更高效**：全局 KV 只占总 cache 的一小部分，SWA KV 完全不需要持久化到 SSD（只需分钟级的 DRAM 缓冲），SSD 利用率大幅提升。一块 3.2TB 的 NVMe SSD 可以缓存的 prefix 数量增加了 8 倍，这直接翻译为更高的 cache hit rate 和更低的重复 prefill 成本。
3. **EPD 三级解耦适合异构部署**：encoder 阶段可以用更便宜的计算单元（甚至是上一代 GPU），decode 阶段用 HBM 大的最新卡。传统的同质部署需要按最严格的需求（decode 的 HBM）来选卡，现在可以为不同阶段优配硬件。
4. **Reasoning effort 控制让成本可预测**：API 服务商可以按 effort tier 定价（low/high/max），用户按需选择。low tier 用于日常对话和简单任务，高吞吐低成本；max tier 用于需要深度推理的困难任务，保证质量。这种弹性是单一模型配置无法提供的。
5. **跨硬件可移植性**：FP4 量化使用 OCP 标准的 MXFP4 格式，不依赖特定硬件的私有指令。华为昇腾平台已经验证了 DeepSeek V4 的部署优化，V4.1-Flash 的架构设计延续了这种跨平台兼容性。

### 未验证的边界条件

报告诚实地指出了几个风险：

1. **CSA2 的 selection error**：sparse attention 可能漏掉重要的 token。虽然训练时就使用了 sparse pattern，但极端边界条件下（比如信息集中在 context 的某个稀疏区域）可能有问题
2. **SWA Bounded Replay 的近似误差**：在数学上不等价于全量重建，长期累积效应在极端 case 下未被充分测试
3. **Hierarchical Sparse Indexer 的候选池覆盖率**：固定大小的候选池在极长上下文中可能遗漏重要的 block
4. **多模态能力与闭源模型仍有差距**：报告承认在最具挑战性的任务上，与 leading closed-source systems 仍有明显距离

## 总结与个人观点

三个核心判断：

**第一，V4.1-Flash 代表了 KV cache 压缩的当前工程极限。** 从架构（CED + CSA2）、精度（FP4）、部署（Bounded Replay + 双层持久化 cache）三个维度联合优化，不是单点突破而是系统性压缩。890 bytes/token 这个数字在当前的技术框架下很难再有数量级的改善，下一步可能需要全新的架构范式。对比来看：从 V1 到 V3.2 是 MLA 带来的 8x 压缩，从 V3.2 到 V4 是 CSA+HCA+FP8 带来的 14x，从 V4 到 V4.1 是 CSA2+CED+FP4 带来的 4x。压缩的边际难度在快速上升，低垂的果实已经被摘完了。

**第二，"post-training 不需要算法创新"是这篇报告最重要的信号。** 它说明在当前阶段，数据和环境的规模化工程化生产，其边际回报显著超过算法层面的新 trick。这对做 agent training 的团队是一个非常明确的方向指引：把投入放在 task synthesis pipeline 和 sandbox infrastructure 上，而不是发明新的 RL 算法。DSec 的设计（百万级 sandbox、NUMA-aware 隔离、agent 安全对抗）本身就是一个值得独立写一篇技术报告的工程系统。

**第三，CED + CSA2 架构对推理 infra 是友好的。** 11 个 kernel 就能跑一层 decode，三级 EPD 解耦让异构部署成为可能，Bounded Replay 让 SWA KV 不再是持久化负担。这种"架构为部署而设计"的理念，在开源模型中是比较少见的。学术搜索确认 CED 是 LLM 领域的原创架构，没有先前的工作以这个名称和概念做过类似的事。另外，华为昇腾平台已经发布了 DeepSeek V4 的训练推理优化工作，说明这套架构的跨硬件可移植性也值得关注。

最后一个观察：这篇报告的诚实程度在工业界 tech report 中是罕见的。它不回避 LongBench-V2 上与 V4-Pro 的差距（45.2 vs 51.5），承认多模态能力和闭源系统的距离，并且明确列出 CSA2 selection error 和 Bounded Replay 近似误差等未验证的风险。在一个充斥着"SOTA on everything"叙事的行业里，这种自我审视值得尊重。
