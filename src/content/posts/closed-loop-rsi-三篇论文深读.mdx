给一个 Agent 测试集、评分器和训练工具，让它反复尝试，直到分数提高。这是一个清楚、可执行的改进过程。

但如果只说一句“成为一个更好的工程师”，情况就变了。它先补算法，还是学会读懂陌生代码？一次修改碰巧通过了测试，应该记住代码写法，还是排查过程？总结出“提交前认真检查”以后，下次任务里又怎样保证这条经验真的改变行为？

这三个问题，也存在于人的学习里：<strong>方向怎样变成行动，经历怎样变成经验，经验怎样变成稳定的做事方式。</strong>

把它们放回 Recursive Self-Improvement（RSI，递归自我改进）的讨论，可以看见一个常被默认的前提：学习任务和可靠反馈已经准备好了。我们不妨把这种只需搜索改进方法的设置称为“半环”，把能进一步承担目标拆解、经验判断与系统改造的方向称为“闭环”。这里的“半环”是帮助讨论的比喻，不是对所有 RSI 研究的统一分类。

2026 年 8 月底至 9 月初发布的 Aspire、S³Gym 和 HarnessDev，分别把这几种能力做成了可研究的评测对象。三篇来自有成员重叠的研究团队，彼此引用，也共享项目主页，并非三个独立团队的重复验证。

</Callout>

## 先把三个问题分开

设想一个要持续处理陌生代码库的工程 Agent。下面会一直用它串联三篇论文。这是教学场景，不是论文里实际运行的共同实验。

它昨天修复了一个故障，今天需要决定是否改变自己。这个决定至少涉及三层：

| 需要做出的决定 | 可能留下的产物 | 对应论文的重点 |
| --- | --- | --- |
| 下一步应该补哪种能力？ | 子目标、学习数据、更新方法、自建验证 | Aspire：宽泛方向能否被正确操作化 |
| 昨天的经历说明了什么？ | 带判断的历史、可复用规则、训练样本 | S³Gym：经历能否改善下一次决策 |
| 怎样让经验在以后持续生效？ | 工作流、工具策略、状态管理、完成检查 | HarnessDev：能否创建并改进可运行系统 |

三个问题互相影响，却可以分别失败。数据选错了，再稳定的训练程序也可能把模型带偏；经验判断对了，摘要仍可能丢掉执行所需的条件；规则写成代码了，也可能根本没有进入实际调用路径。

还有一个必须分清的角色：<strong>学习时可见的反馈，与研究者用来验收的评价。</strong>

外部评价不一定是完美的 Golden Verifier。它可能是程序规则，也可能是固定 rubric 下的模型评分。隐藏评价内容，是为了观察 Agent 能否自己找到方向；保留评价本身，则是为了让研究者判断它有没有进步。两者并不矛盾。

## Benchmark paper 到底在研究什么

普通任务评测通常固定 Agent，给它一批题，看完成率。自我改进的 benchmark 还要给它一段学习或开发过程，再检查<strong>这段过程留下了什么，以及这些改变是否改善后续行为</strong>。被测对象从一次回答，变成了“产生下一版 Agent 的过程”。

因此，阅读这类论文，要顺着一次实验走：研究者先交给 Agent 什么；允许它改变什么；学习途中提供什么反馈；何时冻结产物；最终用什么任务、什么标准验收。只看最终排行榜，会把学习能力、初始能力、工具支持和版本选择混在一起。

例如，系统 A 起点 80 分，学习后 81 分；系统 B 起点 30 分，学习后 45 分。A 的最终能力更强，B 在这次设置下的增益更大。这是教学数字，说明“最强的 Agent”与“最会从经历中改进的 Agent”并不是同一个排名。判断后者，还得比较学习预算、重复实验和是否损伤原有能力。

这三篇分别改变了实验的一个重心：Aspire 不替 Agent 指定具体学习任务；S³Gym 不直接向探索者提供程序算出的奖励，让它判断并复用经历；HarnessDev 不提供成熟求解系统，让模型自己搭建和演化。它们提供的是<strong>诊断能力的实验设置</strong>，不是三套已经解决问题的新算法。

能力分解也不等于完全隔离了因果。Aspire 的低分可能同时来自数据选择和训练失误；S³Gym 的摘要收益依赖探索、判断与压缩；HarnessDev 的结果包含执行模型与系统的配合。论文通过对照和轨迹把问题缩小，但不能只看一个总分就宣布某一环节是唯一原因。

## Aspire：把“变得更好”变成可检验的学习目标

### 交给 Agent 的，是目标的操作化

通常做后训练时，人已经决定要优化哪个 benchmark、任务长什么样、答案如何计分。Agent 可以找数据、训练、比较 checkpoint，但大部分搜索围绕“怎么提高这个指标”。

Aspire 把任务名称和评测细节藏起来，只给一个自然语言能力方向。Agent 必须自己决定：这个方向对应什么缺口，该找什么数据，用什么更新方法，又该怎样自测。

[查看原图](/images/posts/closed-loop-rsi-三篇论文深读/aspire-objective.png)

对工程 Agent 来说，“更擅长处理陌生仓库”可以被拆成“减少误判根因”“提高工具调用正确率”或“在不破坏旧行为的前提下修复问题”。这些方向需要的数据不同。刷大量短函数补全题，未必能改善跨文件诊断；自建验证只检查补丁能否编译，也可能漏掉行为退化。

因此，Aspire 所说的“自主目标”需要准确理解：<strong>宏观能力方向仍由人给出，Agent 自主选择的是可训练、可验证的中间目标。</strong>它没有测试系统能否凭空决定自己最终应该追求什么。

研究环境也主动承担了基础设施工作。Agent 通过统一工具选择数据、启动 SFT 或 GRPO、设置参数、做自测、分支和停止；控制器负责调度、资源限制和 checkpoint 验真。这样，训练是否会配置不再吞掉整个问题，目标选得对不对更容易被观察。[方法与边界见 Aspire §3](https://arxiv.org/html/2608.31111v1#S3)。

### 一次 Aspire 实验怎样开始，又提交什么

以权重演化为例，输入是一个初始模型、一个能力方向、可调用动作和预算。Agent 首先选择或构造学习数据，登记数据来源与用途，再选择训练方法、参数和父 checkpoint。训练完成还不等于候选有效：控制器先确认模型确实来自这条实验谱系、文件完整、更新真实发生，候选才可以进入评测。

Agent 可以在自己建立的验证集上反复检查，根据结果换数据、改训练方案、从旧 checkpoint 分支，或者停止。研究者最后验收的是提交的模型，而不是它写得多漂亮的学习计划。若改的是 harness，则交付物变成冻结后的提示、工作流、工具策略和验证逻辑；运行模型的权重保持不变。

论文用三组实验分别观察这件事，不能把它们的分数合成一个总成绩：

| 实验 | 具体改变与对照 |
| --- | --- |
| RQ1：明确任务变成宽泛目标 | 沿用 PostTrainBench 的任务评测，比较明确任务参考与模糊目标运行；官方结果并非严格的提示词单变量配对 |
| RQ2：自主改变权重 | 从指令微调后的 Qwen 模型出发，在 Aspire 隐藏能力任务上比较更新前后；另分 final-only 与 adaptive-feedback |
| RQ3：自主改变 harness | 固定 Qwen3.5-4B，与原始 Qwen-Agent 对照；创建一次后继系统，冻结后才测研究写作任务 |

RQ2 与 RQ3 使用的六个方向包括科学推理、人文社科、医学、数学、逻辑与可靠性及指令遵循、学术写作。评测条目由专家编写，按对应目标切片计分；能用确定规则评分的任务使用规则，开放回答则使用固定 rubric 下的 judge。它检验的是 Agent 自建学习信号能否对齐这些外部标准，而不是让 Agent 自己定义什么结果都算成功。[Aspire §3、§4.1，附录 A、C](https://arxiv.org/pdf/2608.31111)。

### 隐藏试题，不等于完全没有评分反馈

Aspire 的主要自主权重演化实验使用 520 个专家编写的评测条目，覆盖六类能力方向。Agent 看不到题目、答案、逐题反馈和评分过程。但它是否能在学习中看到总分，取决于协议。

| 协议 | 学习过程中能看到什么 | 最终结果回答什么 |
| --- | --- | --- |
| Final-only | 自建验证的结果；没有中途官方分数 | 没有官方分数指路时，自己选出的最终模型有没有变好 |
| Adaptive-feedback | 自建验证结果，以及有限次隐藏评测总分 | 稀疏总分能否帮助搜索、筛选和保留较好的候选 |

后者反复查询的是同一能力切片，因而带有自适应选择。即使题目从未公开，这个分数也已经参与版本选择。它不能直接当作完全未参与开发的新测试结果。

Final-only 的结果比较克制：Qwen3.5-4B 和 Qwen3.5-9B 各在六个目标上运行两次，共 24 次。每次最多使用 40 GPU-hours 训练，可以产生多个候选，但只提交一个最终 checkpoint。论文按“模型 × 目标”汇报两次的算术平均，记为 Avg@2；它表示两次最终成绩的平均值，不是两次中的最好成绩。

12 个模型—目标组合里，只有 Qwen3.5-9B 的科学与学术推理均分高于初始模型，从 45.33 到 48.00。按单次运行数看，则是 3/24 个最终 checkpoint 高于各自基线。<strong>1/12 和 3/24 使用不同分母，不能混写成同一种成功率。</strong>这两次科学任务运行虽然同得 48.00，具体答对的题也不完全相同；它支持同一评测切片上的正向结果，尚不足以说明稳定、广泛的能力增长。[Aspire §4.3、附录 C.3，PDF 第 9–10、21–22 页](https://arxiv.org/pdf/2608.31111)。

### 案例一：检查表满分了，学习目标却选偏了

<strong>论文轨迹：代理目标怎样选偏。</strong>Aspire 的 harness 实验给出的方向是改善学术与科学写作。GPT-5.6 Luna 从原有 Qwen-Agent 出发，自己设计验证，再决定怎样修改系统。下面按附录 D 整理关键步骤，未公开的提示内容不作补写。

| 过程 | Agent 实际做了什么 |
| --- | --- |
| 建立代理目标 | 用一个自建验证提示和八项检查表评价原系统，得到 7/8 |
| 选择修改 | 加入固定的五部分回答模板：研究问题、设计、分析、风险与局限 |
| 自己验收 | 原提示升到 8/8，另外两个结构相似的提示也得 8/8 |
| 停止搜索 | 大约 40 分钟后结束，冻结后继 harness |
| 外部验收 | 隐藏评测中，原始系统 task-macro 为 28.64，Luna 后继为 19.32；均为冻结系统三次执行的均值 |

表中的 task-macro 让每个评测条目具有相同权重，先按条目平均，再汇报冻结系统三次执行的均值；它与训练实验的 Avg@2 统计对象不同。

这条修改路径是：发现结构缺项，补齐模板，再通过自测。问题出在<strong>它把“回答结构完整”当成了“能更好完成各种研究请求”的代理目标</strong>。作者检查隐藏任务输出时发现，一些本来要求解释机制、公式、参数和工程细节的问题，被重写成了研究设计方案。回答更规整，却没有提供对方要的内容。

这就是“自我判断成功”与“方向真的正确”的分叉：自测只能证明修改符合自己选定的检查表；检查表本身是否覆盖真实需求，还没有得到证明。此处比较的是完整后继系统，轨迹支持模板过度专门化的解释，但没有隔离模板单项的因果效应。[Aspire §4.4、Table 2 与附录 D，PDF 第 13–14、23 页](https://arxiv.org/pdf/2608.31111)。

<strong>教学推演：怎样把目标拆成训练任务。</strong>回到接到“更可靠地修复陌生仓库”要求的工程 Agent。以下展示一种目标拆解方法，不是论文验证过的成功轨迹。

它先把失败样例按现象区分：没定位到根因、修改错误、没有验证就提交。假设轨迹显示第三类反复出现，它才提出一个中间目标：“识别补丁完成前还缺少哪些验证证据”。这个目标比“多学编程”具体，也能产生可训练样本：输入问题、补丁和执行记录，输出尚未排除的失败假设，以及应运行的检查。

如果走权重路径，可以把这些样本组织成 SFT 的输入与目标；如果走 harness 路径，可以把它变成提交前的检查流程。无论选择哪条路，都应另备未用于训练的样例，检查它是否能区分“相关测试通过”“旧结果被重复引用”“测试失败但总结声称成功”。最终再用未参与开发的仓库任务验收修复效果。

反过来，如果它把目标简化成“每份答复都写一句测试已通过”，就会重演 Luna 的问题：自建表格可以满分，能力未必增长。从宽泛目标到训练任务，真正需要保留的是<strong>失败证据 → 能力缺口 → 学习样本 → 验证标准</strong>这条对应关系。下一节的经验判断，正是为这条链提供可信原料。

### 一条上升曲线，也可能只是从损坏中恢复

Adaptive-feedback 的 30 个配置—目标组合中，28 个产出了被评测的 checkpoint，21 个产出了符合保留资格的 checkpoint，最后只有一个组合留下高于初始模型的候选。这个结果来自总分反馈参与的选择，没有额外确认集；不能把它升级为独立复现的泛化提升。

原文有一条很值得记住的数学任务轨迹：

| 比较对象 | 分数 |
| --- | ---: |
| 训练前的 Qwen3.5-4B | 17.86 |
| 第一个评测 checkpoint | 0.79 |
| 第二个评测 checkpoint | 1.75 |
| 第三个评测 checkpoint | 2.38 |

从第一个到第三个 checkpoint，增加了 1.59 分；相对训练前，却仍低了 15.48 分。如果图里只画训练后的三个点，故事会变成“持续自我改进”。补上初始模型这条线，读者看到的就是另一回事：训练先造成退化，后续搜索只恢复了一小部分。

论文还记录了一个具体故障：五个最终 checkpoint 使用数字标签形式的 MMLU 数据做 SFT，相应的 279 个评测输出全部变成单个数字。这个案例提示，学习数据的答案形式也可能破坏原有行为。不过它是轨迹观察，没有随机对照，不能仅凭共现证明退化只由这一因素导致。

Aspire 的回滚机制会拒绝未超过初始分数的候选。这让“保留下来的分数不下降”成立，但非负是筛选规则带来的保障，不表示每次更新都有效。对工程 Agent 来说，要同时保存三个参照物：最初系统、当前候选、实际保留版本。只比较相邻版本，容易把恢复误认成增长。

## S³Gym：经历怎样变成下一次能用的经验

即使学习方向对了，Agent 也可能积累了很多经历，却没有学到可复用的方法。S³Gym 把这段过程进一步拆成 Self-Testing、Self-Judging 和 Self-Improvement。

### Agent 自己打分，研究者另留一份账

S³Gym 使用七种文本游戏。它们的状态、动作和后果可由程序执行，适合观察连续决策，也能在后台计算可核对的结果。

一次交互里，Agent 先看当前状态和历史，再同时给出动作与自评分。<strong>这个自评分是对该动作即时奖励的估计，不是“我有多自信”。</strong>环境执行动作后，返回新状态和可见反馈；后台另行保存真实规则计算的奖励。

主要设置中，后台的逐步奖励和最终得分不会在探索阶段直接交给 Agent。因此，记忆中的分数来自它自己的判断，而研究者可以事后比较两份账：Agent 认为发生了什么，环境实际上给了什么结果。

探索环境相对宽松，评测环境更严格。下面逐项看这些变化怎样检验策略能否迁移。

“自己创造经历”在这里指 Agent 自己选择动作、探索策略，进而产生交互轨迹。游戏规则和环境由研究者提供，并非 Agent 自己发明整个世界。[S³Gym §4、Table 2](https://arxiv.org/html/2608.31100v1#S4)。

### 七种游戏分别给 Agent 出了什么题

文本游戏不是用来模拟完整现实，而是把“动作—状态变化—后果”压缩到可重复检查的环境中。七个任务各自暴露不同的信息缺口，不能把它们都理解成一般问答。

| 游戏 | Agent 每步要决定什么 | 探索到评测的变化 |
| --- | --- | --- |
| Chess | 根据历史状态推断隐藏移动规则，预测棋子坐标 | 棋子由 12 个增加到 22 个 |
| Minesweeper | 根据局部数字约束选择翻格、插旗或撤旗 | 从允许额外两条命到首次踩雷即结束 |
| Nullify | 选择当前索引对应的两个单元进行组合，最终消去所有单元 | 表达式构造步数从 3–7 增到 5–10 |
| Tetris | 为下一块选择落点列与旋转角度 | 棋盘从 10×10 缩到 8×8 |
| Snake | 选择下一步移动方向 | 碰撞从无效动作变成终止条件 |
| Plants-vs-Zombies | 根据资源、敌人位置和轮次安排植物 | 战场从 3×7 变成 5×6 |
| Trust Evolution | 根据交互历史选择合作或背叛 | 从偏向容易对手的采样变成均匀采样 |

来源：S³Gym Table 2 与附录 A。表格描述的是本文实验配置，不是这些游戏在其他实现中的通用规则。

一次实验先测不带跨局经验的起点；随后探索、保存或压缩经历，再按固定间隔去严格环境考试。考试使用独立种子，轨迹不回流到记忆或训练数据。这样，后续考试的变化才能被解释为探索所得经验的迁移，而不是记住了考题答案。

History 与 Summary 在同一模型—游戏组合下对照，保持探索种子、评测种子、交互预算和解码设置一致，主要改变跨局经验的表示方式。它们并不必然消耗同样多的 token：摘要还有额外压缩调用。主表覆盖七个结果完整的模型；辅助训练实验另用 Qwen3-8B，不能把它与商业模型的上下文结果直接当作同条件消融。

三个 Self 也不是三张互不相关的分数表。Self-Testing 主要体现在产生了什么探索轨迹；Self-Judging 可以拿自评分与后台奖励直接比较；Self-Improvement 则由后续严格评测检验。要进一步证明某种探索策略更好，还需要在同预算下替换探索策略做对照，不能仅从最终增益反推出探索质量。

### 三种记忆方式，三种不同的损失

论文比较了经验进入未来决策的三条路径。

| 路径 | 下一次决策会读什么 | 保留了什么，又可能丢掉什么 |
| --- | --- | --- |
| History ICL | 带自评分的原始交互记录 | 留住状态细节，但占用上下文，也夹杂无用信息 |
| Summary Memory | 模型总结的保留策略、避错规则、下一步方向 | 压缩历史，但可能删掉适用条件或保留错误判断 |
| Parameter Training | 用交互样本更新后的参数 | 不必每次重读历史，但噪音可能被写进模型行为 |

这里的摘要主要压缩跨 episode 的经验，当前 episode 的交互仍保留原始历史。不能把它理解成 Agent 当前连棋盘或动作记录都看不到。

### 案例二：一次背叛得了高分，应该记住“以后都背叛”吗

Trust Evolution 很适合把“经历”和“经验”区分开。Agent 每轮选择合作（collaborate）或背叛（cheat），对手在一局中使用稳定策略。规则给 Agent 的收益如下：

| Agent / 对手 | 对手合作 | 对手背叛 |
| --- | ---: | ---: |
| Agent 合作 | +2 | −1 |
| Agent 背叛 | +3 | 0 |

这些收益来自论文附录 A。当前动作更高的即时收益，并不自动意味着整局最好的策略，因为对手可能根据你的历史行动改变下一步行为。

<strong>论文片段：一次动作与作者的解释。</strong>原文 §6.3 的 GPT-5.5 案例记录了一次 `cheat` 动作和后台奖励 3.0。作者认为有效摘要把收益信息变成了带对手条件的决策规则。但片段没有给出完整对手轨迹和该步自评分，无法逐步核对它如何识别对手、形成摘要，再改变下一次动作。

<strong>教学推演：为什么经验必须保留对手条件。</strong>下面沿用论文收益规则，构造两局十轮对照。假设甲对手始终合作；乙对手第一轮合作，此后复制 Agent 上一轮动作。对手设定和下列成绩仅用于解释机制，不补作上面那条真实轨迹的后续。

第一轮，Agent 选择背叛，两种对手都合作，它都得到 +3。此时，把经历压缩成“背叛有利，所以以后都背叛”，会丢掉最重要的未知量：对手怎样回应。

第二轮才出现分叉。在甲面前继续背叛，仍得到 +3；在乙面前继续背叛，双方都背叛，收益变成 0。假设 Agent 因为上一次成功而再次自评 +3，那么第二局就出现“自评 +3、后台实际 0”的判断错误。后台分数在主实验探索时不可见，但它可以根据已知收益规则和可见交互历史重新推断这一后果。

| 固定策略的十轮结果 | 甲：始终合作 | 乙：复制上一轮动作 |
| --- | ---: | ---: |
| Agent 始终背叛 | 10×3 = 30 | 3 + 9×0 = 3 |
| Agent 始终合作 | 10×2 = 20 | 10×2 = 20 |

这个计算只比较两个固定策略，不声称找到了十轮博弈的最优策略。它足以说明：第一轮观察相同，适合长期保留的规则却必须等待更多证据。

于是，经验可以有三种不同质量：

- <strong>事件记录：</strong>上一轮我背叛，对手合作。它保存事实，没有给出适用范围。
- <strong>错误泛化：</strong>背叛总是更好。它把一次局部成功扩大成无条件策略。
- <strong>可执行的条件规则：</strong>记录对手对前序动作的反应；若出现报复性变化，重新比较连续几轮的结果；证据不足时继续区分对手类型，避免过早固定策略。

第三种规则不是一句更长的感想。它明确了要保留的状态、重新判断的触发条件和下一步操作。History ICL 保存两轮原始对话；Summary Memory 应保留这个条件结构；若把样本用于训练，则需要避免只挑第一轮高自评分动作，反复强化无条件背叛。

<strong>Self-Testing</strong>在这里负责产生能区分对手的经历，<strong>Self-Judging</strong>负责修正对动作后果的估计，<strong>Self-Improvement</strong>还要看整理出的规则在独立对手与严格配置中是否改善表现。把自评分改对，只完成了中间一步。

对应到工程 Agent，第一次“加一条断言后测试通过”，也不能直接总结成“所有故障都用这条断言解决”。可复用经验应该保留：什么改动发生后需要检查什么证据，哪些迹象说明检查不足，以及条件不满足时怎样继续排查。下一节会看到，连这些条件都可能在写入系统时被漏掉。[S³Gym §4.2、§6.3、附录 A.4，PDF 第 7–8、18、25 页](https://arxiv.org/pdf/2608.31100)。

### 摘要确实能帮助学习，但没有统一胜出的路径

主实验中，每条上下文学习轨迹有 30 次探索；每三次探索评测一次，每个检查点只运行三个严格模式 episode。论文同时记录沿途平均分、最高分与 AUC+。

AUC+ 可以理解为：把评测曲线高于初始分数的部分，沿探索进程累计起来。同样高的峰值，维持得越久，累计面积通常越大；但它只计算正面积，<strong>低于基线的损失不会被它扣除</strong>。所以仍要看完整曲线和最终表现。不同游戏量纲不同，原始 AUC+ 也不能跨游戏求一个有意义的总平均。

下面只摘录同一个模型在两个游戏中的对照，不用它排名所有任务：

| GPT-5.5 的 AUC+ | History ICL | Summary Memory |
| --- | ---: | ---: |
| Chess | 0.474 | 16.840 |
| Plants-vs-Zombies | 548.499 | 33.219 |

来源：S³Gym Table 4，PDF 第 12 页。这里的 Chess 是隐藏移动规则下的棋子位置预测，并非常规国际象棋对弈。AUC+ 的量纲是各游戏分数乘探索 episode；只比较同一行的两种方法。

摘要在前一行大幅增加正面积，在后一行却明显减少。作者的案例分析给出了一个有用解释：有些经验能被压缩成稳定的推理步骤，另一些决策则依赖精确的局部状态与时序。PvZ 中“先发展经济、及时防御”很合理，却不足以决定哪一条路线此刻需要防守、手里的资源够不够。

这仍是对结果和轨迹的解释，不是“删掉哪一句摘要就会损失多少分”的因果消融。更稳妥的工程结论是：记忆格式需要按任务验证，不能预设越短、越抽象就越好。[S³Gym §5.3、§6.3](https://arxiv.org/pdf/2608.31100)。

### 判断准确，也不自动产生有效策略

S³Gym 还单独测自评分质量，用两把尺子区分“认出了结果”与“估对了价值”：

- <strong>事件一致性（Agreement）</strong>：自评分和后台奖励是否同时大于零，或同时不大于零。假设自评 +3、实际 +1，这一步仍算一致；它只看有没有正收益。
- <strong>归一化平均绝对误差（NMAE）</strong>：先分别按游戏中的取值范围缩放自评分与奖励，再计算两者的平均绝对差，越小越好。它检查分值幅度是否匹配；上面的 +3 与 +1 是否对应大误差，还取决于各自的缩放范围。

事件一致性偏高，也可能只是因为大量动作没有奖励。因此还要看幅度误差，以及判断能否帮助后续决策。论文把两次评测之间的探索合成一个区段，比较该段判断质量与下一次评测增益。汇总区段的相关系数分别为 −0.010（事件一致性）和 −0.018（负 NMAE；取负号让数值越大表示判断越好），均接近零：判断较准的区段，未呈现稳定的后续增益优势。<strong>这是相关性观察，不能推出准确判断没有用。</strong>[S³Gym Tables 5–6，PDF 第 16–17 页](https://arxiv.org/pdf/2608.31100)。

参数训练也有正反两面。辅助实验使用 Qwen3-8B，评测时不提供历史或摘要。Trust Evolution 的最高分达到 30，19 个更新后检查点中有 18 个高于起点；但 PvZ 从初始 23 分降到所有更新后检查点的 6 分。论文提出经验噪音、探索与评测不匹配等可能原因，尚未单独隔离这些因素。

这不是同一组商业模型上三种路径的完整对照，因此不能据此断言参数训练优于或劣于上下文学习。它直接展示的是：经验进入参数后，收益可以被保留，错误也可以被固化。

## HarnessDev：把经验写进系统以后，它真的运行了吗

Aspire 讨论学习方向，S³Gym 讨论经验复用；HarnessDev 把被评测的产物换成了一个可运行的 harness。

Harness 是包在模型外面的执行系统：怎样循环调用模型与工具，怎样整理上下文、保存状态、处理失败，什么时候检查结果并结束任务。它决定经验能否成为默认行为。

### 写系统的模型，与用系统的模型，要分开记账

HarnessDev 有两个阶段。Creation 从一个弱种子开始：输入接口、文件和进程等基础工具已经存在，但没有替你写好任务求解循环、恢复策略和验证规则。Creator 根据任务类型、约束和少量开发案例，补成完整系统。Evolution 则从自己创建的代码 harness 出发，读取下游执行反馈，继续修改。

[查看原图](/images/posts/closed-loop-rsi-三篇论文深读/harness-seed.png)

理解这个实验，需要分开三样东西：

- <strong>Creator</strong>：创建或修改 harness 的模型。
- <strong>Executor</strong>：在冻结后的 harness 内执行下游任务的模型。
- <strong>开发环境</strong>：支持 creator 读文件、改代码、调试的现有工作台。

Self-Eval 让 creator 与 executor 使用同一个模型，测的是它能否为自己写出合用的系统。Unified-Eval 把执行模型统一为 Gemini 3.1 Pro，观察不同 creator 的产物在共同执行者下怎样表现。固定 executor 减少了模型能力差异，但不能消除 harness 与模型之间的兼容性问题。

Creation 覆盖四个领域、五个下游 benchmark，共 2,207 个独立任务。论文观察到，生成的系统在写作、机器学习实验中可以接近或超过所选成熟系统参考，在代码与搜索研究上仍有明显差距。这里的“人工 harness 参考”搭配了不同执行模型，其中一些数据来自外部公开结果。<strong>超过参考分数不等于超过人类，也不能把差距全部归因于 harness 设计。</strong>[HarnessDev §3–4.2、Tables 3–4](https://arxiv.org/html/2609.01437v1#S4)。

### 交付的是哪种系统，评分器又读取什么

Creator 获得任务类型说明、工具与权限约束、简短设计指导以及 1–3 个开发案例，再用可见反馈修改弱种子。Creation 为每个 creator—benchmark 组合独立创建三份 harness，分别验收后取平均，记为 avg@3。它衡量三次创建的平均表现；Aspire 写作实验的三次执行，则是对同一份冻结系统重复运行。

冻结后交付什么，要看下游领域。五个 benchmark 不是五个同质的问答题库：

| 下游评测 | 任务数 | 真正被验收的产物 |
| --- | ---: | --- |
| SWE-bench Pro public split | 731 | 仓库中的实际改动与补丁，按任务成功计分 |
| Terminal-Bench 2.1 | 89 | 工具执行后留下的最终环境状态，按任务成功计分 |
| MLE-bench | 75 | 机器学习实验提交物，按 medal 指标评价 |
| EQ-Bench3 | 46 | 最终写作文本，按 rubric 评分 |
| BrowseComp | 1,266 | 检索所得答案，按准确率评价 |

合计 2,207 个唯一任务。Evolution 使用其中的反馈任务，不另算一套新任务总量。[HarnessDev Table 2、§3.4 与附录 C](https://arxiv.org/pdf/2609.01437)。

这个产物边界很关键：harness 写下 `status=success` 不能直接获得成绩。SWE 的评分依据真实仓库 diff，Terminal 的依据是环境最终状态。审计日志用来解释过程，不能代替任务完成。

系统内部则要组织六类功能：执行循环、工具调用、上下文、状态与记忆、生命周期与恢复、结果验证。它们并不是“目录里各有一个文件”就算完成。例如工具返回错误，需要生命周期逻辑决定重试或退出；上下文需要保留重试原因；最后的验证又要检查产物是否满足要求。评分器看整体结果，运行轨迹帮助研究者定位是哪一段没有工作。

进入 Evolution 后，creator 可在十次正式完整评测对的预算内修改版本；两次正式评测之间还有受限的小样本探测。每个候选以冻结 commit 为单位，在 100 个 SWE 任务和 89 个 Terminal 任务上都完成评测后，才进入正式轨迹。随后声明一个最终版本，再通过不向 creator 返回分数的 630 个 SWE 任务观察迁移。这个过程同时测开发、反馈利用与版本选择，并非无限试到最好分数为止。

### 定义了 State 类，不等于形成了持久记忆

HarnessDev 的运行审计很有价值，因为它不只检查源码里有没有某个模块。

18 个代码 harness 都实现了显式执行循环。11 个定义了 State 类，但只有一个提供状态保存接口，只有一个实现周期性 checkpoint；在记录的 26,679 条任务轨迹中，没有观察到 checkpoint 事件。

这组证据支持一个明确结论：声明了状态结构，远不足以证明持久保存机制在本次评测里生效。它没有证明系统不存在任何临时状态，也不能据此说这些模块在所有可能场景下都不会触发。

对我们的工程 Agent，差别很具体。它可以写一个保存函数，但只有主循环在需要时调用它，失败恢复时读取它，恢复后的任务又利用它避免重复工作，经验才进入了系统行为。源代码中的存在、实际调用和最终收益，是三个不同层次的证据。

### 案例三：从“完成前检查”到真正触发的检查

<strong>论文轨迹：连续三个版本怎样修改和验收。</strong>HarnessDev 附录 I 记录了 Opus 4.8 在自身执行设置下的演化过程。它最初的 harness 在 SWE 反馈集上通过 68/100，在 Terminal 上得 74.157 分。这里继续使用附录中的 T1、T2、T3 表示三次正式修改，避免把未完成的尝试也算作演化收益。

<strong>第一步，先确认失败数据，再决定改哪里。</strong>Creator 发现事件流里有 56 条 SWE 记录的 score 为 null，没有直接把 null 当失败；它继续读取汇总与原始结果，确认基线确为 68/100。随后把 32 个失败中的约十个归为构建、编译或导入问题。修改方向因此变成：编辑后的任务不能仅凭自测声明完成，要增加完成前真实执行检查，并处理异常结束时的产物收尾。

这对应我们一直讨论的工程 Agent：先把“修复不可靠”拆成可观察的失败类型，再把经验转成完成规则。第一版同时包含多个改动，分数增长不能全部记在其中一个检查函数名下。

<strong>第二步，让检查读取真实变更，而不是依赖模型记忆。</strong>第一版改善后，creator 检查编辑记录，认为剩余问题不主要来自字符串替换失败，转而增加 `_current_diff()`，让结束前的自审读取仓库实际 diff。输入从“我记得自己改了什么”，变成“文件里实际发生了什么”。

<strong>第三步，找到没有触发的分支。</strong>这个自审依赖 git diff，但很多 Terminal 任务通过 shell 命令产生文件，不在仓库变更分支内。T2 的机制对这类任务没有触发。T3 因此记录显式写入路径、是否执行命令和工作目录近期文件，让非 git 任务也能在结束前审查产物。

| 冻结版本 | SWE 反馈分数 | Terminal 反馈分数 |
| --- | ---: | ---: |
| H0：原系统 | 68.0 | 74.157 |
| T1：完成前执行检查等修改 | 73.0 | 75.281 |
| T2：加入基于真实 diff 的自审 | 75.0 | 73.034 |
| T3：把自审扩展到非 git 产物 | 74.0 | 74.157 |

来源：HarnessDev 附录 I，PDF 第 40–41 页。每行是完整版本结果，不是对应模块单独贡献的消融分数。

<strong>机制归纳：</strong>下面按附录把最终机制整理成简化流程，并非源码原样抄录；超时和其他恢复分支省略。

```text
模型请求结束任务
  → 收集本轮执行与验证记录
  → 如果是仓库任务：读取真实 diff
  → 如果是非 git 任务：读取写入路径与近期产物
  → 把证据交给模型进行结束前自审
  → 若自审发现问题，继续修改和验证
  → 满足完成流程后提交实际产物
```

这里可以依次回答四个不同问题。<strong>有没有写出来？</strong>有明确版本和改动记录。<strong>有没有触发？</strong>仓库自审触发了，但曾漏掉非 git 分支，随后扩大覆盖。<strong>触发有没有解决问题？</strong>附录指出，T2 的 25 个 SWE 失败任务都已经触发反思，所以“调用了自审”仍不保证判断正确。<strong>整体有没有迁移？</strong>最终版本在冻结后的 SWE-Pro-630 上从 63.02 升到 67.46，提供了这条演化路径的正向结果；它不能证明每个组件都贡献收益，也不等于可迁移到任意任务或模型。

版本选择同样是案例的一部分。Creator 最后选择 T3，而不是继续消耗剩余七次正式评测预算。T1 的两项均值其实比 T3 高约 0.06 分，二者通过任务总数相同；它把这点差异放在运行噪音中解释，并考虑最终机制的覆盖情况。这个选择没有把“最新版本”“最高可见分”和“最佳未见分”当作一回事。

这条路径把经验内化追踪到了实际行为：失败分类决定检查策略，运行暴露遗漏分支，修改后再验收。接下来把它放回其他模型的对照中。

### 反馈集变好以后，还要冻结版本去看新任务

按前述 Evolution 协议，100 个 SWE 与 89 个 Terminal 任务用于开发反馈，另外 630 个 SWE 任务用于冻结验收。<strong>只有后一组的分数不向 creator 返回。</strong>因此，Terminal 成绩属于反馈集表现，不能算未见任务的迁移成绩。

下面选取 Table 6 的三行，分别展示有效迁移、收益缩小与迁移退化。反馈列是两个开发 benchmark 的均值，未见列只测 SWE-Pro-630；它们的差值不能当作同分布的“泛化损失”。

| Creator / 执行模型 | 可见反馈配对分数 | 未见 SWE-Pro-630 |
| --- | --- | --- |
| Opus 4.8 / 自身 | 71.1 → 74.1 | 63.02 → 67.46 |
| Qwen 3.7 Max / 自身 | 41.8 → 55.7 | 42.22 → 43.65 |
| GPT-5.5 / 固定 Gemini | 56.6 → 59.1 | 42.22 → 31.90 |

来源：HarnessDev Table 6，PDF 第 12 页，比较初始 H0 与 creator 声明的最终版本。每个 creator—executor 条件只有一条演化轨迹。

完整结果中，五条自身执行的轨迹在未见任务上都比 H0 好；固定 Gemini 的四条轨迹里，只有 Opus 的产物改善，其余退化。因此，结论既不是“改 harness 没用”，也不是“让模型反复改就一定变强”。<strong>一些改进有效，但其收益依赖执行模型，版本选择也会被可见反馈误导。</strong>

论文还观察到同一版本重复运行的配对分数存在波动。没有重复测量与运行证据的小幅上升，不能直接归因于代码改动。成本也要单独记账：文中的 execution tokens 统计执行者解决下游任务的消耗，不包含 creator 开发系统的 token，更不是全部改进成本。[HarnessDev §4.3、附录 B.4](https://arxiv.org/pdf/2609.01437)。

## 三篇合在一起，离完整的递归闭环还有多远

现在回看开头的三种能力，它们不是“先训练、再写 memory、最后改代码”的固定流水线。目标拆解可能发现需要改变工具；工具改造可能产生新经验；新经验又可能推翻原来的能力诊断。

但这组论文还没有把这种相互作用做成一个长期、统一的实验。尤其“递归”需要再多问一步：<strong>改进后的系统有没有接手下一轮改进工作，并让学习过程本身更有效？</strong>

Aspire 的框架允许在轮次之间提升一个训练后的后代作为决策模型，但本文报告的运行都固定初始决策模型。其 harness 实验也只创建一次后继，没有继续让 H1 演化出 H2。HarnessDev 则固定支持 creator 的开发环境，把“演化出的 harness 能否成为下一轮开发环境”留给未来研究。

对工程 Agent，这些结果可以落成一个具体的研究设计。假设它把最近几次失败归因为“完成前验证不足”，接下来应该留下这样一条可追溯的记录：

1. <strong>提出可证伪的学习目标。</strong>说明哪些失败可能由验证不足引起，哪些是根因诊断或实现错误；为自己的判断寻找反例。
2. <strong>把经验写成有触发条件的操作。</strong>例如发生代码修改后，完成检查需要读取修改后的测试结果，并核对结果与本次变更是否相关；不能仅凭模型声称成功。
3. <strong>实现并确认调用路径。</strong>在真实执行中观察检查是否触发、读到了什么、怎样改变结束决策，同时记录它额外消耗的资源。
4. <strong>冻结版本，使用未参与修改的任务验收。</strong>比较初始系统、候选系统和保留系统，重复运行以估计波动，并检查旧能力是否退化。
5. <strong>让保留版本再承担下一轮学习。</strong>在可比预算下，检验它是否更会发现问题、设计验证和选择更新，而非只在第一批任务上分数更高。

这是根据三篇论文推导的实验建议，不是作者共同发布的已验证方案。前三步检查方向、经验和系统，后两步才逐渐接近迁移与递归。

人的学习类比也应该停在这里。游戏得分和封闭任务集让实验可重复，却没有解决现实目标不断变化、多个目标彼此冲突的问题。“变得更好”最终由谁定义，仍留在实验边界之外。

目标形成要留下能力缺口的证据，经验形成要留下适用条件，行为内化要留下触发与收益的记录。下一轮递归要检验的，则是这些改变有没有让 Agent 更会完成这三件事。
