## 1. 问题背景：11点的报警显示

### 故障速览

**20251108 点请求失败率异常监控报告**

| 日期 | 小时 | exchange_id | 成功请求数 | 故障请求数 | 总请求数 | 成功率 | 故障率 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 20251108 | 11 | 某后验ctr流量对应pod | 153,154,716 | 103,595,855 | 256,753,451 | 59.65% | 40.35% |
| 20251108 | 11 | 模型流量对应pod | 398,953,939 | 68,874,854 | 467,830,380 | 85.28% | 14.72% |
| 20251108 | 11 | 海外对应pod | 461,038 | 954 | 461,992 | 99.79% | 0.21% |

**2025年11月8日 11:00**，广告CTR预估服务告警骤然响起：

- **后验CTR流量成功率暴跌至 59.65%**（正常应>99%）
- **影响范围**：1小时内影响200亿次以上广告请求失败
- **业务损失**：预估影响日收入 XX 万元（具体损失未结合eCPM计算）
- **核心问题**：为什么只有后验CTR流量的Pod出问题？

### 业务背景

在广告技术（AdTech）中，后验CTR（Post-verification CTR）流量是指：

- 需要对广告曝光后的真实点击情况进行回验
- 用于模型迭代和效果评估
- 对计算资源要求较高（需要实时统计、特征计算）

这类流量通常会部署独立的Pod集群，与线上实时竞价流量隔离。

### 2.3 初步假设

基于数据特征，我们的初步判断：

1. **不是流量洪水攻击**（海外流量正常，说明入口限流正常）
2. **不是代码回归**（模型流量正常，说明核心逻辑未变）
3. **极可能是后台任务导致**（CPU周期性波动，符合定时任务特征）

### 3.4.2 问题代码片段

**问题1：预算统计全量扫描**

```go
// internal/scheduler/statistic_task.go (问题代码)
func (s *StatisticTask) calculateBudget() error {
    //  问题：每小时全量扫描所有广告主预算
    for _, advertiser := range s.getAllAdvertisers() {  // 数万个广告主
        for _, campaign := range advertiser.Campaigns { // 每个广告主数百个计划
            // 计算消耗、剩余预算
            spent := s.calculateSpent(campaign.ID)
            remain := campaign.Budget - spent

            // 问题：大量JSON序列化
            data, _ := json.Marshal(BudgetInfo{
                CampaignID: campaign.ID,
                Spent:      spent,
                Remain:     remain,
            })
            s.cache.Set(campaign.ID, data)
        }
    }
    return nil
}

```

**问题分析**：

- 广告主数量：1万+
- 平均每广告主计划数：200个
- **总计算量：3万 × 200 = 600万次**
- 单次计算耗时：~5ms
- **理论总耗时：600万 × 5ms = 30,000秒 = 8.3小时** ⚠️

**问题2：冷启动索引全量重建**

```go
// internal/model_index/modules/cold_start_processor.go (问题代码)
func (p *ColdStartProcessor) refreshIndex() error {
    // 问题：每小时全量重建索引
    allCreatives := p.db.GetAllCreatives()  // 数百万条创意

    newIndex := make(map[string]*Creative)
    for _, creative := range allCreatives {
        // 计算特征向量
        features := p.extractFeatures(creative)  // CPU密集计算

        // 问题：内存拷贝
        newIndex[creative.ID] = &Creative{
            ID:       creative.ID,
            Features: features,
            Score:    p.calculateScore(features),
        }
    }

    // 问题：整体替换，触发大量GC
    p.index = newIndex
    return nil
}

```

**问题分析**：

- 创意总数：500万
- 单个特征提取耗时：~10ms
- **理论总耗时：500万 × 10ms = 50,000秒 = 13.9小时** ⚠️

### 3.4.3 根本原因总结

![image.png](/images/posts/线上故障排查-定时任务引发的引擎服务失败率飙升/image 3.png)

**🎯核心问题**：

1. **全量计算**：每次都处理全量数据（数百万级别）
2. **CPU密集**：大量循环、序列化、特征提取
3. **集中触发**：多个任务在整点同时执行
4. **单线程阻塞**：占用主进程CPU资源
5. **未做防护**：无熔断、限流、优先级控制

### **3.3.2 问题代码分析**

**优化前的代码（commit之前）**：

```
<GO>
// internal/model_index/filters/dmp_filter.go
type DMPTargetFilter struct {
    ctx *context.RequestContext
}
// 检查设备是否在白名单中
func (f *DMPTargetFilter) isInWhitelist(deviceGroups []int32, whiteTarget []int32, rule int32) bool {
// 【问题1】每次调用都创建新的map，重复构建
    whiteMap := make(map[int32]bool)
    for _, groupId := range whiteTarget {// O(m)
        whiteMap[groupId] = true
    }

// 【问题2】嵌套循环，时间复杂度 O(n×m)
    matchCount := 0
    for _, groupId := range deviceGroups {// O(n) - n=1000（设备DMP标签数）
        if whiteMap[groupId] {// O(1)
            matchCount++
        }
    }

// 判断规则：并集(rule=1) 或 交集(rule=2)
    if rule == 1 {
        return matchCount > 0// 任意匹配
    } else {
        return matchCount == len(whiteTarget)// 全部匹配
    }
}
// 对每个创意调用过滤检查
func (f *DMPTargetFilter) Filter(ad *Ad) bool {
// 每个创意都要执行一次 isInWhitelist
    return f.isInWhitelist(
        f.ctx.DeviceDmpTarget,// 设备DMP标签：1000个
        ad.DeviceGroupWhiteTarget,// 策略白名单：100个
        ad.DeviceGroupWhiteRule,
    )
}

```

### **3.3.3 性能计算（惊人的发现）**

假设一个典型的后验CTR请求：

- 召回创意数：`tot = 90,852`
- 设备DMP标签数：`len(DeviceDmpTarget) = 1000`
- 策略白名单数：`len(DeviceGroupWhiteTarget) = 100`

**计算量分析**：

```

单次 isInWhitelist 调用：
  - 构建 whiteMap：100 次操作
  - 遍历 deviceGroups：1000 次操作
  - 总计：1100 次操作
单个请求总计算量：
  = 90,852 创意 × 1100 操作/创意
  = 99,937,200 次操作
  = 约 1 亿次操作 💣
假设单次操作耗时 100ns：
  = 1 亿 × 100ns
  = 10,000,000,000 ns
  = 10 秒

```

**🎯根本原因找到了！**

- 每个创意都重复构建白名单map（`whiteMap`）
- 算法复杂度是 **O(tot × n × m)**，其中：
    - `tot`：召回创意数（90,000+）
    - `n`：设备DMP标签数（1000+）
    - `m`：白名单组数（100+）
- 单个请求需要 **1亿次操作**，耗时10秒+
- 并发请求导致CPU飙升至500%，大量请求超时

func (f *DMPTargetFilter) isInWhitelist(deviceSet map[int32]struct{}, whiteTarget []int32, rule int32) bool {
    if len(whiteTarget) == 0 {
        return true// 白名单为空，不限制
    }

    matchCount := 0

        }
    }
