> 原报告：*Qwen3.8-Omni: Towards Native Omni-Modal Agents*，Qwen Team，arXiv:2609.25611v1。arXiv 提交于 2026 年 9 月 22 日，PDF 封面日期为 9 月 23 日。以 v1 为准；代码分析固定到 9 月 30 日采集的提交。

会议助手听到一句“按刚才那个方案，把这一块改掉”，离完成任务还远。它得知道是谁说的，“刚才”对应哪段讨论，“这一块”指屏幕上的哪个对象，再把这句话变成工具能执行的目标。Qwen3.8-Omni 技术报告的主线正是这条链：感知编码器怎样把不同信号交给同一个 Thinker，训练又怎样让这个 Thinker 继承文本 Agent 的推理和执行能力。

[报告原文](https://arxiv.org/abs/2609.25611v1)覆盖模型、训练、视频生产、实时语音和两个开源框架，按功能逐个介绍很容易读成产品目录。真正把这些部分连起来的是表示和训练，实验和系统实现则能检验这条链在哪里成立、在哪里还缺证据。

## 从“看懂这段视频”到“根据这段视频去做事”

文本 Agent 已经有一套成熟的循环：读任务，调用工具，接收结果，继续推理。多模态输入让循环的起点变复杂了。音频里不只有文字，视频也不只是一串独立图片；说话人切换、重叠语音、语气、屏幕操作和时间先后，都可能改变下一步行动。

常见的组合是先用 ASR 转录，再让视觉模型写摘要，最后交给文本 Agent。它能用，但有明确的信息瓶颈：转录丢掉空间声音线索，视频摘要可能漏掉一个短暂动作，两份材料也不一定用同一条时间轴。关键线索一旦没进中间结果，后面的推理模型就没有机会重新判断。

Qwen3.8-Omni 的做法是让这些信号尽早进入同一个推理模型。感知编码器仍然分开，但输出投影到共享空间、按时间组织成一条序列，文本能力和多模态能力在训练中共同塑造这个模型。作者想要的结果是：输入换成声音或视频，模型仍保有文本任务上的规划、工具使用和长流程执行能力。

报告主要讨论的模型是 **Qwen3.8-Omni-Flash**，实时版本是 non-thinking 的 **Qwen3.8-Omni-Flash-Realtime**。它继承 Qwen3.8-Next 的 sparse MoE backbone，但 Omni 报告和 Next 架构报告是两份材料：Next 可以帮助理解骨干设计，它的训练参数、速度和评测结论不能拿来当 Omni 的结果。

这条链可以拆成三个问题：编码器有没有留下任务需要的信息？Thinker 能否关联这些信息、找到相关上下文？训练有没有让模型把理解变成可靠的行动，而不只是一段解释？架构和训练设计分别对应这三个问题。

Figure 1 把模型和应用画在了一起：左上是 Thinker 和感知部分，中间是记忆、caption、skill 等接口，右侧是主 Agent 的规划、工具调用、上下文管理与执行，下方是视频生产和研究流程。其中关键的连接是“感知输出怎样成为执行证据”。图里的生成、剪辑和实验工具属于外部工作流，交付一个视频或训练结果时，不能把全部产物都算成模型的原生输出。

## 三个编码器：先保留不同信息，再进入同一个 Thinker

### AuT 把声音压成低频率的上下文表示

一般音频走 Audio Transformer（AuT）。Section 2 的前处理写得很具体：一般音频（包括视频里的音轨）重采样到 **16 kHz**，用 **25 ms 窗口、10 ms hop** 生成 **128 通道 mel-spectrogram**；四个 Conv2D block 下采样 16 倍，再经时序 self-attention 得到上下文化表示，输出速率 **6.25 Hz**，约每 160 ms 一个 token。Figure 2 在一般 AuT 路径上标了 32 个 self-attention 层。

这些数字能连成一条可核对的链：10 ms hop 对应每秒约 100 个特征时间步，下采样 16 倍后约每秒 6.25 个输出位置。实际边界长度还受分块、padding 等实现细节影响，报告没有展开。

低频率表示一方面缩短了长音频交给 Thinker 的序列，另一方面让每个位置能整合一段局部声音。“一个 token 对应 160 ms”并不是把话机械切成互不相关的片段，时序 self-attention 让每个输出都带着更大范围的上下文。

报告还提到 dynamic attention-window training，让同一个编码器既支持带缓存的 streaming 推理，也支持 offline 理解。这解释了 AuT 为什么要兼顾两种模式；窗口采样分布、缓存容量和两种模式各自的延迟，v1 没有给出。

AuT 预训练用专门的 Qwen ASR 模型生成转录监督，语料覆盖 20 多种语言，中文、英文与其他语言的比例为 **3.5:3.5:3**。这个比例只描述 AuT 预训练语料，推不出整个 Omni 训练数据的语言构成。

<Figure src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/p02-audio-encoders.png" alt="原报告 Figure 2：一般 AuT 与 Spatial AuT 两条并行音频编码路径" caption="来源：原论文 Figure 2，PDF 第 4 页；仅作忠实裁剪" />

用输出速率估一下量级：一小时 3,600 秒，一般 AuT 约产生 **22,500 个编码输出位置**。这是表示层的估计，**不是 API 计费 token 数**，也不含视频 patch、空间音频、时间戳、对话历史、工具结果和输出。写成“一小时音视频只花 22,500 token”，就把几个不同层面的量混在了一起。

压缩率和任务可靠性之间有实际取舍。低频率减轻了序列负担，但快速事件、多人重叠和细小声学差别保留了多少，要靠具体任务检验，编码率本身说明不了识别率或定位精度。

### Spatial AuT 保留声音从哪里来的线索

一般音频表示擅长承载声学和语言内容，空间声音还需要通道之间的关系。Spatial AuT 单独走一条路径：先经空间接口把多通道音频表示成 **FOA（first-order ambisonics）**，再对 FOA 通道做复数 STFT，**同时保留实部和虚部**，然后用卷积前端、时序 self-attention 和输出投影转成空间音频表示。

保留复数表示，保住的是通道间的幅度与相位关系。不同方向的声音在多通道记录里留下的关系不同，混成单声道后这部分信息就没了。所以这里的“空间”不是给普通声音 token 贴一个方向标签；手里只有单声道录音时，复制成几个相同通道也恢复不出原本不存在的相位和方向证据。能不能用上这条路径，首先取决于采集端和媒体格式有没有保留这些信息。

报告把这些线索关联到声源的方向、距离和运动。更准确的理解是：Spatial AuT 为这些判断提供了信号通道。阵列标定、FOA 转换、坐标约定、空间误差函数，以及把 embedding 解码成米制距离的方法，架构章节都没有公开。后面 OmniEchoBench 的提升是相关证据，但覆盖不了所有采集设备和声学环境。

### 三路编码器共用推理空间

视觉路径处理图片和动态采样的视频帧。三路编码器的输出各自经过 modality-specific adapter，投影到 Thinker 的 embedding 空间；文本用继承自 Next 的 byte-level BPE tokenizer，词表约 250K。不同信号由此有了进入同一个语言骨干的入口。

共享空间让 Thinker 能在一次推理里关联“说了什么”和“画面上发生了什么”。但维度对上不等于能用：adapter 传出的表示要能被骨干正确理解，需要训练把它和已有的语言表示接起来，这正是 S1 单独做编码器对齐的原因。

视觉编码器的初始化来源，v1 前后写法不一：Section 2 说 adopted from Qwen3.8-Next，Section 3 的 S1 说 adopted from Qwen3.5。架构层面“三路编码器经 adapter 接入共享 Thinker”是确定的，精确的初始化 checkpoint 要等作者澄清。

## 时间对齐：让统一表示保留可回查的关系

视频任务常常依赖一组同时成立的事实：某句话在什么时刻说出，当时画面上是什么，动作发生在话语前还是后。如果所有 audio token 放一处、image token 放另一处，模型要花额外力气去关联。Qwen3.8-Omni 把视觉、一般音频和空间音频表示按时间组织，并保留**显式文本时间戳**，让源媒体的时间线直接进入语言骨干。

时间在这里有两个用途。位置索引告诉模型表示之间的相对结构；显式时间戳则让输出和工具调用能指回原媒体的具体时段。模型觉得证据不够时，可以请求重读某个片段，不必只依赖压缩过的摘要。

Spatial AuT 的位置安排类比同一帧内的视觉 patch：同一时间片的空间 embedding 共享 temporal index，但各有不同的 spatial position index，既对齐到音频时间轴，又不会被当成同一个位置。报告说明这沿用了 Qwen3.5-Omni 的音视频时间戳策略，只是把空间音频纳入了已有约定。

<TechGraph src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/g02-temporal-layout.svg" title="TEMPORAL EVIDENCE" caption="图解：声音、画面与空间表示共用时间锚点（博主自绘，基于原论文 Section 2.2；非精确 token 排列）" />

拿“他刚才说这个方案不行”来看：音频内容给出否定判断，时间锚点限定“刚才”的范围，视频可能说明指的是哪张图，空间信息可以辅助区分声源。模型要把这些证据组成一个判断，而不是把三份 caption 拼在一起。

这是对机制的解读，报告没有单独消融文本时间戳或空间位置索引，也没有给出跨流时钟偏差的容忍度。音轨与画面起点不同、裁剪偏移或丢帧时，统一序列里照样会有错误的对应。所以做按需读取时，要把原媒体时间、片段起点、采样时间和输出引用串起来：模型说“12:30 的画面”，工具得知道这是原视频的时间还是裁出短片里的时间。

## Thinker：压缩历史与检索细节共同承担长上下文

### GDN 留住历史状态，注意力保留直接取证

Thinker 继承 Next 的 sparse MoE backbone，混合 Gated DeltaNet 与 interleaved attention。GDN 用固定大小的 recurrent state 总结前文，注意力层保留对上下文 token 的直接访问。前者持续更新历史，控制长序列成本，但终究是压缩表示；需要逐字引用、辨认很早的一张图或回查一段声音时，还得靠直接访问原 token 的路径。

QSA（Qwen Sparse Attention）进一步缩小注意力的访问范围：轻量 indexer 对压缩后的 **micro-block representation** 打分，选出相关块，核心注意力再在选中块的**原始 token** 上计算。被压缩的只是 indexer 用来做选择的块级表示，参与注意力的仍是原 token。长视频里大量片段与当前问题无关，稀疏选择正是利用这一点；反过来，indexer 选错，关键证据就进不了这一层的注意力。

模型内部的 QSA 检索和 Agent 调工具重读视频，是两个层级的事。QSA 在已经进入上下文的 token 里挑选，工具调用则从外部媒体取来还没进上下文的新证据。前者改进内部访问，后者改变输入获取，报告同时强调长上下文骨干和主动取证，原因就在这里。

Next 报告里的 micro-block 参数、top-k、训练 step 和吞吐，不能移植到 Omni 上：Omni 报告说明了机制和阶段，没有公布这套多模态训练里的具体配置。

### 256K 和 1M 属于不同训练阶段

四阶段预训练全程使用 **262,144 token** 的原生序列长度，**后训练之后**才扩展到 **1M token**。所以 1M 不是“一开始就在百万 token 音视频上共训”，256K 也不是最终支持的上限。

窗口大小解决的是一次能装多少上下文。能不能用好这些上下文，还取决于表示质量、时间结构、稀疏选择和任务训练：窗口装得下一小时媒体，和稳定识别其中的说话人、完成行动项，是两回事。它也影响使用策略，任务只需要几个片段时，先粗看再精读比整段塞进去省得多，后面的 Table 7、Table 8 就在检验这个选择。

## 四阶段预训练：把表示学稳，再适应稀疏访问

架构提供了路径，预训练决定模型是否真会用它。Qwen3.8-Omni 把预训练拆成 S1 到 S4，每一步改变的参数和目标都很清楚，思路是让每次训练变化只解决一个问题。

<TechGraph src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/g03-pretraining.svg" title="FOUR-STAGE PRETRAINING" caption="图解：编码器对齐、全参数共训、QSA warmup 与稀疏适配（博主自绘，基于原论文 Section 3）" />

### S1：冻结语言骨干，先打通编码接口

S1 用 Next 参数初始化 LLM 并冻结，三个编码器分别在 image-text、monaural audio-text 和 multichannel audio-text 数据上对齐，先训 adapter，再训编码器。

冻住骨干，等于给编码器一个固定的目标空间：它们得输出现有 LLM 能理解的表示，而不是一边改输入、一边大幅挪动接收端。先 adapter 后 encoder，又把“怎么连接”和“怎么提取”分成了两层。报告没有做“不冻结”的消融，这个顺序是作者的实际选择，不是被证明的最优解。

“分别训练”说的是对齐阶段的训练方式，部署时并不是三个独立 Agent，三路输出仍投影到同一个 Thinker。

### S2：全参数共训练，让语言能力参与多模态学习

S2 解冻全部参数，用更广泛的文本、音频、图像、视频和 video-audio 数据训练，语言骨干开始参与学习多模态关系。纯文本没有被丢掉：分项中 text 1.1T token，audio 0.7T，image 0.35T，video 0.15T，video-audio 0.3T。这和核心目标一致，引入新模态的同时保住强文本能力，为后面把文本 Agent 能力迁到多模态任务打底。

<Callout type="note" title="原文的数据总量存在口径冲突">

S2 正文写“约 2.5T token”，五项相加是 2.6T。两个原始口径都保留，不把任一个当精确总量，也不据此计算精确的模态占比。报告没有说明差异来自四舍五入、统计范围还是编辑问题。

</Callout>

“统一”这个词容易遮住混合训练的难处：各模态的损失、长度、数据质量和任务难度都不一样，便宜的文本容易主导训练，噪声音频会增加优化负担。token 总量只说明规模，说明不了有效监督是否均衡。后面文本任务保持得不错，支持“加入多模态没有全面破坏文本能力”；要证明是哪种配比带来的，还需要训练混合的消融。

### S3：先教 indexer 选择，再把注意力改稀疏

S3 冻结 backbone，dense attention 照常工作，只训练 QSA indexer，监督信号来自骨干的 full-attention distribution。

关键在于这时 indexer 还不决定主模型能看到什么。密集注意力仍在，教师信号覆盖完整上下文；如果一开始就让没训好的 indexer 丢掉大部分上下文，模型的访问方式会突然改变，还会失去正确的选择监督。先在稳定骨干上学选择，把“检索哪些块”和“怎么用这些块”拆成两步，检索器和下游推理一起从不稳定状态出发时，出了问题很难分清是证据没选中，还是选中了没用好。

蒸馏损失、block size、分数归一化和模态相关的选择策略，报告没有给出。不同模态的 token 数和信息密度不同，某一路表示会不会在选择中被系统性忽略，是个值得研究的问题。

### S4：启用 QSA，让骨干适应新的访问方式

S4 真正启用 QSA，骨干和 indexer 联合优化。dense attention 训出来的骨干习惯了某种证据覆盖方式，改成稀疏后，即使重要块大多找得回来，注意力分布和可用信息也变了，联合训练给两者一个共同调整的阶段。

回头看，S1 到 S4 分别解决接口对齐、共同表示、块级选择和稀疏适应：感知信息可靠送入在前，降低访问成本在后。这个顺序是报告里最可借鉴的工程逻辑，只是离复现手册还差得远，具体缺什么见文末的缺口清单。

## 多教师后训练：让同一个 Thinker 学会多种任务策略

预训练给了模型可用的表示和知识，后训练要把它们组织成能遵循指令、调用工具、完成长任务的策略。Thinker 的后训练分两步：**Multi-Teacher Distillation** 和**统一 RL**，训练对话用 ChatML 序列化，覆盖纯文本、视觉、音频和混合模态。

### 教师提供的是任务轨迹，不是部署时的专家委员会

作者从同一个 pretrained Qwen3.8 base checkpoint 初始化多个领域专家，各自做 SFT 和 RL，覆盖一般指令、基础推理、coding、agentic tasks、视觉理解和音频理解。专家生成高质量的领域训练轨迹，汇成统一的多模态训练混合，蒸馏给一个学生。

<TechGraph src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/g04-distillation.svg" title="MULTI-TEACHER DISTILLATION" caption="图解：领域专家生成轨迹，能力汇入单一学生（博主自绘，基于原论文 Section 4）" />

这里的“专家”和 MoE 的 expert 是两回事。MoE expert 是骨干内部按 token 路由的参数模块；后训练教师是独立优化、用来提供轨迹的模型。蒸馏完成后，学生每次请求不用召集任何教师，最终得到的是一个共享参数的策略。

作者认为，让各领域先在自己的任务和反馈里充分优化，再给学生提供一致的监督，比直接在异构混合数据上 fine-tune 更能减少跨领域、跨模态的干扰。这是作者的机制解释：报告没有做同等预算下单一混合 SFT、多教师蒸馏和不同教师数量的对照，定量上还不成立。

轨迹的价值在于能承载过程。对 Agent 来说，只给最终答案和给出完整过程，监督量差得很远：何时请求证据、何时调工具、拿到失败结果后怎样改计划，都会影响执行策略。轨迹 schema、工具调用字段、过滤阈值和领域权重，报告没有公开，也就无从假设训练数据里有某种特定的隐藏推理格式。

这一步也部分回答了“音频怎样继承文本 Agent 能力”：架构让不同输入进入同一个 Thinker，多领域轨迹让它在共享参数里学到不同任务的策略，目标、证据和环境反馈可以来自不同模态，决策由同一个策略做出。报告用整体评测支持这一点，但没有设计严格匹配的实验，证明某项声音任务的提升只来自文本领域的迁移。

### 蒸馏之后，统一 RL 修正真实交互中的不均衡

作者坦白了蒸馏后的问题：音频条件的 query 比对应的文本 query 更难；长对话会暴露不必要的语言切换、persona drift 和指令遵循退化。第二阶段 RL 就针对这些实际行为，不假定各领域能力合在一起就自动稳定。

任务混合覆盖 reasoning、coding、agentic execution、多模态理解、audio-conditioned dialogue 和 multi-turn interaction，奖励同时看任务正确性和交互质量。对长时程 Agent，奖励由**任务结果和执行结果**决定，模型自报“已完成”不算数。

<TechGraph src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/g05-reward-loop.svg" title="OUTCOME-BASED POLICY" caption="图解：将任务执行结果与交互质量反馈到统一策略（博主自绘，基于原论文 Section 4）" />

这是整份报告里和 Agent 实现关系最直接的一句话。模型可以把步骤讲得很流畅，也可以出错后声称任务完成；奖励只看表面文本，它就有机会去优化“看起来成功”。用执行结果定奖励，策略目标才接回环境：文件有没有生成，程序有没有通过检查，工具调用有没有产出所需结果。

复杂交互里的“帮助程度”“自然度”“人格稳定”仍需要定义，甚至互相冲突，v1 没有披露 reward model、奖励权重、Thinker 的 RL 算法、rollout budget 和训练曲线。尤其不能因为后面 Talker 写了 GSPO，就推断 Thinker 也用 GSPO：报告对 Thinker 只写了两阶段框架和优化目标，Talker 是另一套五阶段训练，最后一阶段才点名 GSPO。

跨模态一致性是另一个难点。同一个任务用文字问和用声音问，理想情况下判断不该差太多；但声音带着停顿、含糊和环境信息，逐字一致也未必是正确目标。一个可行的检验是：同一任务分别准备文本、音频和音视频版本，比较目标理解、证据引用、工具调用和最终产物是否一致，再拉长到多轮，看会不会忘记约束、擅自换语言或重复执行。这是从训练目标推出的建议，报告没有提供现成的测试集。

## 实验检验：统一策略保住了什么，改善了什么

### 文本能力保留，是迁移主张的第一道检验

加入多模态后如果文本能力明显下降，“继承 Agent 能力”就失去了前提。Table 2 把 Omni 与 Qwen3.8-Flash 等模型放在文本 reasoning、coding 和 agent benchmark 上比较。

<Figure src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/p03-text-results.png" alt="原报告 Table 2：文本 coding、agent 与通用能力评测及评测脚注" caption="来源：原论文 Table 2，PDF 第 9 页；仅作忠实裁剪" />

与 Qwen3.8-Flash 相比，Omni 的 DeepSWE 为 57.8 对 58.7，SWE-bench Pro 63.3 对 62.5，SWE-bench Multilingual 80.5 对 81.0，NL2Repo-Bench 48.9 对 48.1；通用任务上 IFBench 81.5 对 81.3，GPQA Diamond 91.0 对 91.7，HLE 36.5 对 35.9。有升有降，整体持平。这组结果支持“在报告选定的文本任务上保持了相近水平”，但没有置信区间，零点几分的差值是否稳定无从判断。

### 音频收益集中在结构理解，普通 ASR 也有退步

Table 4 覆盖多人 ASR、multilingual ASR、audio caption、音频推理、音乐理解和 audio interaction，指标各不相同，不能直接求平均。DER、cpWER、WER 越低越好，accuracy 和 similarity 越高越好。

<Figure src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/p04-audio-results.png" alt="原报告 Table 4：多说话人、识别、推理、音乐与语音交互评测，含指标方向脚注" caption="来源：原论文 Table 4，PDF 第 11 页；仅作忠实裁剪" />

变化最大的是多人场景。AliMeeting 的 **DER / cpWER** 为 3.4 / 17.2，前代 88.1 / 89.6；AISHELL-4 为 2.8 / 11.2，前代 100 / 100。DER 衡量说话人分离错误，cpWER 衡量带说话人归属的转录错误。这些结果关乎“谁在什么时候说了什么”，一句“ASR 大幅提升”概括不了。对会议 Agent，这种结构比识别一串文字更接近行动项分配的前提，把甲的承诺记到乙名下，识别再准也会派错任务。不过会议总结准确率、行动项归属和外部执行成功率仍要各自评估，低 DER 不等于整条会议工作流可靠。

普通 ASR 并非全面进步。WenetSpeech Net 的 WER 从前代 3.7 升到 4.8，FLEURS-ASR 从 7.2 升到 9.3，都是退步。OmniLingua-Long-AudioASR 的 success rate 从 94.07 升到 95.56，WER 却从 6.89 升到 9.27：成功返回和转录质量是两个维度。音频交互同样有负结果：WildSpeech 74.3（前代 75.7），VoiceBench 91.6（前代 92.9）。音乐理解的 MuChoMusic-RUL 明显提高，MMAU、MMAR、MMSU 没有形成全面领先。仅凭这些数字，分不清退步来自数据配比、优化还是评测设置，但足以否定“统一多模态一定全面更好”。

Spatial AuT 对应的空间能力，在 Table 5 的 OmniEchoBench 上是 **43.9**，前代 23.3，Gemini 3.8 Flash 32.0，方向和新增的空间路径一致。报告没有做去掉 Spatial AuT 的匹配消融，这个模块的独立贡献仍量化不了。正文另写了 41.7，与表格不一致，以表格值为准。

### Agent 评测检验的是输入理解与工具环境的组合

Table 6 比较四个多模态 Agent benchmark。Omni 在 WildClawBench、UniClawBench、Agentic-V、OmniGAIA 上分别为 71.0、69.6、36.8、74.0，前代为 34.5、67.1、14.5、57.2。涨幅很不均匀，也并非四项都领先其他基线。

各项的执行环境不同：WildClawBench 和 Agentic-V 用 Claude Code，UniClawBench 用 OpenClaw，OmniGAIA 在表里没有外部 harness。把这些分数看成四种任务与环境的组合更贴近实际。它们支持多模态执行能力有进步，但报告没有把编码器升级、多教师蒸馏、统一 RL 和工具配置逐项拆开，整条训练链的结果能评估，每个环节各贡献多少还不知道。

对复现者来说，最该带走的是任务成功的判定标准：规划看起来合理、工具被调用过都不够，还要检查取到的证据对不对、目标对象有没有真的被修改、产物能不能用。这和报告的后训练方向一致，也比聊天观感更容易做成可重复的测试。

## 主动取证：把统一策略用于输入选择

模型会调工具之后，最直接的用途之一就是改变长视频的读法。静态方式把采样帧和音频一次性送进去；agentic 方式先围绕问题做规划，再用工具由粗到细取相关片段，必要时反复核对，或者把音频、视觉分析交给子 Agent。

这把长上下文问题拆成了“先决定看什么”和“再看足够的证据”。大窗口依然有用，只是不必每个问题都把媒体完整重看一遍。QSA 减少对已有上下文的访问，主动取证减少进入上下文的内容，两者在不同位置控制成本。

Table 7 很适合检验这一点，因为它对同一个模型只切换使用方式。Omni 的 OmniVideoBench 从 63.4 升到 67.8，Video-MME-v2 从 65.0 升到 71.3，LVOmniBench 从 63.3 升到 73.6。Gemini 3.8 Flash 在前两项从 65.2 升到 70.1、从 71.0 升到 72.7，LVOmniBench 持平于 70.7。

<TechGraph src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/dv01-static-agentic.svg" title="STATIC VS AGENTIC" caption="数据来源：原论文 Table 7，PDF 第 14 页；按原始六组数值重绘，无新增数据或插值" />

在报告的设置下，主动执行改善了 Omni 的三项理解任务，另一模型也在部分任务上受益，收益并非 Omni 独有，任务和工具方式同样重要。这里改变的是推理工作流，说明不了训练中哪个模块有效。

Table 8 给出 OmniVideoBench 上的输入成本：准确率从 63.4% 到 67.8%，提高 **4.4 个百分点**；每个 query 的 token consumption 从 **145,736** 降到 **79,117**，减少约 **45.7%**，统计保留了跨轮次上下文。这是可核对的 token 效率证据，但不是“总耗时减少 45.7%”，也不是“账单减少 45.7%”：工具调用、媒体裁切、网络传输和多轮输出都要花时间和钱，报告没有给端到端统计。

按需读取也有自己的失败方式：粗看没发现关键片段，精读就会沿着错误方向展开；摘要丢了时间锚点，工具就无法准确回查；子 Agent 给出没核实的解释，主 Agent 可能继续放大错误。所以除了控制 token budget，实现里还应保留源片段地址、读取记录、工具结果和失败状态。报告没有公开完整的错误恢复策略，这几条属于工程建议。

报告还演示了四川话 ASR 的 autoresearch：12 小时内四轮迭代，构建 3,413 条样本，CER 从 25.79 降到 15.30，下降 10.49 个百分点，相对减少约 40.7%。它说明 Agent 能组织数据、迭代实验；但测试选择、样本构建和优化在同一个工作流里，没有完全独立的 held-out 集和重复试验，推不出通用的自主研究成功率。

## Talker：把统一策略的结果变成连续语音

实时交互还有一个问题：Thinker 做出决定后，用户多久能听到声音，声音能否与仍在生成的文字保持一致？报告把这项职责交给 Talker。

Thinker 接收多模态输入，产生文本和高层表示；Talker 据此生成 acoustic token；causal Code2Wav 把 acoustic token 转成可连续播放的波形。Talker 用 RVQ（Residual Vector Quantization）表示声音，其中的 MTP 模块预测**当前 acoustic frame 的 residual codebook token**。这和文本模型里“预测未来多个 token”的 MTP 含义不同，它服务于帧内细节建模，配合因果波形重建，免去等待整段声音生成完。

<Figure src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/p06-realtime.png" alt="原报告 Figure 3：Thinker-Talker 实时模型及 Qwen-Live-Harness 的工具、子 Agent 和记忆连接" caption="来源：原论文 Figure 3，PDF 第 15 页；仅作忠实裁剪" />

语音和文本的 token 速率不同，按固定比例交错容易对不齐。报告沿用 ARIA（Adaptive Rate Interleave Alignment），让 Talker 在部分文本前缀上就能生成连贯语音。前代 Qwen3.5-Omni 报告 Section 2.4 把它描述为自适应速率约束，本版没有重新展开公式和阈值，buffering 参数也就无从补写。

这一代 Code2Wav 加了上采样路径，把波形重建从 **24 kHz 扩展到 48 kHz**，作者称改善了高频保真度。采样率提高只是给了高频内容表达空间，听感、自然度和克隆准确度要看 speech benchmark。

Talker 的训练分五个阶段：平衡数据预训练、复杂对话 CPT、语言专家加 MOPD、说话人轻量 fine-tuning、最终 RL。最终阶段由已对齐的 Thinker 提供奖励信号，Talker 用 **GSPO** 优化。Thinker 负责理解、决策和交互策略，Talker 负责语音实现与偏好，两套训练各管一段。

语音输出质量也要分任务看。Table 12 里 speech style control 为 95%，Gemini 为 97.5%；phoneme instruction following 为 93.3%，前代 61.3%。Table 11 中部分长语音转录和说话人相似度明显改善，但 SwanBench-Speech 中文内容稳定性的错误率是 1.96，前代 1.76，仍有退步。能流式播报、能控制风格、能准确执行指令，是三种不同的能力。

### 首音频包和完整对话延迟要分开测

Table 9 给出 Realtime API 的性能：6、12、20 秒音频输入的 TTFT 约 591-618 ms，TTFC 约 978-1,026 ms；音视频输入 TTFT 约 838-981 ms，TTFC 约 1,215-1,350 ms。generation RTF 约 0.153，即在其统计区间内生成速度约为实时播放的 6.5 倍。

<Figure src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/p07-latency.png" alt="原报告 Table 9：Realtime API 的输入时长、TPS、TTFT、TTFC 与 generation RTF" caption="来源：原论文 Table 9，PDF 第 15 页；仅作忠实裁剪" />

测试条件：16 kHz mono PCM，视频 1280×720、1 FPS；每种设置 warmup 一次后，在新 session 中取十次有效响应，要求输出超过 200 token；输入在显式 commit 前已上传完毕，voice activity detection 关闭。

读这张表的关键是计时起点。TTFT / TTFC 从客户端 **commit** 开始，分别到第一个非空文本 / 音频 chunk，包含这段时间的网络和服务等待，但**不包含建连、输入上传和客户端播放**；generation RTF 从首个到末个音频 chunk 计算，不含首包等待。所以“约一秒出首个音频包”不能改写成“用户说完约一秒就能听到回应”，后者还要算上 VAD、上传、缓冲和设备播放。报告也没有提供高负载 P95、错误率、完整 turn latency 和打断恢复的数据，放进真实产品前需要按完整链路自己测。

## Harness：让训练出的策略有地方执行

模型学会使用工具，不等于自动拿到每个桌面软件的接口。报告开源了 Qwen-MM-Plugins，给现有 harness 补上多模态能力；Qwen-Live-Harness 负责组织实时前台、后台任务、监视和记忆。

归档的 MM-Plugins commit 为 `07736672525443c7f8a3f6405eed37d2236f023f`，Live-Harness 为 `b6ce544ebbcd7417e37e0314ec946466c49c615c`。这是 9 月 30 日的快照，晚于报告提交，可以用来看机制有没有代码承接，不能当成论文实验恰好使用的版本。

### Plugins 把能力接进工具和产物流程

[MM-Plugins 固定版本的 README](https://github.com/QwenLM/Qwen-MM-Plugins/blob/07736672525443c7f8a3f6405eed37d2236f023f/README.md) 把能力组织成 Skill 加可选的 MCP server，并指出现有大多数 harness 还不能把音频原生传给主模型，音频目前走 API。模型能理解音频，和任意文本 Agent 客户端都能把音频传进去，中间还隔着一段接口距离。

报告里的 Omni-Caption、Video2Note、Omni-Memory 和 Omni-Skill-Creator，分别把理解结果用于文本证据、笔记、可检索记忆和操作技能。音乐 MV、视频翻译和电影解说还需要外部的生成、配音或剪辑工具，Omni 在其中负责理解、规划、审核和调用，它不是原生视频生成模型。

固定快照里 `omni-video2note` 的 `pipeline/runner.py` 流程很清楚：读取源视频并计算哈希，准备媒体 chunks，调用模型理解，生成文档计划和初稿并校验，按时间选帧，最后本地渲染 PDF；截图不可用时退到纯文本，带图渲染失败时也可能输出纯文本 PDF；输出前再核一遍源文件哈希。理解和产物分阶段，失败能定位到具体环节；处理中复核哈希，避免理解的是一份视频、交付时引用的是另一份。

同时要注意两点。`status: complete` 可能伴随“没有截图”的 warning，不能只看完成状态就认定产物与原计划一致。报告说 Video2Note 可以结合审核反馈，但这个入口返回的是 `audit: None`、`review: None`，至少这条路径上不能认为自动审核已经执行。代码只做了静态阅读，没有运行云端视频理解，读懂不代表运行一定成功。

### 实时前台与后台任务采用不同节奏

[Live-Harness 固定版本的文档](https://github.com/QwenLM/Qwen-Live-Harness/blob/b6ce544ebbcd7417e37e0314ec946466c49c615c/README_ZH.md)把系统拆成 Node.js daemon 和 Electron Host：Host 负责采集、播放、权限和 UI；daemon 连接云端 Omni Realtime，调度对话、工具、后台 harness、Proactive 和 Memory；两者通过本机 WebSocket 通信。

<TechGraph src="/images/posts/qwen38-omni-声音和画面怎样被训练成agent的行动能力/g06-async-harness.svg" title="ASYNC EXECUTION" caption="图解：前台实时应答与后台任务事件分开运行（博主自绘，基于原论文 Section 7.3 及固定代码快照）" />

前台接到复杂任务，可以先确认收到，再通过统一适配器交给 Qwen Code、Codex、Claude Code 等后台；后台异步回传进度、权限请求和最终结果，前台把这些事件注入上下文，在合适的时机播报。一次语音回答不必一直等到编译、研究或文件编辑全部完成。

这和训练主线直接相关：Thinker 得分清“任务已接收”“正在执行”“执行结束”和“结果有效”。把第一种当成最后一种，后台即使运行正确，用户也会被误导。报告的执行结果奖励给了这种区分一个训练方向，harness 则要用任务身份、状态和回流规则把它落地。打断前台讲话和取消后台工作也要分开，用户打断语音可能只是想补一句条件，报告明确后台可以独立于当前说话和通话状态继续运行；具体取消语义要看所选后端的实现，不能从麦克风或播放状态去推断任务的生命周期。

Proactive 用独立的监视 session 检查音频、画面或时间条件，生成文本事件交给前台，再用 cooldown 避免重复触发；固定文档里 Monitor 按 1 FPS、每轮 2 秒观察，这是长期运行的工作流，和前面的一次性延迟 benchmark 不是一回事。Memory 保存对话、working memory 和用户事实，支持检索和可选的视觉观察；文档区分了本地记忆库与云端整理、向量化，数据文件在本机不代表推理离线，也区分了 On Demand 的单次截图分析和 Live Feed 的持续输入。

这些入口同样只做了静态检查，没有安装框架、接入 API 或运行后台任务。开源的是周边工作流和 harness，Omni 的训练权重、训练集和训练代码并没有随之公开。

## 给做多模态 Agent 的人

回头看，这份报告给出了一条前后衔接的路线：三路编码器留下不同信号，时间表示让它们能被关联和回查，混合骨干兼顾历史压缩与具体取证，四阶段预训练先解决表示、再适应稀疏访问，多教师轨迹和统一 RL 把能力组织成一个用执行结果约束的策略，Talker 和 harness 再把策略接到用户听得到、工具做得到的地方。实验支持其中几个关键环节，也留下了普通 ASR 与语音交互的退步、token 减少不等于端到端提速这些反例。

落到实现上，可以先做这几件事：

1. **给媒体片段稳定的时间地址。** 原视频时间、片段起点和采样时间要能互相换算，模型输出的每个引用都能回到原证据。
2. **用执行结果判定任务完成。** 检查文件、程序和工具的实际产出，不采信模型自报的“已完成”，训练和评测都用同一套标准。
3. **做同任务、多模态的一致性测试。** 同一任务准备文本、音频和音视频版本，比较理解、取证、工具调用和产物，再拉长到多轮看约束会不会丢。
4. **先粗后细地读长媒体，并留下读取记录。** 保存片段地址、工具结果和失败状态，方便出错时定位是没找到证据还是用错了证据。
5. **把任务状态和说话状态分开。** 前台打断不等于后台取消，“已接收”也不等于“已完成”。
6. **延迟按完整链路测。** 厂商表格的计时从 commit 开始，自己的产品要把 VAD、上传、缓冲和播放都算进去。
