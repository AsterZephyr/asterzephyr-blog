评价一个模型时，有一种变化很难用“回答更聪明了”来描述：它在复杂界面里找按钮更稳了，操作专业软件时少走弯路了，生成的东西也更接近可以直接使用的成果。

本文的起点就是这样一个实测观察：GPT-6 的视觉、专业软件和电脑操作能力似乎更强了。这种感觉，能否从 OpenAI 并排展示的 Agents’ Last Exam、ScreenSpot-Pro、OSWorld 2.0 三项评测里找到解释？

我的判断是：**它们确实提供了互补的线索，但要看清这些线索，必须跟着一项工作从输入走到交付。** 单独看三个涨了多少分的柱子，容易把“看到”“做到”和“做对”混成同一件事。

我们就沿着一项具体工作往下走：给 agent 一张工程图和一张参考图片，让它在 FreeCAD 里重建一个支撑零件，最后提交 STEP 模型。这是 OSWorld 2.0 的真实 Task 103。它足够具体，也恰好包含了用户感受到的几种能力：读图、找控件、操作软件、写代码、检查结果。

ScreenSpot-Pro 会帮助我们理解其中的界面定位；OSWorld 2.0 让我们观察整条操作过程；ALE 则把目光进一步移到专业成果怎样验收。后文还会用 ALE 的制造与动画案例检验这条主线能否推广。**这些是不同论文中的独立实验，并不是同一个零件在三项评测里接力完成。**

这里的当前模型是 **GPT-6 Astra**，主要对照是 **GPT-5.6 Sol**。成绩取自 OpenAI 发布页，任务与评测定义来自原论文和官方项目资料，检索截至 2026 年 9 月 13 日。原论文的旧模型轨迹用于拆解任务，不能当成 Astra 的运行记录。

## 先把任务摆在桌面上：从一张图到一个零件

Task 103 开始时，FreeCAD 里没有现成模型。桌面上有 `drawing.pdf` 和 `ref.jpg`，用户只描述了要交出的东西，没有告诉 agent 使用哪个工作台、先创建哪个实体、怎样组合布尔运算。[来源：OSWorld 2.0，Appendix H.1.2](https://arxiv.org/html/2606.29537v2)

<Figure src="/images/posts/gpt6-专业软件能力与三个基准测试/freecad-drawing.png" alt="OSWorld 2.0 Task 103 中的工程图，包含投影视图、尺寸标注与技术要求" caption="来源：OSWorld 2.0，Figure 27，PDF 第 48 页；第 58 步查看工程图，忠实裁剪。" />

工程图上的线条没有自动变成软件里的对象。agent 必须先判断：哪个轮廓是底板，哪个圆表示孔，哪条尺寸线约束哪个特征；多个投影视图说的是同一个零件的不同侧面，不能分别画成几个互不关联的形状。图中的技术要求也需要进入后续建模，而不是读过一遍就算完成。

接下来它才有资格决定操作：底板如何建立，孔怎样排列，主体圆柱怎样与支撑壁连接，哪些地方需要切除。再往后，模型必须被检查、修改、导出。即使前面都做得差不多，最后导出的文件也可能不是最新版本，或者只是一个轮廓相似、关键尺寸不对的零件。

这条工作线可以拆成六次转换：**要求变成约束，约束变成操作，操作改变软件状态，状态形成几何，几何接受检查，检查通过后成为交付物。** 每次转换都有自己可能丢失的信息。

## 第一段：读懂要求，还要把它落到正确的位置

回到空白的 FreeCAD。假设 agent 已经决定要打开某个操作面板，接下来遇到的就是一个很小、却非常实际的问题：那个入口现在在哪里？

知道软件具备某个功能，知道这个功能该在什么时候用，知道它在当前界面中的坐标，是三个不同判断。前两个判断完全可以正确，第三个仍然出错。尤其在专业软件里，同一块屏幕上可能同时有对象树、属性面板、工作台、控制台和绘图区；相邻图标可能只差一条线，却触发不同操作。

### ScreenSpot-Pro 的一题到底怎样运行

ScreenSpot-Pro 把这一步单独拿出来：给出完整截图与自然语言指令，要求模型输出目标位置。评测者预先用专家标注框圈出可交互区域，预测点落入框内就算正确；如果模型输出框，就取框的中心点。定位完成后，这道题便结束了，并不继续点击或检查操作结果。[来源：ScreenSpot-Pro，§3、§5](https://arxiv.org/html/2504.07981v1)

论文收集了 1,581 条指令及对应截图，来自 23 个应用和三类操作系统通用场景。这里保留完整高分辨率桌面的意义很大：如果先把正确面板裁出来，模型已经免费获得了“去哪里找”的答案；如果提供几个候选按钮，它又不必自己生成精确位置。ScreenSpot-Pro 希望把这两部分困难留在测试里。

下面是原论文的 Blender 例子：要求改变物体的坐标模式。它不要求模型生成三维作品，只要求把一句指令准确对应到界面中的一个控件。

<Figure src="/images/posts/gpt6-专业软件能力与三个基准测试/screenspot-blender.png" alt="ScreenSpot-Pro 的 Blender 坐标模式定位样例，论文用局部放大展示细小目标" caption="来源：ScreenSpot-Pro，Figure 5 的 Blender 子图，PDF 第 15 页；忠实裁剪，放大框与标记均来自原论文。" />

读这张图时，可以先找大区域，再找局部入口。对人来说，工具栏的位置、相邻控件以及当前编辑状态，都会缩小搜索范围。对模型来说，如果一开始把指令对应到了错误面板，后续坐标再精细也没有用；如果找对了面板，却把结果落在旁边的按钮上，同样不得分。

这也是为什么“能描述这张截图”并不能替代 GUI grounding。Grounding 在这里可以理解为：把语言中的操作对象，落实到此时此地一个可执行的位置。描述画面允许概括，操作却要求落点。

### 目标只占屏幕 0.07%，小到什么程度

论文中的目标平均占整张截图面积的 **0.07%**。为了形成直觉，做一个单独的尺寸换算：假设屏幕为 3840×2160，面积的 0.07% 约为 5806 像素；若目标近似正方形，边长只有约 76 像素。再把整张图等比例缩到 1280×720，这个目标就只有约 25 像素宽。

这只是用论文比例构造的教学例子，实际目标不一定是正方形，Astra 的图像预处理也没有由此得到说明。但它指出了一个具体矛盾：模型需要全局上下文来选对面板，又需要足够局部细节来区分小图标。只保留整体，容易丢细节；盲目放大一个错误区域，又会失去找到目标的机会。

原论文专门尝试了这种取舍。ScreenSeekeR 先让一个较强的规划模型推断目标可能出现的区域，并利用邻近控件帮助搜索，再逐层缩小范围，交给定位模型判断，最后复核。它还会扩大过小的候选框，减少把目标裁掉的风险。这个旧方法让 OS-Atlas-7B 从 18.9% 提高到 48.1%，没有额外训练。[来源：ScreenSpot-Pro，§4.2、§5.3](https://arxiv.org/html/2504.07981v1)

这项实验值得保留，不是为了把旧模型放进当前榜单，而是因为它把瓶颈拆开了：**界面知识可以帮助选择搜索区域，局部视觉处理负责精确落点，两者的配合会改变定位结果。** Astra 的 92.7% 被标为 `no tools`，不能因此说它内部也运行了 ScreenSeekeR。

### 92.7% 与使用体感最直接的连接

从 76.9% 到 92.7%，是提高 15.8 个百分点。换成错误率，则是 23.1% 降到 7.3%，相对下降约 **68.4%**。它只指这套定位题中的错误，不是所有视觉错误的下降幅度。

现在把它放回建模工作里：一次误点可能只是没反应，也可能选中错误对象、改变工作台、弹出另一个对话框。后者会连带改变下一次看到的屏幕，agent 得先识别误操作，再回到原状态。定位改善因而可能节省一段恢复过程，而不仅仅少错一个坐标。

但模型即使每次都点对，也可能把圆柱建成错误直径。ScreenSpot-Pro 为“更会在专业界面上找东西”提供了直接证据；对于“看懂工程图、完成正确建模”，我们还需要继续往下走。

## 第二段：从尺寸到几何，专业理解在哪里发挥作用

工程图并不是一组等着抄进输入框的数字。必须先把数字与它约束的对象建立关系，才能生成正确几何。

OSWorld 的 FreeCAD 轨迹里，第 58 步读取工程图，第 94 步查看俯视投影，涉及安装孔、小孔、沉孔与中心孔等信息；这些都要成为后续脚本的参数。论文的分析明确指出，失败不只是没看清数字，而是没有稳定保持“特征—尺寸—几何原语—检查”的对应关系。[来源：OSWorld 2.0，§4.4、Appendix H.1.2](https://arxiv.org/html/2606.29537v2)

### 一个数抄对了，几何仍然可以错

用一个**不属于 Task 103 的简化教学例子**，把这句话展开。假设图纸要求一个外径 40 mm、壁厚 4 mm、高 30 mm 的空心圆柱，我们准备通过“外圆柱减内圆柱”来生成它。

第一步，识别 `40 mm` 表示直径，转换成外半径 20 mm；第二步，从半径上减去壁厚，得到内半径 16 mm；第三步，以相同轴线建立两个圆柱，并做布尔相减。内径应为 32 mm，因为壁厚同时占据了左右两侧。

这里已经出现了几种不同的错误：把直径 40 直接传给半径参数，模型会大一倍；把内径算成 40−4=36，壁厚会变成 2；两个圆柱的坐标轴没对齐，差集会形成偏心孔。每一种错误都可能产生能显示、能保存的合法几何，也不要求发生任何误点。

<TechGraph src="/images/posts/gpt6-专业软件能力与三个基准测试/constraint-to-geometry.svg" title="同一条尺寸要求，怎样穿过读图、建模和检查" caption="图解：外径 40 mm、壁厚 4 mm、高 30 mm 的空心圆柱（博主自绘的教学例子，不是 Task 103 图纸参数）。同一组约束既用于生成，也用于检查结果。" />

这说明专业视觉理解至少包含两步：读到一个符号，然后确定它在任务里的含义。单纯 OCR 读出了“40”，并没有回答这是半径、直径、孔距还是总长度。即使语义正确，几何 API 的参数形式也可能不同，还要再转换一次。

更难的是多个视图之间的对应。俯视图里的圆、主视图里的矩形轮廓，可能来自同一个圆柱；某一视图中重叠的边，在三维空间里却属于前后不同位置。如果每个局部都看起来合理，却没保持它们属于同一对象，最终模型就会在整体关系上出错。

### 好的中间状态应当保留什么

继续使用教学圆柱，一个有用的中间记录至少要把几件事连在一起：图纸原始要求是外径 40；代码输入采用半径，因此填 20；当前生成的对象是外圆柱；最后检查要回到外径 40，而不是只检查脚本有没有报错。

关键在于，**检查目标来自原要求，而不是来自已经生成的代码。** 如果代码一开始错误地写成半径 40，再检查“对象半径是否等于代码中的 40”，这个检查会成功，却无法发现任务做错了。

这也解释了为什么更强的专业软件能力未必表现为学会更多快捷键。它可能表现为能在文字、图像、参数、对象和检查结果之间维持一致关系。对电子表格，这种关系是业务含义与单元格公式；对视频，它是参考动作与时间线；对 CAD，它是尺寸与几何。软件变了，信息传递不能走样这个要求没有变。

## 第三段：选择 GUI 还是代码，决定了怎样把约束变成操作

读懂零件以后，agent 仍有一个没有被用户规定的选择：按界面里的建模工具逐步操作，还是写脚本生成几何？

Task 103 的第 76 步选择了 FreeCAD Python console。论文随后记录了脚本执行、观察模型、再次修改脚本和导出。采用代码并不意味着绕开任务：需要交付的是正确模型，程序化建模是软件允许的路径之一。

两条路径各有负担。沿 GUI 操作，必须管理当前选择、工作台、对话框与对象依赖；写脚本，可以把重复结构和数值参数表达得更紧凑，但需要知道 API、对象命名与几何运算，也需要处理脚本失败。选了代码以后，视觉工作没有消失：输入依然来自工程图，输出仍然需要与参考比较。

如果把“CUA 更强”理解成只用鼠标完成越来越多事情，就会漏掉这里最有价值的一部分。一个能灵活工作的 agent，可能用视觉读取目标，用代码构建精确结构，再用软件打开最终成果进行检查。真正需要评价的是这套组合有没有忠实实现用户要求。

### 更快地修改底层文件，也可能更快地做错

OSWorld 2.0 的旧模型轨迹提供了一个有用反例。Task 035 要处理采购信息并更新工作簿；论文记录到，一条轨迹直接修改工作簿 XML，却覆盖了应保护的行，而不是按要求追加获批采购。另一类轨迹更贴近 GUI，保留了工作簿结构，却仍可能遗漏后来出现的审批信息。[来源：OSWorld 2.0，§4.4、Appendix H.2.2](https://arxiv.org/html/2606.29537v2)

这两种失败说明，工具的快慢与方法的正确性必须一起看。直接修改文件可以很有效率，但要知道哪些结构必须保留；手动操作可以避免某些底层破坏，但不会自动保证读全了业务规则。用什么工具，并不能单独决定成果好坏。

映射回我们的零件，脚本可以一次生成全部孔位，也可以一次把全部孔位生成错。如果模型对图纸的解释没有改善，只是代码执行更快，那么错误成果也会更快出现。因此，OSWorld 和 ALE 的分数包含了**选择方法、调用工具和理解领域要求的联合表现**，不能全部归给界面定位。

ALE 的原始失败分析也支持这个区分：在 Claude Code 搭配 Opus 4.7 的特定可分类失败集合里，Approach 与 Understanding 占多数，纯 GUI interaction failures 占 4%。这是旧模型和特定分母下的观察，不是 Astra 的失败构成；它提示我们，很多专业任务早已卡在“路线选错或要求理解错”，而不是“按钮点不到”。[来源：ALE，Appendix D.3](https://arxiv.org/html/2606.05405v2)

## 第四段：为什么做了 202 步，最后仍只有 0.35 分

现在沿着 Task 103 的真实轨迹走完剩下的路。下表按步骤编号排列，只保留论文展示的关键节点，中间没有公开展示的动作不作补写。

<div className="benchmark-table">

| 步骤 | 论文报告的动作或状态 | 这一刻还没有解决什么 |
|---|---|---|
| 1 | 面对空白 FreeCAD 会话 | 建模路线尚未决定 |
| 58 | 查看工程图和技术要求 | 要把二维信息落实到三维结构 |
| 76 | 选择 Python console 建模 | 需要正确参数与 API 表达 |
| 94 | 提取俯视图中的孔位和尺寸信息 | 要与前面的几何关系保持一致 |
| 126 | 首版模型已经可辨认 | 支撑壁与圆柱比例仍需调整 |
| 173 | 两次脚本重写后再次检查 | 修改了比例，仍需确认几何正确 |
| 200 | 导出 STEP，确认文件存在并查看正视图 | 关键几何仍未满足隐藏参考 |

</div>

整条轨迹共 202 步。第 126 步之后，并非直接宣布完成；模型确实进行了修改。到第 173 步，圆柱外径和支撑壁曲线已被调整。最终模型的部分孔与整体边界尺寸大致正确，但主圆柱直径和 U 形槽仍偏离参考，所以只获得 0.35 的部分分。[来源：OSWorld 2.0，Appendix H.1.2，PDF 第 47–50 页](https://arxiv.org/html/2606.29537v2)

这里最值得细读的不是“它失败了”，而是**它已经做了许多通常被当成能力证明的动作**：看图、写程序、生成三维对象、对照参考、发现比例问题、修改、导出。问题出在这些动作之间的传递，没有一直收敛到正确约束。

### 观察、发现、修复、验证，是四件事

“又看了一次结果”只证明获得了新观察。“发现圆柱太粗”意味着观察转成了诊断。接下来还需要找出哪个参数导致偏差，修改相应对象，并确认其他已经正确的结构没有因此被破坏。最后要用原始要求复查新结果，才能说这次修复生效。

如果观察之后只写一句“需要更像参考”，它还没有形成可执行修改。如果修改只靠视觉比例，可能改善整体观感，却没有逼近确切尺寸。如果导出的仍是修改前对象，屏幕上看起来已经修好，交付物仍是旧版本。

后两种是从工作过程推导出的可能错误，不是对 Task 103 未公开步骤的补写。它们帮助解释：为什么一次完整的检查应同时联系输入要求、当前对象、修改动作和实际提交文件，而不能只增加“检查一下”的提示。

### 长任务不是把短任务简单重复很多次

OSWorld 2.0 的完整集合包含 108 个长工作流，平均每题 27.25 个评分检查点。它按最终环境状态和成果评分，允许不同有效路径，不规定必须复现某一串点击。[来源：OSWorld 2.0，§2.1.3](https://arxiv.org/html/2606.29537v2)

这使它能够区分两类行为：做了很多动作，与持续向完整目标推进。Task 103 即使主要围绕一个专业软件展开，也会经历读图、选择表示、写代码、比较结果和修复等不同阶段。后一个阶段需要继承前一个阶段的准确结论，步数越多，早期信息越容易在后面丢失。

有些任务还会改变正确答案本身。Task 035 中，新的 TeamChat 消息会覆盖此前规则，后续纠正又改变预算和供应商约束。最初判断正确，后来也可能过期。agent 必须更新工作状态，并修复已经依据旧规则写入的内容。[来源：OSWorld 2.0，§4.4](https://arxiv.org/html/2606.29537v2)

另一种“过期”发生得更快：Task 052 的促销弹窗不断移动。模型在截图上认对了关闭按钮，但思考结束后，按钮已经不在那个坐标上。这里缺的不是对静态截图的理解，而是观察与执行之间的时效性。

这两个短例放在 FreeCAD 旁边，能把“状态”说得更完整：既有零件尺寸与对象关系这样的持久状态，也有刚到达的新要求，还有随时间变化的界面位置。更好的静态视觉只是其中一部分。

### 72.6% 究竟意味着什么

OSWorld 的部分得分反映检查要求被满足的程度；完整通过则要求部分分达到 1.00。假设两道题，每题四项等权检查，模型都做对三项，那么平均部分分是 75%，完整通过率却是 0%。

<TechGraph src="/images/posts/gpt6-专业软件能力与三个基准测试/partial-vs-complete.svg" title="平均部分得分与完整通过率" caption="图解：两项任务各满足四项检查中的三项（博主自绘，基于 OSWorld 2.0 指标定义）。四项等权检查是教学假设，不是实际题目或模型成绩。" />

部分分仍然有价值：它让“几乎没有进展”和“已经做对大半”不再都显示为失败。但从使用者角度，最后没做对的那一项可能正是圆柱直径、必须保留的公式或审批条件；它会决定你能否直接接收成果。

OpenAI 的 Astra 72.6% 属于 **v2026.08.08 的离线子集部分得分**。官方项目页的离线子集含 82 个无需互联网运行的任务；离线不表示静态截图，也不表示不操作真实软件。[来源：OSWorld 官方榜单](https://osworld-v2.xlang.ai/)

本次查询中，榜单尚未显示 Astra 行，Sol 的最高离线部分得分为 64.1%，而 OpenAI 发布页是 65.7%。差异原因未确认，所以本文采用发布页内部对照，保留这处不一致。我们可以说发布方报告了更高的任务部分得分，不能把 72.6% 写成“七成任务完整交付”。

## 第五段：导出文件之后，专业验收才真正开始

走到这里，支撑零件已经被保存成 STEP。对一个只检查“有没有文件”的任务，它可能已经成功；对需要拿这个零件继续设计或加工的人，文件存在只是入口。

ALE 把大量专业工作组织成这样的验收问题。一次任务有明确说明、输入资产、装有软件的环境、输出要求，以及对执行者隐藏的参考。agent 可以混用 GUI、shell、文件操作和 API。评测最后读取成果，而不是仅根据 agent 的完成声明打分。[来源：ALE，§2–4](https://arxiv.org/html/2606.05405v2)

它覆盖 55 个子领域。这个覆盖范围的意义，在于要求变化很大：几何任务检查空间结构，仿真任务检查数值，动画任务检查时间与动作，表格任务检查字段和公式。专业能力最终必须落在具体对象的正确性上。

### 给几何成果打分，怎样避免“外观接近就算对”

ALE 的一个制造任务采用 `gate-and-score`：先检查硬条件，再计算质量。论文里的 PowerMill 加工任务要求先通过碰撞与过切检查；如果这道门没通过，几何再相似也不给分。通过后，再比较结果与参考 STL 的表面距离。[来源：ALE，Appendix C.3.2–C.3.3](https://arxiv.org/html/2606.05405v2)

这里的逻辑可以与 FreeCAD 零件联系起来理解，但二者不是同一题、也不共用这套评分。它说明专业验收可能同时包含“不可违反的条件”和“可以逐渐改善的质量”。前者决定结果是否有资格被接受，后者才衡量接近目标的程度。

论文给出的几何评分例子是：处在 0.3 mm 距离阈值内的表面采样比例占 70% 权重，处在 2.0 mm 阈值内的比例占 30% 权重。若另设一份教学结果，两个比例分别为 0.64 和 0.94，那么通过硬门槛后的得分为：

**0.70 × 0.64 + 0.30 × 0.94 = 0.73。**

其中两个比例是教学假设，权重与阈值来自论文。这个算式解释了为什么可以同时关注精细贴合和粗略轮廓：非常接近的部分进入两个阈值统计，偏差稍大的部分只可能进入宽阈值统计。若碰撞门槛失败，这个 0.73 则没有资格成为最终成绩。

<TechGraph src="/images/posts/gpt6-专业软件能力与三个基准测试/artifact-acceptance.svg" title="专业验收：先过必要条件，再比较质量" caption="图解：交付完整性、硬性条件与质量评分（博主自绘，基于 ALE §3.3、Appendix C.3）。这是概念示意，各任务的门槛、评分函数和权重不同。" />

这比“看着挺像”更严格，也更能解释近乎正确的成果为什么仍不好用。一个模型可能已经学会生成总体形状，却还无法让所有必要条件同时成立；另一个模型则可能在大部分任务里把最后几个关键细节补齐。相同的平均分增量，可能对应很不同的实用性改善，需要逐题结果才能区分。

### 仿真案例：JSON 填满，不等于求解完成

ALE 的 Moldex3D 任务沿着另一种专业对象继续检验这个问题。输入包含已有网格和材料的项目、工艺配置 `process_spec.json`，以及规定结果字段的模板。任务要求运行填充、保压、冷却和翘曲分析，提交保存后的工程及 `results.json`，包含压力、锁模力、时间、体积、重量等求解器结果。[来源：ALE，Appendix B.3.1，Task Card 1](https://arxiv.org/html/2606.05405v2)

评分首先拒绝缺失、格式损坏或全为空的结果文件，再把数值与隐藏求解参考比较，主要字段采用 1% 的相对容差。要求不是“写一个格式正确的 JSON”，而是“把这次配置真正求解出来的数值放进 JSON”。

论文展示的 Opus 4.7 轨迹确实走到了正确设置界面，也交出了结果文件，但只得到 0.4762。任务卡指出，一些值来自估计，没有可靠地从完成后的求解输出中提取。

这让验收链多了一个很重要的维度：**结果的来源关系。** 字段完整可以通过格式检查，数字看起来合理可以骗过粗略阅读，但它们仍可能没有对应这次输入、这次工艺和这次求解。正确的后续动作应包括确认结果文件已产生、读取或导出求解数据，再填入交付文件。

若在实际使用中，Astra 更少用“合理估计”填补工具执行留下的空白，更经常等到真实结果并回读，那么体感会非常明显。ALE 的整体提升与这种变化相容，但当前总分不能证明 Astra 在这道 Moldex3D 题上正是这样进步的。

### 动画案例：一帧好看，不等于整个作品正确

ALE 的另一个任务要求在 Blender 中给静态角色绑定骨骼、复现参考视频的身体动作，使用规定的 19 个骨骼名称，同时提交可编辑的 `final.blend` 和可播放的 `preview.mp4`。评分会看视频匹配、从工程重放的一致性、骨骼覆盖以及针对性的视觉检查。[来源：ALE，Appendix B.3.1，Task Card 4](https://arxiv.org/html/2606.05405v2)

论文里的提交两种文件都有，也包含动画，但约 13.6 秒的参考动作被做成约 4 秒的预览，动作幅度还被压低以减少网格变形。最终得分为 0.4285。

一张渲染图很难暴露这类问题。它可以显示角色存在、材质正常、姿势像样，却不能说明动作持续时间、完整姿态范围以及工程能否重放出同样视频。专业视觉任务中的“看对”，有时要求沿时间观察，而不只是检查一个静态画面。

这也补充了用户提到的视觉能力：界面定位是视觉，工程图的空间关系是视觉，参考动画的时间关系也是视觉。三个 benchmark 恰好触及其中不同部分，但 ScreenSpot-Pro 的 92.7% 只直接回答第一种。

### 59.3% 为什么不能翻译成“能做六成职业工作”

ALE 的原论文同时报告细粒度平均得分与完整通过率，并存在不同难度集合。工作流、实例、领域之间也有聚合结构。它报告的 960 个工作流、1490 个实例包含仍在质量控制中的样本，不能直接当作 Astra 本次评测的题数。[来源：ALE，§2、§4、Appendix C](https://arxiv.org/html/2606.05405v2)

本文把发布页的 59.3% 保留为专业任务评分，因为当前未取得 Astra 本次精确 split、样本数、重复次数与评分聚合的完整说明。它支持“这组专业任务上的表现提高”，却不支持按现实职业人口或全部工作时长去乘一个 59.3%。

评分方法本身也不是所有任务都靠代码。ALE 优先采用能执行的检查；对难以完全形式化的视觉与创意任务，也会使用固定问题和 rubric 的模型裁判。因此，判断可信度时要看某道题究竟检查了什么，而不是只听到“自动评分”四个字。

## 第六段：把三个提升放回这条工作线

现在可以回到最初的问题了：为什么这三项 benchmark 可能比一个通用问答分数，更能解释“GPT-6 突然更会用专业软件”的感觉？

因为它们把模型放到了不同的失败现场。ScreenSpot-Pro 检查指令是否准确落在界面上；OSWorld 检查一连串操作之后，任务要求究竟保留了多少；ALE 检查产物是否能承受更具体的专业验收。

把支撑零件再走一遍：定位改善可能让控制台和参数入口更容易找到；图纸理解与方法选择改善，才可能让直径、孔距与布尔关系进入正确参数；状态保持改善，才可能让这些关系经过上百步仍未丢失；检查与修复改善，才可能把“可辨认的支撑件”继续推向“符合要求的模型”。

后三项能力没有在发布页里各自分离成一个分数，OSWorld 与 ALE 给出的是它们混合后的任务表现。因此，这是一条解释体感的路径，不是一份已经确认的能力归因表。

### 小错误为什么会带来大返工

在单题定位里，错一次只是 0 分；在工作流里，错一次可能改变后续环境。点错对象后设置参数，设置再准确也作用在错误对象上；读错直径后编写脚本，后续大量代码都可能围绕这个错误组织；忘记最新审批后完成整张表，交付前就需要找回并重算受影响内容。

所以，某些局部改善会减少后续分支上的工作。它们不一定体现为 agent 更会解释自己的计划，反而可能体现为过程更短、撤销更少、人工介入更少。这是从任务依赖关系出发的推论。

不过，不能把 ScreenSpot-Pro 的 92.7% 当成每一步独立成功概率，再连续相乘，去预测 OSWorld 通过率。真实操作并不独立：有些错误会放大，有些能被恢复，有些步骤根本不涉及 GUI。用一个定位平均值覆盖整个流程，反而会抹掉我们刚刚拆出的差别。

### 进步也可能集中在“最后一点没做对”

FreeCAD 案例让人看到另一种可能：模型已经能完成大部分显眼动作，真正缺的是把结果收敛到精确要求。ALE 的动画与仿真也一样，文件都在，结构也像，最后却差在时间、动作幅度或数值来源。

如果新模型改善的恰好是这些环节，使用者会觉得从“需要我重做”变成“稍作检查就能接收”。这种体感的幅度，未必与平均分增加的百分点相等。但是否真的发生了这样的分布变化，必须看新旧模型相同题目的产物、完整通过率和人工修改量；当前 headline 分数还没有把它证明出来。

这比笼统称赞“更强的 agentic 能力”更具体：我们关心它有没有更准确地保存要求、更合理地选方法、更有效地让检查改变结果。

## 最后再读成本曲线：更准、更快、更省不是同一个结论

用户截图的横轴是 API Cost，这个信息不能略过。ScreenSpot-Pro 中，Astra 的点更高，也更靠右；至少在图中这些配置上，单次定位准确率提高伴随更高 API 成本。不能把三张图统一概括为全面降价。

OSWorld 的工作流成本则有不同含义：一次定位便宜，不代表完成整个任务便宜。若需要更多截图、重试、回退和最终修复，调用会继续累积。反过来，单次调用贵一些，也可能通过减少返工降低任务总成本。要判断哪一种发生了，应比较相同验收目标下的整项任务，而不是把两个测试的横轴直接拼在一起。

时间同样需要拆开。OpenAI 报告的 OSWorld 对比来自 **latency simulations**，约为 Astra 40 分钟/任务、Sol 75 分钟/任务。它是效率线索，但不是用户桌面上的实测耗时。等待应用响应、求解器运行、文件导出、网络服务与人工介入，都可能影响实际端到端时间。[来源：OpenAI 发布页，Computer use](https://openai.com/index/gpt-6-astra/)

对前面的零件，最有意义的比较应该是：同一份图纸、相同工具、相同预算，两者最后提交的 STEP 是否合格，过程中用了多少时间与费用，又需要人修正多少次。只比较“首次生成一个模型有多快”，会漏掉最费人的收尾工作。

## 我会怎样理解这次能力变化

你提出的直觉有一个很好的切入点：这三个测试都把模型带离了纯文字回答，要求它接触界面、改变环境或交出专业成果。它们确实比一个泛化的“智力涨了多少”更接近专业软件的使用体验。

其中，**高分辨率界面定位改善的证据最直接**；长流程和专业任务分数则提供了更接近实际交付的互补证据。我们沿着工程图到 STEP 的过程，已经能明确指出：这类进步可能发生在定位、表示转换、方法选择、状态保持和验收修复中的什么位置。

对于“审美更好”，还需要另一种验证。能按参考重现动画、读准工程图、找到排版控件，都不等于能在开放需求中选择更好的构图、配色和节奏。约束下的忠实复现与开放式设计判断有联系，但不能相互代替。

目前公开材料也不足以把三项提升归因于某一种训练方法，或证明全部实测体感都由它们解释。把 benchmark 当成观察窗口比较合适：它们让我们看到了更准确的定位、更高的任务得分，却仍需要逐题轨迹才能看清中间究竟发生了什么。

如果接着做个人实测，我会留下同一份输入、操作记录和最终产物，先写清验收要求，再比较模型。以那个支撑零件为例，第一眼像不像只是开始；接下来要查关键尺寸、几何关系、导出文件以及修改次数。沿着这条线，才能把“这次感觉更强”进一步说成：**它在哪一次信息转换中少犯了错，又因此让哪一段工作真正省了下来。**
