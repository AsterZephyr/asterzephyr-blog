一段会议录像：屏幕上是季度预算表，主持人说“按第二版推进”，旁边有人插了一句“等等，第二版还没批”。如果任务是把预算表转成电子表格，证据全在画面里；如果任务是判断会议最终通过了哪一版，那句插话、谁先谁后、说话时屏幕停在哪一页，都可能改变答案。两个任务装在同一个视频文件里，需要的却是不同的证据。

读完 Qwen3.8-Omni 的技术报告，很自然会冒出一个问题：Qwen3.8-Max 已经能理解图片、文档和视频，还能操作界面、写代码，为什么还要一个 Omni？

两边公开的深度并不对等：[Qwen3.8-Max 官方发布文](https://qwen.ai/blog?id=qwen3.8)主要讲工作流、训练系统思路和评测，[Qwen3.8-Omni 技术报告](https://arxiv.org/abs/2609.25611)则给出了感知编码、预训练和实时系统的细节。官方接口文档以 2026 年 10 月 1 日的版本为准。

## 两个模型，三个入口

当前官方视觉模型文档里，`qwen3.8-max` 的输入是文本、图像和视频，输出是文本；同一页明确提示，需要理解视频里的声音或直接输入音频时，改用 `qwen3.8-omni-flash`，它同样输出文本。实时语音和视频会话则对应第三个入口 `qwen3.8-omni-flash-realtime`。[来源：视觉模型文档](https://docs.qwencloud.com/developer-guides/getting-started/vision-models)、[语音到语音模型文档](https://docs.qwencloud.com/developer-guides/speech/s2s-models)

| 公开接口 | 关键输入边界 | 输出与交互方式 | 比较时要注意 |
|---|---|---|---|
| Qwen3.8-Max | 文本、图像、视频 | 文本；可调用工具 | 文档没有列出原始音频输入 |
| Qwen3.8-Omni-Flash | 文本及音视频理解，包括声音 | 文本 | “Omni”这个名字不代表这个接口输出语音 |
| Qwen3.8-Omni-Flash-Realtime | 实时音频、图像、视频等 | 实时文本与语音会话 | 报告把它列为 non-thinking，不能套用普通 Flash 的推理设置 |

<TechGraph src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/g01-endpoints.svg" title="ONE FAMILY, DIFFERENT ENDPOINTS" alt="Max、Omni-Flash 和 Omni-Flash-Realtime 三个公开接口的输入输出对照" caption="图解：模型家族与具体接口分开看（博主自绘，基于官方 vision-models、s2s-models 文档，核查于 2026-10-01）" />

这张表回答的是公开产品边界。Max 没列音频输入，证明不了它的内部架构永远不能加音频，也说明不了某个千问产品有没有在后台接语音识别。它能回答的是一个工程问题：如果原始声音是任务必需的证据，就不能把 Max 支持 `video` 当作支持声音。

两个模型的来历也要分开。Max 发布文说它基于 Qwen3.5，扩展到 2.4T 总参数、95B 激活参数；Omni 报告说它的语言骨干继承 Qwen3.8-Next 的稀疏 MoE 路线。公开材料里没有“在 Max 上加个音频头就得到 Omni”的关系，也没有说 Omni 的教师就是 Max。它们同属一个家族、共享部分技术方向，直接继承、蒸馏和权重关系没有证据。[来源：Max 官方发布文引言](https://qwen.ai/blog?id=qwen3.8)、Omni 报告 Section 2，PDF 第 3 页

所以比起排一个“Max 强还是 Omni 强”的序列，更有用的是分别问三个维度：通用任务能力、输入证据范围、运行时交互约束。名字能提示定位，替代不了这三项检查。

## 一段录像里有几种证据

视频容器可以同时装着画面、音轨、字幕和时间信息，但模型最终收到什么，取决于接口、媒体处理和输入组织。只抽帧、抽帧加字幕、保留原始音轨联合输入，得到的是三种不同的观察条件。

画面能告诉模型预算表的列名和金额、被指着的区域、投屏切到了哪一页。字幕能告诉它谁说过什么字。原始声音还带着停顿、重叠发言、语气强调、警报和背景事件；如果录制设备保留了合适的空间通道，声音从哪里来又是另一类信息。

<TechGraph src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/g02-evidence.svg" title="WHAT SURVIVES PREPROCESSING?" alt="会议视频中的画面、转写文本、原始声音和时空关系四类证据" caption="图解：同一段视频包含不同证据，预处理决定哪些信息进入模型（博主自绘，基于 Omni 报告 Section 2；会议为解释性假设场景）" />

把语音先转成文字再交给 Max，是完全合理的方案。如果任务只是提取口述的日期和金额，转写可能就够了。代价在于，后面的模型只能在前面保留下来的东西上判断：一份没有说话人区分、没有时间戳、没有重叠标记的转写，会把“谁打断了谁”“这句话对应哪张投屏”这些关系压平。这种损失靠更长的上下文补不回来，上下文能装下更多已保留的内容，声音若在输入前就被丢了，模型无从知道那里响过警报。同样，把单声道录音复制成多个通道，也恢复不出录制时没有记下的声源方向。

反过来，保留音轨也不是充分条件。各路流是否在同一时间轴上、抽帧是否错过了关键动作、转写是否把否定词听错，都需要检查。原生多模态模型把一部分融合工作放进了模型里，但采集和输入组织仍然决定它能看到、听到什么。

## 在 Qwen3.8-Max 看来：视频是画面、字幕和工作反馈

### 视频怎样进入 Max

Max 发布文对长视频的描述很具体：面对上百小时的视频，它能定位片段、回答细节问题，还能把人物、事件、时间和场景组织成视频 Graph 记忆，在长跨度里建立关联。[来源：Max 官方发布文“多模态智能体”](https://qwen.ai/blog?id=qwen3.8)

评测设置把这条路径交代得更清楚。Max 发布文的多模态结果表里，VideoMME 和 VideoMME v2 标注为 **w/ Sub.**，即启用字幕评估，Max 分别为 90.4 和 68.3；LVBench 与 EgoLife 另有 **w/ Mem.** 一栏，用基于 Qwen-MM-Plugins 构建的记忆系统评估，Max 的 LVBench 从 81.8 到 85.6；VideoDR 标注 **w/ Search**，使用了搜索工具。

这些标注说明，在 Max 的公开评测里，视频里的语言信息主要通过字幕这条文字通道进入，长时间跨度靠 Harness 侧的记忆系统支撑。这是评测配置，不是对 Max 能力上限的断言；但放回那段会议录像，Max 视角下能稳定拿到的是画面、字幕文本，以及记忆工具整理出的事件结构，插话的语气、两人同时开口的重叠，要看前面的转写有没有保留下来。

“上百小时的视频被组织成可检索记忆”和“一次 API 请求塞进上百小时原视频”不是一回事：当前官方文档把 Max 和 Omni-Flash 的视频输入都限定在最长 2 小时、2GB 以内。[来源：视觉模型文档“Video support”](https://docs.qwencloud.com/developer-guides/getting-started/vision-models)

### 视觉不只在输入端

Max 的多模态更关键的一面，是把视觉接到了行动上。发布文强调，模型在执行过程中会持续观察自己的中间产物，检查页面布局、物体方向、空间关系、动画效果和交互结果，发现电视放反、界面错位这类问题后重新规划、自主修正。视觉由此从“理解输入”变成贯穿规划、执行、验证和迭代的反馈回路。

拿“从一张界面截图复刻应用”来说，第一版产物可能只在颜色和文字上相似。模型打开页面后，还得判断按钮有没有被遮住、窗口缩小时布局会不会挤坏、点击后状态有没有真的变化。代码构造界面，运行中的界面又反过来检验代码。官方把编程与 GUI 操作结合的这条路线叫 Hybrid Agent：编程高效地完成大量工作，GUI 操作把真实运行系统的反馈带回来。

<TechGraph src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/g03-visual-loop.svg" title="VISION INSIDE THE WORK LOOP" alt="目标经过代码或 GUI 执行产生实际结果，Max 观察结果后修正，并由验证器检查完成情况" caption="图解：视觉进入规划、执行与修正循环（博主自绘，基于 Max 官方发布文“多模态智能体”；图中 verifier 为对公开机制的概括）" />

RecreationBench 是这条路线的一个具体任务定义：模型面对没有源码、不能联网的黑盒应用，只能通过交互理解它的行为，再从零复刻，平台覆盖 Ubuntu、macOS、Windows、Android 和 Web。发布文表格里 Max 在这项内部基准上为 51.7。它考的是观察、实现、回看之间的反复循环，和判断一场多人会议里谁先提出异议，需要的证据完全不同。

这里也要区分模型输出和系统产物。Max 的接口输出是文本，它生成代码、工具参数或操作指令，再由工具去渲染页面、生成 Blender 场景、剪辑视频或执行 GUI 操作。端到端能交付这些产物，说明模型和工具链配合得好，不能据此把 Max 的输出类型改写成“原生图像、视频和三维场景”。

### 训练系统要让反馈稳定地起作用

Max 发布文的“办公助手”部分披露了三项相互关联的训练系统设计，它们是并列的三根支柱，不是先后的训练阶段。

**环境按维度组合扩展。** Task 从单任务到多任务、跨天任务；Workspace 从几份文件到层级目录和异构材料；Harness 有不同类别、版本和技能。三者可以组合，环境覆盖随组合增长，不必每多一种情形就从头定制一个完整环境。这对 Agent 训练很实际：同样是“修改报告”，材料在一个文件里、散在多个目录里、还是要用浏览器确认，执行轨迹完全不同；同名工具在不同 Harness 里的反馈格式也可能不一样。模型要学会按当前环境推进工作，而不是记住某条固定的工具序列。

**统一奖励系统承接异构的验证。** 官方列出的信号包括基于执行的校验、对文本和渲染后视觉产物的 rubric 评估，以及 agentic 检查。脚本能不能跑通、文档是否合规、网页在视觉上是否完整，没法用同一条字符串匹配判断。统一的意思是由一个系统来组织这些不同的检查方法，复刻页面要看渲染结果，数据处理要核对计算，标准并没有被合成一个。完整的 verifier 实现和权重没有公开。

**在线数据均衡器重组每个 batch。** 按任务、难度、工作区和 Harness 让 batch 内分布保持均衡，作者的解释是降低 batch 间的梯度方差，让强化学习的训练算力能稳定地继续扩展。如果连续采到一批相近的简单任务，紧接着又突然换成一批复杂的长程任务，训练信号的分布会剧烈摆动，控制混合比例正是把“多环境”变成“稳定训练”的一环。

Max 的工作能力就是这样被训练系统组织起来的。完整 RL 算法、奖励权重、环境规模和训练成本都没有公开，也没有可以拿来和 Omni 对照的感知编码器配置。[来源：Max 官方发布文“办公助手”](https://qwen.ai/blog?id=qwen3.8)

## 在 Qwen3.8-Omni 看来：声音和它发生的时刻

换到 Omni 的视角，同一段录像里多出来的是那条音轨。Omni 报告的架构是：视觉编码器、AuT 音频编码器和 Spatial AuT 空间音频编码器，各自经过 adapter 接入一个共享的 Thinker，文本也进入同一个推理骨干。要解决的首先是表示对齐，让不同输入变成骨干能一起使用的序列，而不是各自先写一段摘要再拼起来。[来源：Omni 报告 Section 2，PDF 第 3-4 页](https://arxiv.org/abs/2609.25611)

### AuT 留下的不只是转写

普通 AuT 路径把音频处理为 16kHz 采样、128 维 Mel 特征，窗口 25ms、步长 10ms；随后四个 Conv2D 模块共做 16 倍下采样，得到约 6.25Hz 的特征序列，Figure 2 里还画出了 32 层 self-attention，最后由 adapter 接到语言骨干。

<Figure src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/p02-audio-encoders.png" alt="Omni 原报告 Figure 2，普通 AuT 与 Spatial AuT 的音频编码路径" caption="来源：Qwen3.8-Omni 原报告 Figure 2，PDF 第 4 页；仅作忠实裁剪" />

这些数字说明声音在进入共享推理之前被压缩过：10ms 是最初的时间分辨率，约 160ms 一个位置是编码器输出的间隔，两者不在同一层。按 6.25Hz 粗算，一分钟声音约对应 375 个该层特征位置；这个数不含视频、文本、空间通道和其他序列开销，也不是接口的计费 token 公式。6.25Hz 更不是播放采样率或响应速度，用户说完话多久能听到回复，还取决于会话提交、模型计算、语音生成、网络和播放缓冲。

AuT 用 ASR 监督训练，但运行时交给 Thinker 的是学到的音频表示，并不是“把声音强制转成的文字”。ASR 目标帮表示学会语言信息，联合感知路径则希望共享模型能利用声音本身，以及声音与画面的关系。具体保留了多少非语言线索，最终要看任务结果。

### 空间声音为什么单独走一条路

Spatial AuT 的输入是 FOA（First-Order Ambisonics）。报告强调对复数 STFT 同时保留实部和虚部，也就是保住幅度和相位信息。普通 Mel 特征适合表达声音内容，替代不了跨通道的空间关系；单独一条空间路径，是为了让模型有机会用上声源方向这类额外证据。

放回会议室，空间信息可能帮助区分是谁在说话，前提是录制条件到位：设备有没有采集 FOA、通道约定对不对、声场是否混杂。模型里有空间编码路径，恢复不了麦克风没记下的数据；报告描述了这条架构，也不等于所有云端音频接口都开放了完整的 FOA 输入。

### 多路输入共用一条时间轴

光把声音 token 和图像 token 放进同一个上下文，并不保证模型知道它们同时发生。会议里，“第二版”可能在投屏切页前说出，也可能在切页后被否决；同一个词出现在不同时刻，任务含义可以完全不同。Omni 报告保留了显式的文本时间戳；空间 token 在同一时间片共享 temporal ID，再用不同的 spatial ID 区分位置，时间和空间关系由此有了表达的位置。

这也给系统设计一个启发：模型提取出的事件，最好能指回原媒体的时间范围，方便之后重新取证。显式时间信息是报告的架构事实，可回查的事件对象则是由此推出的工程建议，报告没有给出；时间戳够不够精确、不同设备的时钟是否一致，仍要在真实输入上测。

### 先学会接入，再学会一起用

Omni 的四阶段预训练顺着这个难点展开。S1 冻结语言骨干，先训 adapter、再训编码器，让各路感知接进既有骨干；S2 解冻全部参数联合训练，让骨干适应共享的多模态输入。S3 保留 dense attention、冻结骨干，只让 QSA indexer 学习完整注意力给出的监督；S4 才开启 QSA，骨干和 indexer 联合训练。先接入、再共同变化，先教索引器挑内容、再让整个模型适应挑选后的计算路径，这是报告披露的顺序，报告没有给出逐项取消的消融。四个预训练阶段都在 262,144 长度上进行，最终的 1M 上下文在后训练之后才扩展。[来源：报告 Section 3，PDF 第 5-6 页](https://arxiv.org/abs/2609.25611)

后训练面对的是另一个问题：音频、视觉、文本、工具和长任务能力要在同一个学生里共存。报告的做法是先训练不同方向的专家教师，各自经过 SFT 和 RL，再把它们的轨迹汇合给单一学生，最后做统一 RL；长任务的奖励看实际执行结果，不看模型自称完成。[来源：报告 Section 4，PDF 第 6 页](https://arxiv.org/abs/2609.25611)

<TechGraph src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/g04-training.svg" title="TWO VIEWS OF AGENT TRAINING" alt="Max 的环境与奖励组织，以及 Omni 的感知接入、稀疏训练和教师轨迹合流" caption="图解：两份公开材料披露的训练重点（博主自绘，基于 Max 官方发布文“办公助手”与 Omni 报告 Sections 3-4；不表示两者使用同一训练配方）" />

把两侧训练放在一起看，差别在公开的重点：Max 披露的是怎样组织环境、反馈和 batch，让工作能力能稳定扩展；Omni 披露的是怎样让多路感知接进同一个骨干，再把多种能力合进一个学生。图上没画的部分不代表模型没有，Max 同样需要输入表示，Omni 同样需要工作环境和结果验证，它的后训练和实验里就有工具、编程和长程任务。所以别把两者简化成“Omni 负责听看、Max 负责思考”。

Omni 这一侧也有缺口：报告没有公开 Thinker 的完整 RL 算法和奖励配比，Talker 最后阶段用的 GSPO 不能拿来填这个空白；视觉编码器的初始化在不同段落写成了 Next 和 Qwen3.5 两种，具体 checkpoint 无法确定。

## 对话变成实时以后

假如那场会议不是录像，而是正在进行的协作。用户说“按第二版准备”，系统已经开始回答，用户又补一句“先别发，改成第三版”。问题不再只是听懂一句话：旧回答要不要停、任务参数要不要更新、已经启动的后台工作怎么处理，都跟着来了。

普通文本接口可以用 `stream=True` 一块块返回文字。实时语音系统则要持续接收输入、提交当前片段、维护会话状态，再边生成边播放声音；官方 Realtime 文档用 WebSocket / WebRTC 会话和 `session.update` 里的 text、audio 输出配置来描述这套机制。两者都叫“流式”，运行语义却不同。[来源：Realtime 多模态语音指南](https://docs.qwencloud.com/developer-guides/speech/realtime-multimodal-speech)

Omni 报告里的 Thinker-Talker 路径分工明确：Thinker 负责理解和文本内容，Talker 用 RVQ 和 MTP 生成声学码，其中 MTP 预测的是**同一音频帧内**剩余的 RVQ codebook，不是对未来多帧音频的预测；因果 Code2Wav 把声学码转成音频，输出扩展到 48kHz；ARIA 让语音基于部分文本前缀就能持续生成，不必等整段回答写完。[来源：报告 Section 7，PDF 第 14-15 页](https://arxiv.org/abs/2609.25611)

<Figure src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/p06-realtime.png" alt="Omni 原报告 Figure 3，实时语音、工具及 Live Harness 相关运行结构" caption="来源：Qwen3.8-Omni 原报告 Figure 3，PDF 第 15 页；仅作忠实裁剪" />

这条路径解释了为什么这个家族能生成语音，但调用时仍要选对接口：普通 Omni-Flash 的音视频理解入口输出文本，只有 Realtime 入口才对应实时语音会话，而它是 non-thinking 版本，不能照搬普通推理模型的长思考预算。

延迟也要拆开读。报告 Table 9 的首文本、首音频计时从 commit 开始，输入上传发生在计时之前，测试关闭了 VAD，也不包含建连和播放端缓冲。它衡量的是指定条件下的生成表现，代表不了“用户开口到后台文件交付”的总时间。真实系统里至少有三种等待：当下说话的回应、拿到足够证据的时间、后台执行完成的时间。把导出文件的几十秒算进语音首包，会混淆执行和交互；把一句即时确认当成任务完成，又会犯相反的错误。

Qwen-Live-Harness 给了一个有用的结构：前台委托任务后立即确认，后台继续执行和监控，完成后再组织反馈，实时交互和长任务不必挤在同一条阻塞路径上。[来源：报告 Section 7.3，PDF 第 16 页](https://arxiv.org/abs/2609.25611)

## 把两个视角接到同一个任务里

假设要做一个会议助手，它既要理解现场讨论，又要整理资料、修改文件、生成页面。一种可行的分工是：需要原始声音的观察和实时会话交给 Omni，后续适合 Max 或其他执行模型的工作交给它们。这是**一种工程设计建议**，官方没有规定 Omni 接 Max 的固定管线，也没有经过 API 实测。

<TechGraph src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/g05-handoff.svg" title="PROPOSED EVIDENCE-PRESERVING HANDOFF" alt="工程建议：实时前台产生带原媒体指针的证据对象，交给可选执行后端，工具结果验证后再反馈" caption="图解：保留原始证据的前后台协作（博主自绘；工程建议，受 Omni 报告 Section 7 与 Max 视觉工作流启发，非官方固定模型组合）" />

### 交接对象要能回到原始证据

前台如果只交出一句“会议决定用第三版”，后台就会把一次感知判断当成已确定的事实，之后想核对谁提出的变更、有没有反对意见、第三版对应哪个文件，都很难重新定位。

更稳妥的交接对象，会同时保留事件标识、发生时间、观察内容、原媒体位置和待确认的问题。示例结构是建议写法，不是官方 API schema；`unresolved` 是系统记录的待核实项，不是模型校准过的概率。

```json
{
  "event_id": "meeting-042-revision-03",
  "time_range_ms": [124000, 130500],
  "observation": "主持人提出改用第三版，并要求暂缓发送",
  "evidence": [
    { "media_id": "meeting-042", "kind": "audio", "start_ms": 124000, "end_ms": 130500 },
    { "media_id": "meeting-042", "kind": "frame", "time_ms": 127000 }
  ],
  "proposed_action": "准备第三版材料，等待发送指令",
  "unresolved": ["第三版对应的文件尚未核实"]
}
```

后台不必全盘接受前台的结论，它拿到的是回查入口：找到第三版文件、核对版本差异，必要时重新取出对应的音频和帧。原媒体指针、摘要和行动建议一起保留，观察和执行才接得上。长视频同理，Max 发布文的视频 Graph 记忆、Omni 报告里按问题逐步检索片段，处理的都是“历史材料怎样继续可用”。Max 发布文也引用了 Qwen-MM-Plugins，它是 Harness 扩展库，不是 Omni 独有的模型结构。[来源：Max 发布文“多模态智能体”](https://qwen.ai/blog?id=qwen3.8)、Omni 报告 Section 5.1，PDF 第 7 页

### 实时修改需要版本和任务状态

用户把第二版改成第三版时，感知侧应产生一个新事件，执行侧要知道自己在准备哪一版。可以把 `task_id`、输入修订号和执行状态放在后台：旧事件被更高修订号取代后，未执行的计划随之更新，已生成的材料重新检查。

停止前台播音和取消后台任务也要分开。用户打断一句解释，可能只是想补充信息；明确取消任务，后台则要确认取消真的生效。“话被打断”“参数被修订”“任务被取消”应是三种不同的状态变化，不能都归成一个 stop。音频事件重发、网络重连、监控轮询，都可能把同一个意图送到后台多次，事件标识和任务状态让系统分得清这是重复通知、任务更新还是新任务。模型负责理解意图，持久状态和幂等执行由 Harness 与工具层承担。

后台宣布完成时，应交出真实产物和验证记录：表格能不能打开、页面是否真的渲染、发送是否成功，是三种不同的检查。前台据此回复用户，而不是凭模型最后一句“已经完成”收尾。

### 很多任务用不着两个模型

识别截图里的表格、调整网页布局、处理已经可靠转写的纯文本材料，从视觉和文本工作流起步就够了；原始声音不影响结果时，多接一条音频路径只会多一个要管的环节。必须区分画外声音、重叠发言、声画关系时，输入就要保留这些证据，Omni 的原声音路径才有明确价值；如果还要求低等待的语音交互，再上 Realtime 会话，把慢的执行委托出去。Omni 自己也能做 Agent 任务，没必要为了架构图好看硬接一个 Max。

这些是基于输入边界的路由原则，不是测出来的性价比排名。选单模型、ASR 加执行模型、原生 Omni 还是前后台组合，要在自己的任务上比较准确性、等待时间、调用成本和失败恢复。

## 公开结果能证明到哪一步

两份材料都有不少评测，但它们凑不成一组条件匹配的 Max 对 Omni 比较。Max 发布文里不少视频任务带字幕、记忆或搜索，各基准的 Harness 和统计口径也不同；Omni 的文本表格主要对照的是 Qwen3.8-Flash，不是 Max，把 Flash 那一列换成 Max，论文的意思就变了。Omni 报告 Table 7 里也有 Video-MME-v2（静态 65.0、Qwen Code 71.3），但它的输入方式和 Max 表中启用字幕的 68.3 不同，放在一起排名没有意义。

更有说服力的是 Omni 报告内部的一组比较：同一个 Omni，用静态输入理解长视频，和通过 Qwen Code 主动取证相比，结果怎样变化。

<Figure src="/images/posts/qwen38-max-与-omni-同一段录像各看到了什么/p03-token-evidence.png" alt="Omni 原报告 Table 8，同一模型在静态输入和 Qwen Code 主动理解设置下的准确率及每查询 token" caption="来源：Qwen3.8-Omni 原报告 Table 8，PDF 第 14 页；仅作忠实裁剪。比较对象是同一 Omni 模型的两种使用方式" />

Table 8 中，OmniVideoBench 准确率从 63.4 升到 67.8，提高 4.4 个百分点；每次查询的 token 从 145,736 降到 79,117，约减少 45.7%，统计保留了跨轮上下文。在这个模型和任务设置下，先组织观察、再按需取证，同时改善了答案质量和输入消耗。它没有测出 Max 比 Omni 好或差，也不说明总延迟或账单会等比例下降：多轮工具调用有媒体处理、请求和执行的开销，不同输入类型的计费也可能不同。

Omni 也不是在所有声音任务上都进步了。Table 4 里，相比表内前代模型，WenetNet 的 WER 从 3.7 变成 4.8，FLEURS 从 7.2 变成 9.3，WER 越低越好。能力覆盖变宽，不保证每一种转写任务都更强；如果需求只是 ASR，应该用自己的语言、噪声和说话条件直接测。[来源：Omni 报告 Table 4，PDF 第 11 页](https://arxiv.org/abs/2609.25611)

Max 的版本也要和发布时分开。官方公告说明，`qwen3.8-max` 自 2026 年 9 月 5 日起切换到 `qwen3.8-max-0902` 快照，8 月 3 日发布文中的评测对象与现在调用别名得到的版本，不宜默认完全相同。[来源：Max 更新公告](https://docs.qwencloud.com/changelog/model-updates/qwen3.8-max-upgrade)

真要比较两者，至少得固定原始媒体、声音和字幕的保留方式、工具权限、Harness、重试次数、模型版本和计时起点；会议任务还要检查关键决定能否回到原片段，桌面任务要验证真实应用状态。只比最终回答通不通顺，就漏掉了证据与行动之间的关系。

## 回到那段录像

从 Qwen3.8-Max 的视角看，这段录像是画面、字幕和可以整理成记忆的事件，它擅长把看到的东西变成工作，并且在执行中不断回看结果、自我修正，训练系统围绕环境组合、统一奖励和 batch 均衡组织这种能力。从 Qwen3.8-Omni 的视角看，录像里还有原始声音、声音的方向和它发生的时刻，这些信号经过各自的编码器进入同一个推理骨干，再通过实时会话变成对话里的即时回应。

所以“已经有 Max，为什么还要 Omni”的答案，取决于任务缺的是哪段证据：预算表需要可靠的视觉和文档理解，谁否决了哪一版需要声音和时间关系，把修改落进文件需要工具执行和验证。两个模型能力有重叠，公开接口有清楚的边界，系统可以选其中一个，也可以让它们协作。

动手之前，先问三个问题：输入有没有保留任务需要的原始证据？感知得出的结论能不能指回原始位置？“已完成”有没有真实的工具结果支撑？

<Callout type="note" title="比较范围">
比较对象是公开的架构、训练系统和接口边界，没有运行 Max 或 Omni 的 API，也没有做匹配条件的性能实验。会议场景、事件对象和前后台协作是解释与工程建议。Max 的视频评测数字取自其官方发布文结果表，带字幕、记忆或搜索的设置以原表标注为准。
</Callout>
