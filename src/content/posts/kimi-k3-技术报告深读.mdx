> 解读对象：**Kimi K3: Open Frontier Intelligence**，Kimi Team。<br/>
> 主依据：[arXiv 2607.24653 v2](https://arxiv.org/abs/2607.24653v2)，2026 年 8 月 7 日修订，初稿发表于 7 月 27 日。下文页码均指这份 47 页 PDF。<br/>
> 报告中的排行榜和价格沿用其评测时点，不代表本文日期的实时排名。

假设你把一个维修管理系统交给 Agent 重建。它需要查旧接口、阅读代码、修改数据库、运行服务，再打开浏览器检查页面。测试报错后，它得判断是自己的实现错了，还是对原系统的行为理解错了。几个小时过去，最初的需求、几十次失败尝试、终端输出和截图已经混在一段很长的历史里。

把上下文窗口扩到一百万 token，只解决了这段历史有没有机会被送进模型。模型还要能从中提取有用信息；训练时要见过这种反复试错的过程；系统要负担得起每次继续执行的成本；最终还要有一个独立于模型自述的办法，判断它是否真的完成。

**K3 值得连起来读的，正是这四件事之间的连接。** KDA 和 MLA 分担长历史的处理，Attention Residuals 改写深层网络的信息汇合方式，Stable LatentMoE 扩大每个 token 能调用的专家集合。它们提供基础能力，长轨迹 RL 和可恢复的 sandbox 再把这种能力训练成持续行动。

本文沿着上面的开发任务往下走。这个任务是帮助理解的贯穿示例，不是论文公开的一条完整运行日志。涉及实测时，会单独说明 benchmark、条件和出处。

## 1. 先看一张全景：K3 把信息流拆成三个方向

理解 Transformer，可以先分清两种计算：attention 让当前位置读取其他位置的信息，FFN 变换当前位置的表示。MoE 则给 FFN 准备多个专家，按输入选择其中一小部分。残差连接负责把每层的计算接起来。

K3 同时改了这三个部位。

图里的基本组合是三层 KDA 接一层 Gated MLA。实际网络有 93 层，因此不能把它理解成整齐的 24 组四层：最终配置是 **69 层 KDA、24 层 MLA**。表 1 给出的总参数是 2.78T，每个 token 激活 104.2B；常见介绍把它们约写成 2.8T 和 104B。

这里有两个容易混淆的大小。每个 token 只计算部分专家，不代表部署时只需要容纳 104B 参数；未被当前 token 选中的专家，仍然属于模型权重。KDA 减少的是一部分历史状态成本，也不会把专家权重存储一起消掉。

接下来先跟随一个新 token，看它怎样更新过去的信息。

## 2. KDA：把新信息写入一张会被修正的状态矩阵

### 2.1 从保存历史，走到维护状态

在普通自回归 attention 中，模型为历史 token 保存 key 和 value。新 query 到来时，按内容计算权重，再汇总历史 value。缓存随着序列增长；MLA 用低维潜变量压缩每个位置的缓存，但仍保留了逐位置增长的历史。

KDA 采用另一条路径。每个 attention head 维护一张固定形状的矩阵 `S`。历史已经被累计进这张矩阵，新 token 带来三个向量：用于读取的 `q`、用于定位写入方向的 `k`，以及希望写入的内容 `v`。

若 key 维度为 `d_k`、value 维度为 `d_v`，那么 `S` 的形状是 `d_k × d_v`。按报告公式 1 的方向约定，读取结果是 `Sᵀq`。矩阵尺寸由模型确定，不随已经处理了多少 token 增长。

但固定容量意味着必须选择怎样覆盖已有内容。KDA 的关键是先估计旧状态在当前 key 上已经记住了什么，再只写入差额。

### 2.2 一次更新分四步

把报告公式 1 改写成等价的计算顺序，更容易理解。`α` 是长度为 `d_k` 的保留门，每个分量位于 0 和 1 之间；`β` 是控制本次写入强度的标量。它们由当前输入生成。

```text
S_bar = Diag(α) · S_old       # 分别衰减 key 通道
v_hat = S_barᵀ · k           # 旧状态对当前内容的预测
error = v − v_hat            # 本次需要修正的差额
S_new = S_bar + β · k · errorᵀ
output = S_newᵀ · q
```

这就是 delta rule 在这里的含义。直接把 `k vᵀ` 不断加进状态，可能把已经存在的信息重复累加；减去预测值后，更新围绕“旧状态还差多少”展开。`α` 允许不同通道以不同速度遗忘，`β` 决定相信这次新观察多少。

用一个明确简化的例子验算。假设只有一个 head，key 和 value 都是二维，旧状态是 `[[2, 0], [0, 1]]`。令 `α = [0.5, 0.8]`，`k = q = [1, 0]`，新内容 `v = [3, 0]`，写入强度 `β = 0.5`。

<TechGraph src="/images/posts/kimi-k3-技术报告深读/kda-update.svg" title="一次 KDA 状态更新" caption="博主自绘，依据 §2.1.1、公式 1。二维数值为教学假设，不是 K3 的真实 head 尺寸或测量结果。" />

衰减后，第一行从 `[2, 0]` 变成 `[1, 0]`，第二行变成 `[0, 0.8]`。当前 key 选中第一行，读出的预测是 `[1, 0]`。新内容要求 `[3, 0]`，所以差额为 `[2, 0]`；写入一半差额后，第一行回到 `[2, 0]`。

这时再次沿同一个方向读取，得到的是 `[2, 0]`，而不是新值 `[3, 0]`。原因是 `β = 0.5` 只完成了半步修正。如果把 `β` 设到接近 1，这个方向就会更接近新值。真实 key 通常不会如此正交，因此一次写入也可能影响其他查询方向；这正是固定状态的表达能力和干扰之间的取舍。

例子只展开了递归核。真实 KDA 在 q、k、v 投影后使用 ShortConv 和 Swish，对 q、k 做 L2 归一化，输出还要经过归一化及门控。报告也把输出门从先前的低秩参数化改成全秩。这些外围操作会改变进入递归核的数据分布，不能把五行教学计算当成完整实现。

### 2.3 为什么保留 MLA

回到维修系统。Agent 可能在大量代码和日志中形成了“这是一个订单状态流转问题”的中间表示，也可能必须再次找到最初规格里“已结算订单不允许回退”的精确要求。

前者适合用不断更新的状态吸收信息；后者提醒我们，压缩后的固定状态不能保证无损保存每一个细节。K3 因此保留 Gated MLA，提供对全局历史的内容查询。这里的业务语义是帮助理解的类比，论文没有证明某个 KDA head 专门负责订单状态、某个 MLA head 专门负责规则检索。

MLA 仍以低维缓存表示历史位置。K3 在这条路径上使用 NoPE，不额外加入显式位置编码；作者认为 KDA 的递归和门控已经提供了顺序信息。MLA 输出再经过全秩门控，让当前 token 调节从全局 attention 读出的通道。

<Callout type="note" title="固定状态的边界">
K3 的部分层具有固定大小的递归状态，整个模型仍有随上下文增长的 MLA 缓存。“百万上下文只需常数内存”会把混合架构最重要的条件删掉。
</Callout>

### 2.4 一个数值约束，怎样改变 GPU 的计算方式

递归写法适合解释，却不适合让 GPU 一次只算一个 token。训练和 prefill 会把序列切成 chunk，使 chunk 内部的一部分计算并行展开。问题在于，展开后的表达式涉及多步保留门的乘积及其倒数：乘积过小，倒数就可能溢出。

先前 Kimi Linear 使用的 log-decay 没有有限下界。K3 把它改成有下界的形式，报告设 `g_min = −5`，并通过 sigmoid 将 `g = log(α)` 限制在 `−5` 与 `0` 之间。

由此能做一个很具体的检查：16-token tile 内的累计 log-decay 大于 `−80`，对应倒数小于 `exp(80)`，落在 BF16 的指数范围内。这里保证的是这一环节的动态范围，不等于 BF16 获得了 FP32 的有效数字精度，也不是整个网络不会溢出的证明。

<Figure src="/images/posts/kimi-k3-技术报告深读/bounded-decay.png" alt="有下界的 log-decay 曲线，以及对角 tile 从显式逐位置计算切换为 Tensor Core 计算的示意" caption="来源：Figure 3，PDF 第 5 页。左图比较 log-decay 参数化，右图说明数值范围约束怎样改变 chunk 对角区域的实现。" />

这个限制让原先需要特殊处理的对角区域也能进入 Tensor Core 矩阵乘法路径。它解释了报告中“算法与系统共同设计”的一个实际含义：先改变数值范围，再让更统一的计算实现成为可能。不能从右图面积估算端到端加速，因为 kernel 之外还有投影、通信和其他层。

## 3. AttnRes 与 Stable LatentMoE：状态进入深层以后怎样使用

### 3.1 AttnRes 在网络深度上做选择

标准残差连接把每层输出加回当前表示。展开后可以看到来自多层的信息，但后续层拿到的是累加后的单个向量。它没有一个显式接口，单独重新选择某个较早的层输出。

Attention Residuals 给这种选择增加了接口。每层有一个学到的 pseudo-query，用它对先前层的表示打分，经过 softmax 后加权汇总。这里查询的是**同一个 token 在不同网络深度产生的表示**，不是再次在整段历史 token 上做 attention。

pseudo-query 本身是该层的可学习参数，打分仍会随 token 改变，因为作为 key 的表示来自当前 token。算 key 分数前先做 RMSNorm，以免幅值大的层仅靠“声音更大”占据权重；用来加权求和的 value 保留原表示。

为直观看加权结果，假设当前有三个来源：嵌入 `[1, 0]`、较浅层输出 `[0, 2]`、较深层输出 `[2, 0]`。假设模型算出的权重为 `[0.2, 0.5, 0.3]`，汇合结果就是 `[0.8, 1.0]`。这个例子只演示加权汇合，没有模拟真实打分。它说明后续计算可以偏向较浅层来源，而不必让所有来源以相同系数累加。

Full AttnRes 要保留所有层输出，会增加显存驻留和流水线阶段间的通信。K3 使用 Block AttnRes：块内继续求和，块间才保留可供选择的表示。93 层按 12 层一块分为 8 个块，最后一个不足 12 层；算上嵌入，共有 9 个来源块。计算某块内部的后续层时，还会纳入该块当前的部分和。

这样既保留跨深度读取，也限制了需要保留的来源数。它不能任意取回块内每个层的独立输出，这正是用块粒度换取存储和通信可控的代价。报告 §2.2 引用先前 AttnRes 工作来支持约 8 块的选择；K3 本身没有给出一套覆盖所有块数的独立下游对比表。

### 3.2 专家更多了，为什么先把表示变窄

K3 的隐藏宽度是 7,168。若每个 token 都把这个宽度的表示发送给 16 个路由专家，激活传输和专家矩阵读写会随之增加。

LatentMoE 先把路由分支投影到 3,584 维，再交给选中的专家。每个专家在较窄空间中处理；各专家输出按路由权重聚合后，经过 RMSNorm，再投影回 7,168 维。与此同时，两个共享专家直接处理全宽输入，提供一条不经过潜空间压缩的变换路径。

```text
输入 x：7,168 维
  共享分支：2 个共享专家处理全宽 x
  路由分支：x → 3,584 维 → 选中 16 / 896 个专家
          → 加权聚合 → RMSNorm → 投影回 7,168 维
两条分支的输出相加
```

潜空间宽度减半，不等于整个模型计算减半：它增加了下投影和上投影，共享专家仍走全宽，专家数量及中间宽度也变了。它提供的是扩大路由专家集合时更可控的成本结构。

“Stable”针对两个具体故障。第一，压缩投影、专家内部变换、还原投影串起来，会放大中间激活；第二，896 个专家更难被均衡地使用。前一个问题靠归一化与有界激活处理，后一个问题靠路由偏置更新处理。

### 3.3 SiTU-GLU 到底限制了什么

SwiGLU 的两个乘法分支都可能变大，乘在一起更容易产生离群值。SiTU-GLU 对两个分支分别施加平滑上限：把线性项 `z` 换成 `β tanh(z/β)`，门分支仍保留 sigmoid 因子。

K3 设门分支的 `β₁ = 4`，up 分支的 `β₂ = 25`。因为 tanh 的绝对值小于 1，sigmoid 介于 0 和 1，二者乘积的每个坐标就有 `4 × 25 = 100` 的上界。原点附近，`β tanh(z/β)` 近似 `z`，所以小值区域保留了 SwiGLU 的局部行为。

这也限定了“稳定”的范围：有界的是 **SiTU-GLU 的逐坐标输出**，不是专家最后投影后的所有张量都小于 100。报告附录 B 给出了这个推导；聚合后的 RMSNorm 则在另一处控制路由分支送入上投影前的尺度。

### 3.4 Quantile Balancing：调专家的入选门槛

路由器先为每个专家产生 sigmoid 分数，再把专家偏置加上去，选择 Top-k。偏置只影响入选；被选专家最终参与混合的权重，由原分数归一化得到，不包含偏置。

以前一种简单的平衡方法是：专家太忙，偏置减一点；太闲，偏置加一点。固定步长太小会追不上负载变化，太大又可能反复振荡。Quantile Balancing 改为估计：要让这个专家接近目标负载，门槛应当落在分数分布的哪个位置。

设一批有 `m` 个 token、`n` 个专家，每个 token 选 `k` 个，那么平均目标负载为 `mk/n`。计算时多看一个候选，即 Top-(k+1)；第 k+1 名的带偏置分数成为当前 token 的入选门槛。对每个专家，收集它相对所有 token 门槛的 margin，再按目标比例取分位数，得到下一步的偏置。

<Figure src="/images/posts/kimi-k3-技术报告深读/quantile-balancing.png" alt="Quantile Balancing 原图：8 个 token 路由到 4 个专家，由负载 4、3、1、0 变为示例中的 2、2、2、2" caption="来源：Figure 5，PDF 第 8 页。图中 m=8、n=4、k=1，因此目标负载为 2；红色连线标出发生变化的分配。" />

图中右侧恰好平衡，是为了展示这个规则。实际训练不会拿当前批次算出的新偏置重路由当前批次：**新偏置下一步才生效**。百万级 token 的分位数也不是全量收集再排序，而是各设备累计直方图，通过一次 all-reduce 合并计数，再读取分位点。附录 D 给出误差受 bin 宽度限制的解释；推理时偏置冻结，不再做这种批次统计。

还有一层系统补偿容易被忽略。QB 调的是“专家受欢迎的程度”，MoonEP 调的是“专家计算落到哪块设备”。即使专家总体比较均衡，一个微批次仍可能把某些设备挤满。MoonEP 按当前路由结果动态复制和迁移冗余专家，让各设备处理同样多的 token 分配，计算后把副本梯度归并回原处。

因此，路由平衡与设备平衡不是重复设计。前者关心专家训练是否充分，后者关心并行步骤会不会一直等最忙的设备。报告给出每个 rank 最多预留 `E/R` 个冗余专家槽位的上界，并在附录 E 证明其近乎紧；工程上还要支付副本预取和梯度归并成本。

## 4. 预训练提供基础，但 2.5× 不能归给一个模块

在维修系统里，终端输出和界面截图都可能改变下一步判断。K3 使用从头训练的 MoonViT-V2，把图像和视频映射进同一语言主干；语言与视觉从预训练开始就在 next-token prediction 目标下联合优化。

这条视觉路径有 27 层、约 401M 参数。投影前做 2×2 空间降采样，把视觉 token 数减少到四分之一；图像和视频共享参数，视频还有时间方向的处理与池化。它支持最高 3584×3584 像素输入，但“支持这种分辨率”不等于所有视觉任务都使用这个尺寸。

为什么放弃以 SigLIP 等预训练视觉编码器初始化？报告 Figure 6 给出的直接证据是训练中的梯度范数：从头训练的 MoonViT-V2 更平稳，而 SigLIP 初始化的对照有更频繁的尖峰。作者同时报告视觉评测匹配该基线。这支持他们在这一联合训练方案下的选择，不能扩大成“对比预训练对所有多模态模型都没价值”。

训练还有两处配合。Per-Head Muon 对注意力投影的动量按 head 分块正交化，减少不同 head 尺度差异对共同更新方向的影响。上下文也按阶段增长：预训练从 8K 到 64K，cooldown 阶段再从 256K 扩到 1M。没有显式位置编码，并不意味着可以跳过长序列数据和长上下文训练。

这里一起变化的包括架构、数据、优化以及重新调过的 batch size、学习率、tokens-per-parameter 和模型形状。报告 §3.2 也说明曲线使用 OOD 验证数据。因而 2.5× 应当记在**整体训练配方**名下，不能拆成“KDA 提升多少、AttnRes 再提升多少”相加，更不能当作部署吞吐提升 2.5×。

报告披露了 cosine 学习率、1% warmup、0.1 weight decay 等细节，也介绍了文本与视觉数据处理方式；但没有把全部语料比例、最终训练预算和各阶段超参数整理成一份可直接复现的完整配方。读者能理解重要设计选择，距离独立训练出同等模型仍有很大差距。

## 5. 长轨迹 RL：把“会写下一步”训练成“能继续做下去”

### 5.1 先把任务变成可判定的环境变化

继续看维修系统。目标“做一个像样的管理页面”很难直接作为奖励；如果只让模型解释自己做得如何，生成漂亮的完成总结也可能拿到高分。

报告里的 Autonomous Execution Tasks（AET）为任务定义初始状态、目标、限制、工具、执行预算和独立 verifier。Agent 自己决定怎样分解和执行；奖励来自最终环境状态，而不是它是否声称成功。

一个教学版本可以这样设置：给 Agent 查询旧系统的接口和一套空项目，让它实现接单、报价、维修、结算；公开测试返回当前失败项，隐藏测试检查未见过的状态组合。公开反馈指出“结算后的订单还能被撤回”时，Agent 应当定位状态转换约束、修改实现，再跑测试。最后提交是否成功，要看隐藏验收，而不是公开测试有没有全部被迎合。

这段流程是依据 AET 定义构造的例子。论文确实给出一个相机维修系统黑盒复制案例（Figure 10），却没有在正文公开足以重放每一步的完整工具日志。不能把教学中的具体接口和错误当成论文原始轨迹。

AET 还用有限提交预算、公开与隐藏 verifier 分离等办法限制 reward hacking。它与其他训练任务共同扩大了可验证行为的范围：kernel 任务同时看数值正确性和性能；网页任务会检查构建、实际交互及是否伪造产物；个人助理任务在持续演化的模拟应用中运行，事件可跨多个模拟日，单条 rollout 能达到数千次工具调用。

训练任务从哪里来？§4.2.2 介绍了知识图谱引导的合成：从粗粒度领域逐层扩展到细概念，采样相关节点，检索真实材料，再选任务类型进行合成。它让覆盖范围和颗粒度更可控，但并不自动保证任务无泄漏或 verifier 正确；报告没有用一个全量审计结果解决这两个问题。

### 5.2 为什么不能等最慢的一条轨迹

普通单轮推理的长度可能差几倍，Agent 任务还会等待编译、测试和工具返回。一批任务中，有的十几步结束，有的几百步还在修问题。若所有 GPU 都等最后一条轨迹，训练更新会被长尾拖住。

K3 使用 partial rollout。简化地说，每批采样 `N` 个 prompt，每个生成 `K` 条轨迹；达到指定完成比例时暂停尚未完成的生成，进入更新阶段。下一轮优先恢复这些未完成轨迹。**同一个 prompt 的 K 条轨迹全部完成后，才作为完整组进入优化。**

<TechGraph src="/images/posts/kimi-k3-技术报告深读/rollout-resume.svg" title="暂停的是执行过程，不只是文本" caption="博主自绘，依据 §4.1.1 与 §5.3。图中的集成测试为教学情境；生成调度和 sandbox 暂停有各自的触发点。" />

对维修系统来说，保存聊天记录还不够。数据库可能已有测试数据，后台服务正在运行，测试进程刚走到一半。如果下一轮只给模型原来的文本，却换成一个全新目录，它继续执行的前提已经变了。

报告的 AgentENV 用 microVM 支持环境状态的增量 checkpoint 和恢复，只保存上次之后变脏的内存页。Pause/Resume 可以在等待模型输出时释放 sandbox 的 CPU 与内存；Fork 可复制状态给奖励判定使用，避免评测改坏正在执行的环境；周期性 Snapshot 则服务于故障恢复。

报告给出的 checkpoint 和恢复延迟最低分别为 133ms、49ms，是其工作负载中的系统结果。它没有提供足够完整的硬件、状态大小和延迟分布，无法据此承诺任意 sandbox 都以这个速度恢复。模型侧的 KDA/MLA 缓存则由另一套管理路径保存，不能把 microVM checkpoint 理解为自动包含了全部模型缓存。

跨轮续跑还会产生一个训练问题：一条轨迹可能由多个策略版本生成。它不再是完全由当前策略采样的数据。报告用逐 token 正则处理这种 off-policy 情形，但仅凭本报告正文，还不足以重建全部优化细节。保存得住轨迹和正确使用轨迹，是两个需要同时成立的条件。

### 5.3 长任务可以多想，但不能靠无限输出获胜

K3 并非只训练一个固定推理预算。它先训练 max effort，再通过预算约束发展较低 effort。对每个 prompt，冷启动 rollout 提供一个基础长度预算 `b₀(x)`；当轨迹长度超过乘数 `τ` 调整后的预算时，任务奖励被改为 `−1`。

计数口径很关键：普通任务统计 thinking token；Agent 任务统计整个过程中累计输出的 token，包括 thinking 和工具调用参数。工具返回的输入 token 会增加上下文，却不在这个输出长度定义里。工具执行的墙钟时间也不是这个公式直接限制的量。

这让“做对”和“在合适预算内做对”进入同一训练目标。若 Agent 对同一错误连续改二十次却没有进展，多输出本身不会受到鼓励。与此同时，过紧预算也可能惩罚真正需要更多尝试的问题，所以报告使用随 prompt 变化的基础预算，并调节 `τ`，而不是给所有任务硬塞相同上限。

不能直接验证的任务仍需要模型奖励。报告的 GRM 先形成与结果相关的 rubric，再评分；成对比较还限制过度冗长的回答，避免把篇幅误当质量。这套机制减少一种偏差，却没有让 judge 变成完全可靠的真值源。

### 5.4 九个老师怎样变成一个模型

后训练有三个领域：通用、通用 Agent、编码；每个领域再分 low、high、max 三档 effort，形成九个专门训练的 teacher。**这里的九个 teacher 是完整模型，和 MoE 层里的 896 个路由专家不是一回事。**

若只是拿老师现成的答案训练学生，学生自己走偏后的前缀可能不在这些答案里。Multi-Teacher On-Policy Distillation（MOPD）让学生先生成，再由匹配任务领域和 effort 的老师，在学生实际到达的前缀上提供 token 级信号。

报告公式 15 使用 teacher 与 student 对采样 token 的概率比的对数作为奖励，并截断到指定范围；优化时不沿这项奖励的计算图反传。直观上，同一个位置若老师比学生更认可这个 token，会提供正向信号，反之则相反。正文没有给出所有超参数值，不能把概念式写成可复现实验配置。

一个应当保留的负结果是：他们也试过 top-k 蒸馏，没有观察到明确的收敛或最终表现优势。因此九个老师的结论不是“把老师分布保留得越全越好”，而是该配方选择了在学生轨迹上提供更直接的监督。

这条训练链还从 SFT 一直使用 QAT。主要低精度路径是路由专家的 MXFP4 权重和 MXFP8 激活；共享专家、attention、潜空间投影及 router 等保留更高精度。它提前让模型适应部署中的部分数值误差，也再次说明不能把 K3 简称为“全模型 FP4”。

## 6. 真正续跑一次请求，需要恢复到同一个历史位置

前面的模型结构让长历史更便宜，partial rollout 让长轨迹不必卡住整批更新。但当 Agent 调用工具后回来，下一次推理能否复用上一次结果，还取决于缓存到底保存在哪里。

### 6.1 KDA 和 MLA 必须在同一边界命中

MLA 按 token 保存缓存；KDA 原地更新一张状态矩阵。假如只保留 KDA 最新状态，模型已经走过第 10,000 个 token 时，就无法仅凭这张矩阵直接回到第 8,000 个 token。前面的信息已经经历了后续遗忘和写入。

因此，共享前缀不能只问“这段文本以前见过吗”，还要问“在它结束的同一个位置，MLA 缓存和所有 KDA cache group 的 checkpoint 是否都存在”。

<Figure src="/images/posts/kimi-k3-技术报告深读/prefix-cache.png" alt="6144-token 物理缓存块内包含 12 个 512-token 哈希块，在 2560 位置命中 MLA 前缀及 KDA checkpoint" caption="来源：Figure 12，PDF 第 23 页。分配的物理块、查找前缀的 hash 块与 KDA checkpoint 边界是三种不同概念。" />

沿着原图做一次查找。物理块容量为 6,144 token，内部每 512 token 形成一个 hash 边界。新请求与缓存前 2,800 token 一致，则完整 hash 块最多覆盖到 `5 × 512 = 2,560`。如果所有 KDA group 在这里都有 checkpoint，就可以命中 2,560，余下 240 token 再计算。

若某个 KDA group 缺少这个 checkpoint，就要寻找更早的共同有效边界。MLA 单独匹配得更长，也不能强行让 KDA 从较短位置和它拼在一起；两者描述的将是不同历史。

K3 因此把物理分配粒度与 hash 粒度拆开。MLA 可以在一个还没填满的物理页内部登记可复用端点；KDA 则在 hash 对齐的位置保留稀疏快照，优先保留对话轮次边界，回收被后续状态替代的中间快照。命中后，KDA checkpoint 复制进请求私有运行状态，MLA 的部分块采用 copy-on-write，避免新请求修改别人仍在使用的前缀。

并发时还有三个一致性要求：先固定所有命中的块再做新分配；尚未完成 GPU 拷贝的块暂不参与匹配；某个 KDA group 的 checkpoint 被淘汰时，同边界的关联条目一起失效。否则一个表面上的 cache hit，可能读到被覆盖的数据或另一段历史。

这解释了为何线性 attention 的状态虽然固定，prefix cache 反而需要更细的设计。固定大小解决容量增长，快照和版本边界解决可恢复性，它们不是同一个问题。

### 6.2 长上下文怎样跨设备并行

递归还带来另一个难题：后一段要用前一段输出，怎样把长序列分到多块 GPU？

KDA Context Parallelism 把一段序列的作用写成 `S_out = M · S_in + U`。`M` 是这一段对输入状态施加的累计转移，`U` 是从零状态开始时这一段自己产生的内容。两者都可以先由本地 token 计算出来。

然后按照序列顺序组合。两段 A、B 的合成是 `(M_B M_A, M_B U_A + U_B)`，满足结合律，可以做 prefix scan，但一般不满足交换律。

<TechGraph src="/images/posts/kimi-k3-技术报告深读/state-composition.svg" title="必须传递状态怎样变化，不能只传递新增内容" caption="博主自绘，依据 §5.1.2、公式 17。标量教学例子展示为什么两段本地产生的状态不能直接相加；真实计算使用矩阵。" />

图中 A 从零产生 2，B 从零产生 3，直接相加得到 5。但真实顺序里 B 会先把 A 留下的 2 衰减为 1.6，再加自己的 3，所以正确结果是 4.6。传输 `M` 和 `U` 才能恢复这一影响。

报告的实现通过固定大小的 all-gather 交换分段信息，再恢复段入口状态。这个通信量不随每段 token 数直接增长；它仍取决于状态维度、head 数和并行设备数。它还只解决 KDA 分支，不能据此说混合模型的全部长上下文通信都成为常数。

### 6.3 模型缓存、训练状态与工具环境在争同一份资源

在百万上下文 RL 中，K3 把训练和 rollout 放在共用的设备资源上，报告说单个实验可控制在数百块 GPU 内。这会让训练状态和推理缓存争夺内存。

它用 write-back 策略处理前缀：正在解码的块留在 GPU，闲置且被淘汰的可复用前缀再写入 CPU DRAM，下一次复用前预取回来。KDA 状态与对应 MLA 块一起迁移，保持生命周期对齐。训练迭代完成后，权重和优化器状态可以暂时卸到 NVMe，为 rollout 的外部缓存池腾出 DRAM；rollout 结束后再释放缓存池。

调度并发也随轨迹增长变化。开始时上下文短，可以多接任务；后期 KV 占用升高，再根据活动请求数、排队量和 cache 使用率降低并发。用整条轨迹的平均长度固定并发，会在早期浪费资源或在后期触发抢占。

线上服务还要保护已有前缀。报告用一个 400K 历史、只新增 4K 输入的编码请求说明命中的价值：cache miss 会重新做很大一段 prefill。会话优先路由到持有缓存的集群；备用集群并不提前保有同一份缓存，故障时仍要重算，只是用一致性哈希把重算负担分散开。

推测解码也必须照顾 KDA 原地状态。草稿 token 被拒绝后，不能简单删除几个 KV 条目就让递归状态回到过去。K3 缓存体积较小的投影输入，在片上重放已接受的部分，再写回正确状态，而不是为每个草稿位置保存一整张状态矩阵。草稿模型采用 EAGLE-3 式结构，训练目标直接关注接受率。

这些优化都有共同的判断依据：这段信息下一次在哪里用、能否重算、重算比移动更贵还是更便宜。读完之后，更应该记住这些选择条件，而不是把 CPU、NVMe、prefix cache 分别记成三项互不相关的加速技术。

## 7. Benchmark 究竟测到了哪种“长程能力”

### 7.2 搜索：一百万上下文是否可以替代上下文管理

BrowseComp 不是评价一篇长报告写得多好，而是给出交错线索，要求找到短而可核验的答案。模型需要尝试搜索、排除候选、组合证据。它给“持续查找”提供了清晰终点，同时缩小了对开放式研究质量的覆盖范围。

K3 的主结果是 **91.2%**，使用 300K 触发的上下文压缩；完整 1M 窗口、不做上下文管理时是 **90.4%**（§6.1.3）。

这是本文主线里最有用的一组对照：更大的窗口没有让上下文管理自动失去意义。压缩可能减少无关历史、改善后续检索或控制成本，但报告这组结果不足以单独确定哪条机制造成差异，也没有给出支持显著性判断的误差区间。能确定的是，91.2% 不能被写成“原样记住一百万 token 的得分”。

表 2 里 GPT-5.6 Sol 的 BrowseComp 分数也是 90.4。它与“K3 不压缩”的数值相同，是两项不同结果，不能在引用时混为一谈。

### 7.3 编码：harness 是实验条件的一部分

Terminal-Bench 2.1 报告 K3 为 88.3，Sol 为 88.8。这个差距很小，更关键的是：报告对所有模型取多个 harness 的最好结果。它衡量的是在所测试系统配置下能达到的表现，不能直接解释为同一工具与提示词条件下的模型差异。

内部 Kimi Code Bench 2.0 给了一个更直观的例子。同一个 K3，用 Claude Code 时为 73.7，用 Kimi Code 时为 72.9；两者都出现在表 3。模型权重相同，围绕它的工具、提示、上下文管理不同，结果就会变化。报告的白盒 harness 训练也正是在这些可组合模块上增加多样性，减少只适应单一运行方式的问题。

SWE-Marathon 中 K3 为 42.0，Opus 4.8 为 40.0，Sol 为 39.0，Fable 5 为 35.0。若只写“K3 高出 Fable 7 分”，会遮掉两个条件：该评测是 H20 校准分支，而且 Fable 在 35% 的任务触发 fallback。它是报告中这套运行条件的比较，不能当作所有模型在最终官方版本、相同硬件和相同有效模型下的能力排名。

绝对分数也有意义。42.0 并不意味着长程工程问题已经大体解决，困难任务仍留下了相当大的失败空间。

### 7.4 哪些结果支持主线，哪些结果限制它

下面只选与本文问题有关的几行，不按最亮眼的分数选取。数值来自报告表 2、表 3；除特别注明外保留原表口径。它们都是整体系统结果，没有隔离 KDA 或长轨迹 RL 的贡献。

| 观察对象 | K3 | 对照或补充 | 可以据此做出的判断 |
| --- | ---: | --- | --- |

CharXiv 的变化与报告训练方案形成了合理呼应：模型不必一次看图就给答案，可以写程序裁剪、计算和检查，把输出重新作为观察。但表中的提高同时包含额外工具和执行计算，不能写成“MoonViT-V2 独自带来 6.5 分”。

Agent Behavior Bench 则提醒我们，轨迹更长不必然代表行为更成熟。一个 Agent 可以交付不错的产物，同时反复运行无效命令、缺乏及时止损，或在最后没有做好验证。把结果评测与过程评测分开，才能看到这种差异。

### 7.5 费用、延迟与成功率要各自保留分母

报告 §6.4 把分数与每任务费用放在同一张图里。BrowseComp 中 K3 的 91.2% 对应约 2.03 美元/任务；GDPval-AA v2 等第三方成本沿用 2026 年 7 月 23 日的 API 计价。

这是一份历史成本比较，不是当前报价。每任务费用还受到 token 用量、缓存计价、effort、工具和 harness 的影响。它也不是“每个成功任务的成本”：若有失败任务，后者还涉及失败消耗、重试策略和最终成功率。

同理，预训练的 2.5× scaling 效率、线上 cache hit 节省的 prefill、一个 kernel 的加速，都不能直接兑换成这里的美元降幅。完整成本图把能力和使用成本连接起来，却没有给出各个架构组件分别贡献多少钱的归因。

## 8. 一个真实长任务案例：把延迟从 283.6ms 降到 114.4ms

报告 §7 给了比榜单更具体的证据。模型在同样配置的 sandbox 中，获得每任务最多 24 小时预算，独立进行 profiling、重写和 benchmark。任务覆盖 AttnRes、DSA、KDA、MLA 四类 kernel，硬件包含 NVIDIA Hopper 与另一家 GPGPU。

<Figure src="/images/posts/kimi-k3-技术报告深读/kernel-trajectory.png" alt="AttnRes kernel 优化轨迹，横轴 active hours，纵轴相对 FLA Triton 基线的百分比改进" caption="来源：Figure 14，PDF 第 33 页。曲线展示持续尝试中的阶段性改进；正文给出的延迟从 283.6ms 降至 114.4ms。" />

读这种图，应当先看横轴 active hours，而不是默认它表示一次模型回答的延迟。曲线呈台阶，意味着长时间尝试后才可能出现新的有效版本；某段时间没有提升，也不能仅凭曲线判断 Agent 当时是在无效循环还是在探索新方案。

K3 的 AttnRes 案例从 283.6ms 降至 114.4ms。把数字重新算一遍：

```text
延迟降幅 = (283.6 − 114.4) / 283.6 ≈ 59.7%
速度倍数 = 283.6 / 114.4 ≈ 2.48 倍
```

原图纵轴写 Speedup，标出 59.7%；对应正文延迟，准确的量纲是延迟降低约 59.7%。它不是“速度变成 1.597 倍”，更不是 K3 模型自身推理快了 59.7%。优化对象是一个 kernel 的测量结果。

这条案例把本文的几个环节串了起来：模型要理解代码和设备反馈，多次改写后仍然记得约束，执行环境要能长期保存，最终改进要通过数值与性能验收。它展示出一种可行的完整工作方式。

证据也有边界。报告这段没有列出每个 kernel 的所有输入形状、dtype、完整性能分布和逐步运行日志，因此仅靠技术报告无法重放全部结果。24 小时是预算上限，不是每个成功版本都恰好用了 24 小时。也没有一组关掉 KDA、关掉 partial rollout 的对应实验，证明这些模块各自造成了多少提升。

更大规模的 MiniTriton 案例进一步把产物从单 kernel 扩展到编译器与运行时。作者展示了 L20 上的 roofline、训练 loss 与梯度对照；这些检查比“代码能运行”更接近正确性和效率的验收。但精选案例仍然缺少所有尝试的成功率分母。

芯片案例则必须保留更严格的限定：它是 nano 模型架构的推理芯片原型，使用开源 EDA 流程，报告的是 RTL 仿真的 decode 吞吐。不能把其中超过 8,700 token/s 的数字解释为完整 2.78T K3 的实芯片实测。

## 9. K3 给出了什么，又还缺哪一段证据

我认为这份报告最扎实的地方，是把“长任务”拆成了可以落到具体状态和具体操作的问题。

KDA 的状态如何衰减和修正，有公式可以验算；跨设备如何合成，有转移矩阵和本地产生量的分解；缓存如何恢复到同一位置，有 hash 边界、快照和并发一致性要求；环境怎样暂停续跑，有独立于聊天历史的 sandbox 生命周期。这些细节让“架构与系统共同支撑 Agent”有了可检查的内容。

还没有闭合的证据，主要在三个位置。

**组件贡献没有完全拆开。** 整体配方的 scaling 曲线和后训练 benchmark 说明最终系统表现如何，不能精确回答哪一个组件对哪种长程行为贡献最大。要回答这个问题，需要在可比较预算下改变组件，再观察任务完成率、错误恢复和成本。

**可解释设计距离完整复现仍有缺口。** 预训练语料配比、部分 RL 超参数、内部 benchmark 的完整任务与判分规则，以及若干系统测量的运行配置，没有全部公开到可重跑的程度。公开模型权重使使用和后续研究更容易，但不等于训练和评测配方都已完整开放。

**长时间执行仍然依赖外部目标和验证。** K3 能在明确目标、工具与反馈中优化动作，报告中的 AET 也特意设计了独立 verifier。它没有证明 Agent 能在模糊目标下自行确定值得学习什么，或者在没有可靠判定器时持续形成正确经验。

这也让它适合放在这组解读的较早位置。先理解 K3 如何把模型架构、长轨迹训练和执行系统接起来，再读 [Qwen3.8-Next](/blog/qwen38-next-技术报告深读/) 与 [DeepSeek-V4.1-Flash](/blog/deepseek-v41-flash-技术深度解析-把-kv-cache-压缩做到极致/) 对效率和状态成本的不同取舍，最后回到 [闭环 RSI 的三篇 benchmark](/blog/closed-loop-rsi-三篇论文深读/)，就能更准确地问：当长任务已经跑得起来，目标、经验与验证还掌握在谁手里？
