> [Vidu S2 report](https://arxiv.org/abs/2609.11638v1) · [Official project](https://github.com/shengshu-ai/Vidu-S) · [StreamEval paper](https://arxiv.org/html/2610.28402v3) · [StreamEval leaderboard](https://streameval.ai/)

Ask a character in a video to pick up a cup, and a few seconds later tell it to smile. The character has to understand the second instruction and change its expression while keeping the cup in its hand. The picture cannot stop either, and the system cannot throw the whole video away and regenerate it for one new instruction.

Traditional whole-clip diffusion can afford to wait. Every requirement is written down before generation starts, the model denoises all frames of the clip together so that earlier and later frames correct each other at every step, and the finished video arrives in one piece. Real-time generation cannot wait. While the user watches the first segment, the second is still being computed, and the next instruction may not have been spoken yet. Frames that have been shown are settled, and whatever comes next has to continue from them, even if they already contain a badly drawn hand.

The Vidu S2 report covers two models: S2-Avatar, which generates audiovisual digital characters that talk and move, and S2-Editing, which modifies an incoming video stream in real time. Most of the design in the report deals with one consequence or another of this constraint. The opening example is a good place to start: how the cup stays in the character's hand.

## The cup survives the smile partly because an agent writes it into the prompt

S2-Avatar generates in segments, or chunks, each a short stretch of synchronized video and audio. To generate segment i, the model sees the segment's condition (for example, its text description), a reference image, and the history left by earlier segments. Attention along the time axis uses a block-wise causal mask: positions within a block can attend to each other, and later blocks are invisible to earlier ones. New instructions can only enter through the conditions of later segments. (Main report, §2.2, PDF p.6.)

That raises the question of how the second instruction becomes the next segment's condition. The user only said “smile”. If that phrase were used as the condition directly, the prompt would no longer mention the cup. The generator's history may still hold traces of the cup, but no input explicitly asks for it to be kept, so the model might lose the cup while smiling or perform the pickup a second time. S2 places a VLM agent outside the generator and has it write the states that must persist into every prompt explicitly. The user's text, transcribed speech, the initial image and any newly uploaded reference image go to the agent first, which turns them into prompts for S2-Avatar. The generated frames then come back to the agent, which decides how to write the next prompt. (§2.4, PDF p.8.)

<Figure src="/images/posts/vidu-s2-realtime/agent-loop.png" alt="The report's VLM agent pipeline: user text, audio, and images enter the agent; prompts go to Vidu S2-Avatar; generated frames return as feedback." caption="Source: main report, Figure 3, PDF p.8. Faithfully cropped without modification." />

Prompts describe several things separately: the character's identity and appearance, its expression, gaze, pose and actions, and any object it should keep holding, and details the user did not ask to change are carried over unchanged. For the instruction “pick up a cup, then smile”, once the cup has been picked up, later prompts state explicitly that the character keeps holding it, unless the user asks to put it down or replace it, and the prompt for the smile changes only the expression.

Whether the cup has actually been picked up is decided by reading the frames back. The agent checks the generated frames in time order and reports whether the action is complete, only partly performed, or different from the request. The system checks confidence and, when necessary, requires repeated observations to agree. Once completion is confirmed, the next prompt switches from describing the action to describing the resulting pose or held object, without repeating the action. If the action is unfinished or wrong, the instruction is revised, and an uncertain judgment is not counted as success. The report does not publish the thresholds behind these judgments. (PDF pp.8 to 9.)

Reference images can also be replaced at any point in the stream. The agent first decides whether a new reference shows a handheld object, a background or clothing, then combines it with the user's request to write prompts that describe how the character and scene in the initial image should change. For a scene change, the prompt can describe the character leaving the original view and entering the referenced scene. To take off a hat and put it back on, the prompts describe in turn reaching for it, lifting it off, holding it and returning it to the head, and every later prompt keeps the hat on until the user asks to remove it.

<Figure src="/images/posts/vidu-s2-realtime/reference-control.png" alt="Original report examples of cup generation and replacement, scene changes, and removing and replacing a hat." caption="Source: main report, Figure 4, PDF p.9. Faithfully cropped without modification. (a) Generating and replacing a blue cup, (b) walking into a new scene, (c) taking off and putting back on the same hat. Static frames can show changes in appearance, not interaction latency." />

Two kinds of state therefore work together in continuous interaction. Video latents and KV caches store numerical features that later segments refer to, limited by the window length. The agent's prompts store explicit semantic constraints, such as the cup being in hand or the hat currently being worn. Crediting the whole effect to the long-term memory of the video backbone would leave out prompt maintenance and visual feedback.

The agent's prompts advance event by event: reach, grasp, hold, then smile. For the generator to act on prompts like these, its training data needs complete, continuous actions and descriptions written in time order. S1's characters mostly stayed talking heads, and large body movements were hard to follow. S2 adds solo dance videos and 2D and 3D animation to the data, and its processing pipeline changes in several places to match.

Vlog-style videos contain many subtle edits. An unboxing video often keeps only the moments before and after the package is opened, with the action in between cut out, and learning such a clip as continuous motion builds a jump into the supervision itself. Simply making shot detection more sensitive would wrongly reject many normal clips, so the report samples frames around each candidate cut and has a vision-language model (VLM) judge them a second time. The retained clips contain no cuts, while the false rejection rate stays below 2%. (§2.1, PDF p.4.)

Dance videos are rich in motion, but the camera often orbits, dollies, zooms or tracks the subject. Discarding all such videos would lose motion diversity, while keeping them unchanged would interfere with learning a stable background. The report observes that in most dance videos the camera translates little, the visible change comes mainly from rotation and focal length, and parallax is small, so background motion can be approximated with geometric transformations between frames. Smooth camera motion is therefore kept: foreground subjects are masked, the remaining background is used to estimate the camera transformation, and after correction and cropping the clip is filtered again to make sure the subject is still in frame. Large camera movements with complex trajectories are still excluded. (PDF pp.4 to 5.)

The descriptions are written differently as well. S1 used structured descriptions with separate fields for subjects, environment and camera, which made it hard to express the order of events and the causal links between them. S2 switches to dense, chronologically ordered descriptions that state each event's start and end time, its actions and its outcome, for example what happened between 2.5 and 3.8 seconds and what it led to. Chunk-level descriptions are cut at event boundaries rather than by fixed duration or speech alignment. Reaching for a cup and holding it afterward become two consecutive events in this kind of description. According to the report, the resulting segments are finer, which makes action transitions and responses to new instructions faster and more consistent.

## The longer it plays, the more it drifts: the model continues from its own history

The agent controls what the prompts say; it cannot stop errors in the picture from accumulating. Back to the opening constraint: the history that segment i sees is what the model itself just generated. Eq. 3 of the report writes one causal denoising step as:

```text
x̂₀ⁱ = fθ(xⁱ_tᵢ, tᵢ, r, cⁱ, x<ⁱ_τᵢ, τᵢ)
```

`xⁱ_tᵢ` is the noisy audiovisual latent of segment i, and `tᵢ` the diffusion timestep it is currently at. `r` is the reference image and `cⁱ` the segment's condition. `x<ⁱ_τᵢ` is the history left by earlier segments, at noise level `τᵢ`. The model outputs `x̂₀ⁱ`, an estimate of the segment's clean latent, which still has to be decoded into playable frames and sound. A latent is a compressed numerical representation, not pixels.

Two quantities in the formula are easy to conflate. `tᵢ` says how far denoising of the current segment has progressed, which belongs to diffusion sampling itself. `τᵢ` says how much noise has been added to the history fed in, and it can be set independently. Causality only decides who can see whom and has nothing to do with how many denoising steps are taken: each segment is still denoised step by step, it just cannot see segments that do not exist yet. Keeping some noise in the history means the model need not treat every detail of it as reliable fact.

This causal model is not trained from scratch. The report first trains a bidirectional model on both image-to-video and reference-to-video generation, giving each temporal segment its own text condition instead of one prompt for the whole video. It then replaces bidirectional temporal attention with a block-wise causal mask and continues training with a mix of two methods. Teacher Forcing shows the model clean ground-truth history, meaning the original video from the dataset. Diffusion Forcing adds sampled noise to the ground-truth history so that the model practises continuing from an unclean context.

In both methods the history comes from the dataset, which is not what happens at inference. If segment 3 draws a crooked finger, segment 4 receives that crooked finger, an input it never saw during training. Errors pass from one segment to the next this way, and over a long stream a face slowly changes or the picture breaks down entirely. The report lists this problem as the first direction of improvement for S2-Avatar.

[Self Forcing](https://self-forcing.github.io/) already has the model generate autoregressively during training, as it would at inference, and uses its own generated segments as later context, so the source of the history matches between training and inference. The Vidu S2 report argues that two problems remain. The self-generated history is fed in clean, without added noise, and it is detached from the computation graph, so no gradient flows through it. According to the report, both limit data efficiency and training quality.

Self-Replay Forcing (SRF) splits one training step into two passes. The first is the rollout: the student model generates a fairly long trajectory from front to back, exactly as at inference, with the generated blocks and KV caches detached so that the backward graph of this long trajectory is not kept. This pass settles one thing only: what history the current model actually runs into at inference.

The second pass is the replay. The system samples from the self-generated trajectory, draws an independent noise level for each block and re-noises it following Diffusion Forcing, then runs one gradient-enabled causal forward pass. The replayed blocks share one computation graph, so the loss of a later block can reach the representations of earlier blocks through causal attention. External history inherited from the rollout, outside the replayed stretch, stays fixed. Gradients cross block boundaries only inside the replay and never return to the original rollout from the first pass. (§2.2, Eq. 4, PDF p.6.)

<TechGraph src="/images/posts/vidu-s2-realtime/self-replay.svg" title="ROLLOUT FIRST, REPLAY WITH GRADIENTS" alt="A detached autoregressive rollout is followed by causal replay of three independently re-noised chunks. Gradients cross block boundaries within replay but do not return through the original rollout." caption="Author-created diagram of SRF's two passes and gradient boundary, based on §2.2 of the main report. The three blocks are illustrative." />

Two passages of the report describe this slightly differently. The introduction says the entire student trajectory is re-noised and replayed in one pass; §2.2 describes replaying a sample of the self-generated trajectory while the external history inherited from the rollout stays fixed. Both agree on the gradient boundary: the original rollout and its caches take no part in backpropagation. How long the replay is and how the external history is chosen directly determine training memory and compute, and the report does not give a configuration complete enough to reproduce.

Take three blocks, A, B and C, as an illustration rather than a measured trajectory from the paper. The face in A carries a slight identity error, B inherits it, and by C the face has visibly changed. If A and B are handed to C only as fixed history, C's loss can only teach the model how to continue after such a history; it has no effect on how A and B themselves were generated. SRF re-noises A, B and C and replays them together, so supervision on C can travel back through attention to the replayed representations of A and B. The training states come from trajectories the current student actually produces, and the replayed blocks keep gradient connections with each other. These two properties together are what separate SRF from the approaches above.

The errors in the trajectory do not thereby become a training target. The report defines SRF as an on-policy form of Distribution Matching Distillation (DMD). The self-generated trajectory decides which states training happens in, while the supervision comes from a teacher model and moves the student's output distribution in those states toward the teacher's. The report also reuses the perceptual loss from Vidu S1 to reduce mode collapse and keep generation diverse. The objective is summarized as:

```text
L_SRF = L_DMD(replayed outputs) + L_perc(replayed outputs)
```

`replayed outputs` are the student's predictions on the re-noised self-generated trajectory. The objective does not ask the student to reproduce its own flawed video pixel by pixel, and it does not guarantee that every trajectory converges to one reference answer. The teacher distribution and the perceptual constraint set the direction of optimization; the self-generated history makes those constraints apply to states that actually occur at inference.

Two rounds of preference optimization come on top of SRF. The bidirectional stage uses diffusion DPO to improve visual quality, expression, motion naturalness and audio-visual synchronization, which gives the later causal stage a stronger teacher. The streaming stage uses Streaming NFT (Negative-aware Fine-Tuning), which likewise performs a detached rollout and then replays sampled trajectories for reward-based optimization. Training keeps S1's sink blocks, sliding window and noisy KV caches throughout. The final model benefits from SRF, preference optimization and the data improvements of the previous section at once, and since the report has no per-component ablation, the final scores cannot show how much SRF contributes on its own.

## Detail comes from a one-step Refiner, and frame rate is not reaction speed

S1 produced real-time output at 540p; S2-Avatar raises the real-time resolution to 720p, and the report still gives a frame rate of 25 to 42 FPS. Detail starts with clear training data. Compression varies widely across sources, and heavily compressed 1080p footage still has blurry texture and visible artifacts, so selection does not rely on nominal resolution. It checks whether resolution, frame rate, codec, pixel format, bit depth and bitrate are consistent with each other, then uses expert models to assess texture, edge sharpness and compression artifacts, combined into a weighted quality score. (§2.1, PDF p.5.)

At inference, the causal backbone keeps running at low resolution, followed by a one-step super-resolution Refiner that works in latent space. It upsamples the backbone's low-resolution latent, adds noise at a fixed timestep `t_r`, and predicts the corresponding high-resolution latent. (§2.2, Eq. 5, PDF p.7.)

```text
zⁱ_tr = (1 − t_r) · U(x̂ⁱ₀,LR) + t_r · εⁱ,   εⁱ ~ N(0, I)
```

`U` is spatial upsampling in latent space, and `x̂ⁱ₀,LR` is the backbone's low-resolution result for segment i. The two modules also read different histories. The backbone reads a history cache with higher noise, and the Refiner reads a high-resolution history cache with lower noise, written as `τB > τR` in the report; the idea comes from the TwinCache design in S1.

The report's reason for giving the backbone the noisier history is that high-noise history is insensitive to high-frequency artifacts. What the backbone takes from it is mostly coarse motion and long-range structure, so a small flaw in an earlier segment is less likely to be carried all the way down the stream. The Refiner has the opposite job. It has to keep clothing texture, local appearance and identity details, and for that it needs cleaner high-resolution context. The two caches assign the continuation of motion and the restoration of detail to two separate paths.

<TechGraph src="/images/posts/vidu-s2-realtime/dual-cache.svg" title="MOTION AND DETAIL USE DIFFERENT HISTORIES" alt="A low-resolution causal backbone reads higher-noise history for motion and structure. A one-step Refiner reads lower-noise, high-resolution history to restore detail, followed by VAE decoding." caption="Author-created diagram of the low-resolution backbone, one-step Refiner, and two histories with different noise, based on §2.2 of the main report. No undisclosed internal sizes or timings are assumed." />

This division saves the backbone repeated work at high resolution, at the cost of one more computation step and one more history to maintain. Nor is the history unbounded. Following S1, the backbone always keeps a few blocks from the start (sink blocks) and otherwise only a sliding window of recent content, so the cache has a size limit. A video that can keep being generated does not imply a model that can precisely recall a detail from long ago, which is one reason states like the cup are written into the prompts explicitly by the agent.

25 FPS means producing 25 frames per second. Playback also consumes 25 frames per second, so as long as production keeps up over time the buffer never runs dry. That is a throughput requirement. Users also care about reaction: how long it takes, after they say “smile”, for the first smiling frame to reach the screen. That interval may include speech transcription, the agent writing a prompt, waiting for the current segment to finish, denoising the next segment, the Refiner, VAE decoding and network transfer. `1 / 25 = 40 ms` is only the gap between two adjacent frames, and the duration of that chain cannot be derived from it.

The report itself separates the two. Its internal digital-character evaluation lists three audio chunk sizes of 160, 320 and 480 milliseconds, interruption and recovery, five-minute stability, end-to-end latency and cost, and its evaluation protocol states that frame-rate or latency claims on product pages do not replace measured results. Yet the results published in the report contain no figures for end-to-end latency or cost, and no GPU model, GPU count or concurrency corresponding to S2's 720p at 25 to 42 FPS. The introduction mentions that S1 outputs 540p at up to 42 FPS on regular consumer GPUs; that hardware result cannot simply be carried over to S2.

The acceleration methods in §2.3 are easiest to read by the overhead each one targets. Attention uses a different approximate implementation per layer (SageAttention, SpargeAttention or Sparse-Linear Attention), approximating more aggressively in layers less sensitive to precision. Linear layers use per-block W8A8 quantized matrix multiplication, because when a whole tensor is quantized at once, a few outliers take up the entire quantization range. Many short operators are fused into custom kernels and then captured once as CUDA Graphs and replayed, which removes launch and synchronization overhead. Across GPUs, Ulysses-style context parallelism shares out the computation, and the tensors exchanged between cards are quantized to cut communication. (§2.3, PDF pp.7 to 8.) These descriptions show where acceleration happens, but the report does not give the time each method saves on its own, so they cannot be used to estimate the deployment cost of a single session.

## In live editing, each frame reads only the source frame at the same moment

S2-Editing faces a different kind of input: a source video that keeps arriving, such as the feed from the user's own camera. The task might be changing a piece of clothing while the person is raising a hand, and the output should raise the hand at the same moment. The reference image supplies the target appearance; the source video supplies motion, layout and timing.

The report encodes the source video and an optional reference image as conditioning tokens, concatenates them with the noisy target-video tokens and feeds them into a DiT, with condition-specific RoPE encodings for spatial and temporal positions. The key restriction is between source and target: each target frame interacts only with the source frame at the same moment, while the reference image is visible to every target frame. This structure is first learned with bidirectional training, then made causal along the same route as the Avatar model, with mixed forcing and finally SRF. (§3.2, PDF pp.10 to 11.)

<TechGraph src="/images/posts/vidu-s2-realtime/aligned-editing.svg" title="SOURCE MOTION IS READ AT THE SAME TIME" alt="Source frames s1, s2, and s3 correspond to target frames y1, y2, and y3. Cross-time source mixing is restricted. A reference provides appearance, while target history remains causal." caption="Author-created diagram of frame-aligned source access and the distinct roles of references and target history, based on §3.2 and the Introduction of the main report." />

If target frames could read earlier and later source frames freely, the model might mix poses from different moments, and the output motion would drift out of step with the input. Frame alignment makes the source frame at the same moment the anchor for the current motion. That is the design rationale; the report does not prove that it never fails under occlusion or fast motion.

The roles of the caches change too. The report says each source frame is consumed together with its corresponding target frame and is not kept in the cache, while the target stream still keeps the causal history it needs for generation. So the source video staying out of the cache does not mean editing needs no cache. The reference image stays readable throughout, which lets the new appearance persist as the motion moves on.

Latency is more noticeable in editing, because users compare their own movements directly with the output. The VAE encoder, backbone, Refiner and VAE decoder of S2-Editing are not all busy at the same moments during streaming inference, and giving each module a fixed group of GPUs leaves cards idle. The report instead schedules them on a shared timeline, so that when the backbone or Refiner does not need certain GPUs, the encoder or decoder can borrow them. (§3.3, PDF p.11.)

This conditioning structure needs paired training data. From the videos filtered through the Avatar data pipeline, the report applies stricter criteria and balances the label distribution to select 800,000 videos, then takes four disjoint subsets of 200,000 each to build data for style transfer, subject replacement, background replacement and virtual try-on. The style-transfer data is made like this: a model such as NormalCrafter first estimates a surface-normal video from the original, and a model is trained to reconstruct the original video from the normal video plus one reference frame. To generate data, the reference is replaced with a stylized image while the normal video stays the same, so the resulting video keeps the original's structure and motion and takes on the new style. The report says this model generalizes to more than 50 photorealistic and non-photorealistic styles. The other three tasks follow a similar idea with task-specific editing models, supplemented by outputs from several open-source editing models, since no single model is best on every task; the candidate results are then filtered and compared before selection. (§3.1, PDF pp.9 to 10.)

One detail of the editing-prompt annotation is designed specifically for streaming. The VLM that writes the descriptions does not read the source video. It only states the editing task, the attributes of the reference image relevant to that task, and the requirement to preserve everything outside the edit. If the VLM had seen the whole source video while annotating, the text condition could describe frames that have not yet arrived at inference time, and during training the model could peek at the future through the text.

At the end, the report connects both pipelines to a VR headset. Monocular video generated by the Avatar model or produced by editing first gets a per-frame depth estimate, which is converted to horizontal disparity, and the monocular frame is treated as a center view and warped toward each side to obtain left- and right-eye views. Holes that warping leaves along object edges and in newly exposed regions are filled with lightweight processing, and depth estimates are kept steady over time to reduce flicker in the perceived depth. Video that is already stereo is handled by joining the left and right views side by side into one wide stream, editing it once with the same set of references, and splitting it back into the two eyes. (§4, PDF pp.11 to 12.)

<Figure src="/images/posts/vidu-s2-realtime/spatial-video.png" alt="Vidu S2 spatial-video examples showing paired left- and right-eye views from Avatar and Editing." caption="Source: main report, Figure 13, PDF p.21. Faithfully cropped without modification." />

Disparity between the two eyes creates a sense of depth, but synthesizing two views from a single center view does not build a 3D scene that a user can freely move around in. How to generate regions that were hidden before the user turned their head, and how to keep objects consistent across viewpoints, both need additional mechanisms. The report itself lists extending fixed-view spatial video to panoramic spatial video that users can explore by turning their heads as a future direction. It also notes that spatial video in a headset demands higher resolution and lower end-to-end latency than ordinary real-time video: in camera passthrough mode, high latency makes head motion and the displayed view fall out of sync.

## Leading scores, and instructions left unfinished

The report's own evaluation and the later StreamEval measure different things and need to be read separately.

### Public benchmarks and human ratings in the report

For digital characters, Table 1 of the main report compares more than a dozen systems on StreamAV-Bench. S2-Avatar has the best value in all nine metrics listed, covering visual appeal and quality, audio quality, semantic alignment and synchronization between audio and video, fulfillment of audio-side instructions, and subject and background consistency. The report states that the table is the available Gemini-MLLM subset. The original [StreamAV-Bench](https://liukqchoco.github.io/StreamAVBench/) has 32 fine-grained dimensions, so nine best columns cannot be stretched into first place on every dimension of the full benchmark. (Table 1, PDF p.14.)

Editing is evaluated on four public benchmarks. On Sparkle-Bench, S2-Editing has an Overall of 3.74, against 3.67 for Decart-Lucy2.5, the streaming baseline in the table. The ViViD test set for virtual try-on uses VFID I, a distance between the feature distributions of generated and reference videos where lower is better: S2 scores 9.9515 and CatV2TON 19.5131. These figures support S2 leading on those benchmarks. Gaps on different metrics cannot be added up, and halving a distribution distance does not mean the result looks twice as good. (Tables 2 to 4, PDF pp.15 to 16.)

Quality over longer generation is assessed with human rating curves. In the figure below, the horizontal axis is generation length from 10 to 90 seconds and the vertical axis is the mean rating on a 1 to 5 scale, with Vidu S1, Runway, HeyGen and PixVerse as the comparison systems. The thing to read is whether the curves hold up as length increases, rather than who scores highest on the shortest clips.

S2's curves stay high on all five dimensions, but curves that stop at 90 seconds cannot prove the absence of drift over arbitrarily long streams, and they do not isolate the effect of SRF. ### StreamEval: task-board leads, with execution still difficult

The first version of StreamEval appeared on October 20, and the current one is v3 from October 26. It asks a different question: as inputs arrive over time, can a system carry out new requests while keeping unchanged what should not change? v3 has 300 scripted test cases, 60 per task, lasting 15 to 300 seconds and grouped into five equally weighted duration strata, and each model runs every case three times. Its five tasks are ranked separately, scores from different tasks are not comparable, and there is no cross-task overall ranking. On the official leaderboard checked on October 31, 2026, the systems ranked first by Overall in each task were the following.

| Task | Leader | Overall |
| --- | --- | ---: |
| Digital-human dialogue | Vidu S2 Avatar | 93.98 |
| Digital-human performance | Vidu S2 Avatar | 81.71 |
| World generation | MemFlow | 33.36 |
| Instruction video editing | Vidu S2 Editing | 45.43 |
| Reference video editing | Vidu S2 Editing | 39.02 |

Source: [StreamEval website](https://streameval.ai/), checked 2026-10-31; the paper is cited as [v3](https://arxiv.org/html/2610.28402v3). The digital-human tasks add 5 points for systems that support custom avatars, so dialogue's 93.98 is a quality total of 88.98 plus 5, and performance's 81.71 is 76.71 plus 5; the other three tasks have no such bonus. In world generation, MemFlow is followed by Rolling Forcing at 33.01.

The individual metrics behind the totals say more about how far interaction has come. As StreamEval defines them, Following measures control events in which the requested gaze, expression, pose or gesture is carried out on the specified target, and Edit Success requires one edit to satisfy scope, active state, deadline, persistence and protected content at once. Scores are averaged first over the three repeats, then over cases within each duration stratum, and finally over the five strata. S2's Following in the digital-human performance task is 36.90 and its Edit Success in reference editing is 15.00; it ranks first overall, and these two metrics are still low. In these scripts, a stable picture and a completed instruction are two separate things: a character can keep the same face and speak continuously without raising the requested hand on time, and an edited video can preserve the source motion closely without ever putting on the clothing from the reference. The scores apply to StreamEval's own scripts and judging rules and are not general success rates for commercial use.

Ranking first overall does not mean being best in every column. In the performance task LiveTalk's Quality is 71.27, above S2's 63.68; in dialogue, Tavus reaches 94.44 on audio-visual synchronization against S2's 84.87; in instruction editing, JoyAI-Video-Edit's Preservation is 83.33 against S2's 60.93. Choosing a system for a particular use means looking at the column that matters most for it, not at Overall.

Nor does StreamEval count as fully independent third-party validation. Among the team members listed in §7 of v3, Jungang Li, Kai Jiang, Jintao Zhang, Jianfei Chen and Jun Zhu are all authors of the Vidu S2 report, and the acknowledgments thank Shengshu Technology for compute. It offers a different set of test questions and scoring rules, which is useful, but it cannot stand in for measurements made by people unconnected to the Vidu team.

What can be confirmed is that S2's video stays stable over stretches of around 90 seconds and that it leads on the report's public benchmarks and on StreamEval's task boards. The two things that matter most in the opening example, how long a smile takes to appear after the user says “smile” and whether the cup is still in hand during it, are not measured directly by any of the available material. The report includes end-to-end latency in its internal evaluation but publishes no figure, and StreamEval's execution scores come from its own scripts, showing only that carrying out controls on time remains hard on benchmarks of this kind.
