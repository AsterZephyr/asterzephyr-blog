Ranking models in recommendation systems do two things: feature interaction (crosses between user profiles, item attributes, and context) and sequence modeling (capturing interest evolution from user behavior history). Over the past decade, these two tasks have been handled by two independent modules—the DNN/FM family for feature interaction, and the DIN/SASRec family for sequence modeling. The two modules iterate independently, scale independently, and are maintained independently.

Between 2024 and 2025, ByteDance pushed both of these lines to their respective limits: Wukong (KDD 2024) scaled feature interaction to unprecedented parameter counts using an FM architecture, and LONGER (WWW 2025) extended user behavior sequence modeling to 10,000+ steps. Both lines delivered significant online gains. But when the team tried to scale both modules simultaneously, they hit a structural bottleneck: **the parameter counts and compute of two independent modules are additive, serving latency and cost stack on top of each other, and their understanding of the same user representation is completely siloed.**

[OneTrans](https://arxiv.org/abs/2510.26104) (WWW 2026) is ByteDance's answer: use a single Transformer backbone to simultaneously handle feature interaction and sequence modeling, with unified tokenization and mixed parameterization to address the fundamental differences between structured features and behavior sequences. The online A/B test result is a per-user GMV increase of **5.68%**. This number is remarkably large for incremental optimization in recommendation systems—typically a ranking model iteration delivering 0.3–0.5% is worth a full rollout.

This article is organized around four questions: what OneTrans is, why pursuing a unified architecture is the right path, what ROI it ultimately delivers, and where to start if you want to learn more about this direction.

## What Is OneTrans

### The Two Core Tasks of Recommendation Ranking Models

Let's first clarify what each of these two tasks does.

**Feature Interaction**: On the user side there are profile features like age, gender, city, and device; on the item side there are attribute features like category, price, and brand; and there are context features like time, location, and network environment. The crosses between these features contain recommendation signals—for example, "25-year-old female + beauty category + evening time slot" is a meaningful cross pattern. The FM, DeepFM, and DCN family of models are centered on efficiently learning these crosses.

**Sequence Modeling**: The items a user has clicked, purchased, and browsed over a period of time form a behavior sequence. Capturing the evolution of user interests from this sequence—for instance, a user recently shifting from browsing phones to browsing earphones signals an interest migration—is the job of the DIN, DIEN, SASRec, and BERT4Rec family of models.

The traditional approach is to concatenate the two modules: the sequence modeling module outputs a user interest vector, which is concatenated with the feature interaction module's output and fed into a final MLP to predict click-through rate.

### OneTrans's Four Core Designs

OneTrans's goal is to make a single Transformer do both tasks well. But naively concatenating all features and behavior sequences into one sequence and feeding it into a Transformer doesn't work—structured features and behavior sequences have fundamentally different statistical properties. OneTrans uses four designs to address these differences.

**Design 1: Unified Tokenizer.** The inputs to a recommendation system are heterogeneous: some are categorical (gender, city), some are numerical (price, age), and some are sequential (behavior history). OneTrans designs a unified tokenizer that converts all these heterogeneous inputs into a unified token sequence. Specifically, each attribute field is assigned a token position, and field-specific embeddings map different types of raw values into the same vector space. Each historical item in the behavior sequence is also mapped to a token. Ultimately, a recommendation request becomes a unified sequence composed of "attribute tokens + sequence tokens."

**Design 2: Mixed Parameterization.** This is OneTrans's most critical innovation. Sequence tokens (items in behavior history) naturally share strong commonalities—they all represent "items the user has interacted with" and should share parameters to learn intra-sequence dependencies. But non-sequence tokens (user profiles, item attributes, context) have very different statistical distributions from each other—"age" and "category" require completely different transformations to capture their respective signals.

OneTrans's solution: at each Transformer layer, sequence tokens share a single set of QKV projections and FFN parameters; non-sequence tokens have independent parameters for each token position. This way, sequence tokens can efficiently perform self-attention (like SASRec), while non-sequence tokens maintain sufficient discriminative capacity (like DCN).

This design shares the same idea as the Token-Aware FFN/LN from GPR discussed in the previous blog post: **heterogeneous tokens cannot be processed with uniform parameters.** Two independent industry papers converged on the same conclusion.

**Design 3: Pyramid Stack.** Behavior sequences can be very long (10,000+ steps), but Transformer self-attention complexity scales quadratically with sequence length. OneTrans progressively prunes the number of sequence tokens between Transformer layers—lower layers use the full sequence to capture fine-grained patterns, while higher layers retain only the most important sequence tokens for global aggregation. Similar to the Pyramid Vision Transformer in computer vision, this hierarchical structure balances precision and efficiency.

**Design 4: Cross-Request KV Caching.** This is OneTrans's key optimization for serving. In traditional architectures, the user-side representation must be recomputed for every candidate ad for the same user—if there are C candidates, the user side is computed C times. OneTrans leverages the Transformer's KV cache mechanism to precompute the Keys and Values of the user side (profile + behavior sequence) and share this cache across all candidates for that user. User-side computation drops from O(C) to O(1). This is exactly the same idea as prefill + decode separation in LLM inference.

## Why Pursue the Unified Architecture Path

### ByteDance's Evolution: From Scaling Separately to Discovering the Ceiling

To understand OneTrans's motivation, you need to first look at the scaling path ByteDance walked from 2023 to 2025.

**Phase 1: Scaling feature interaction and sequence modeling separately.**

In 2024, [Wukong](https://arxiv.org/abs/2403.02545) (KDD 2024) scaled up the feature interaction module using stacked factorization machines. The core finding was that feature interaction in recommendation systems also exhibits a scaling law—as model parameter count increases, prediction accuracy continues to improve without saturating.

Around the same time, [LONGER](https://arxiv.org/abs/2412.17135) (WWW 2025) extended sequence modeling from a few hundred steps of behavior history to 10,000+ steps. Longer sequences covered more user interest shifts and delivered significant incremental gains.

Both lines delivered solid online improvements.

**Phase 2: Discovering the ceiling of scaling separately.**

When the team tried to simultaneously use a larger Wukong and a longer LONGER, they ran into three problems:

First, **parameter counts and compute are additive**. The feature interaction module has its own parameters, and the sequence modeling module has its own parameters; their parameter counts and FLOPs add up directly. If each scales 2×, total compute is 4×.

Second, **serving complexity is additive**. The two modules have their own caching strategies, their own inference optimizations, and their own resource allocations. Operational costs grow linearly with the number of modules.

Third, and most fundamentally—**the two modules' understanding of user representation is siloed**. The feature interaction module's learned signal "this user has a preference for beauty categories" and the sequence modeling module's learned signal "this user has been looking at earphones recently" have no interaction until the final concatenation. The concatenation layer's MLP must rediscover the correlations between two independent representations—this is an unnecessary information bottleneck.

### Three Structural Advantages of Unification

OneTrans's unified architecture directly addresses all three problems above.

**Advantage 1: Shared representations mean feature interaction and sequence modeling reinforce each other.** In OneTrans's Transformer, sequence tokens and non-sequence tokens interact through the attention mechanism at every layer. This means sequence modeling can leverage item attributes to understand behavior ("the user clicked a 200 RMB pair of earphones" carries more information than "the user clicked item_37291"), while feature interaction can leverage behavioral context to understand attributes (the signal "the user is interested in the phone category" can be cross-validated against the user's recent browsing sequence). Ablation experiments confirm this: removing either sequence tokens or non-sequence tokens causes significant performance degradation, and the degradation is larger than the gap between the respective standalone models—indicating that joint modeling produces a 1+1>2 effect.

**Advantage 2: Scaling one model is cheaper than scaling two.** There is only one set of parameters, one forward pass, one KV cache, and one inference optimization pipeline. Scaling 2× means 2× compute growth, not 4×. Training also requires only one data pipeline, one training job, and one hyperparameter search.

**Advantage 3: Cross-Request KV Caching is naturally enabled.** In the unified architecture, all user-side information (profile features + behavior sequences) is processed in the first half of the same Transformer. This computation result can naturally be shared via KV cache across all candidates. In a separated architecture, this kind of sharing requires each module to implement its own caching mechanism, leading to higher engineering complexity.

### Industry Consensus: Unified Architecture Is the Direction

OneTrans is not an isolated case. Internally at ByteDance, HyFormer (a hybrid unified architecture) was pursuing a similar unification effort around the same time. Kuaishou's [OneRec](https://arxiv.org/html/2506.13695v4) arrived at the same destination from a different technical path—using a generative recommendation paradigm to similarly achieve an end-to-end unified model.

Looking more broadly, the evolution path of recommendation systems is highly consistent with NLP: first, specialized models each did their own thing (word2vec for embeddings, LSTM for sequences, CNN for feature extraction), and eventually a single unified Transformer architecture replaced them all. Recommendation systems are walking the same path.

## The Final ROI Results

### OneTrans's Online Numbers

OneTrans is fully deployed in ByteDance's e-commerce recommendation scenario. Online A/B test results:

| Metric | Improvement |
|:-----|:---------|
| Per-user GMV | **+5.68%** |
| Scaling validation | Near log-linear performance improvement as parameter count increases |
| Inference efficiency | Cross-request KV caching significantly reduces redundant user-side computation |

The paper also validates that OneTrans consistently outperforms baselines including Wukong, LONGER, and RankMixer on offline metrics—not better on some metrics and worse on others, but uniformly superior.

### Other Outputs from ByteDance's Scaling Roadmap

OneTrans is not the only output from ByteDance's scaling experiments. Several other notable numbers come from the same technical line:

**TokenMixer-Large / RankMixer**: Scaling a token-mixing architecture (similar to MLP-Mixer) to the 7B–15B parameter level, achieving +1.66% online orders and +2.98% GMV. This experiment validated continued returns for recommendation models at large parameter scales, but also exposed serving cost challenges—serving a 15B-parameter recommendation model within latency budgets requires extensive engineering optimization.

**[UG-Sep](https://arxiv.org/abs/2502.14267)** (CIKM 2025): Specifically addressing serving efficiency for unified models. The core idea is to separate and preprocess user-side (User) and item-side (Good/Item) computation, reducing the real-time online computation burden. This is a more aggressive version of OneTrans's Cross-Request KV Caching concept.

### Kuaishou's OneRec as a Reference Point

Kuaishou's OneRec arrived at a similar goal—an end-to-end unified model—from a different technical path (generative recommendation):

| Metric | Value |
|:-----|:-----|
| App Stay Time | +0.54% (main app) / +1.24% (lite version) |
| QPS share | Handles 25% of total QPS |
| OPEX | Only **10.6%** of the traditional pipeline |

The most noteworthy number from OneRec is not the effectiveness metric but the OPEX figure. Over 50% of the traditional pipeline's operational cost is spent on communication and storage between multiple modules; a unified model directly eliminates this overhead.

### What These Numbers Mean

Recommendation systems are a battlefield of incremental optimization. On systems with hundreds of millions of daily active users like ByteDance's and Kuaishou's, a single ranking model iteration delivering 0.3–0.5% metric improvement is already worth a full rollout. OneTrans's 5.68% GMV increase and OneRec's OPEX reduction to 10.6% are not achievable through routine iterations—they come from paradigm shifts at the architecture level, not fine-tuning at the model level.

This also explains why both ByteDance and Kuaishou are investing substantial engineering resources to advance unified architectures. This is not a one-time gain but rather opens up a new scaling frontier: unified models can continuously achieve near log-linear performance improvements by increasing parameter count, whereas the scaling efficiency of traditional separated architectures is much lower.

## If You Want to Learn This Direction, How to Get Started

### Recommended Learning Path

This direction spans three knowledge domains: recommendation systems, Transformer architecture, and large-scale systems engineering. Below is a path from fundamentals to the frontier.

<TechGraph src="/images/posts/OneTrans-字节跳动如何用一个Transformer统一推荐系统的特征交互与序列建模/learning-path.svg" title="Learning Path" caption="From recommendation basics → Transformer applications → Scaling → Unified architecture" />

**Level 1: Recommendation System Fundamentals.** Understand the basic framework of recommendation system ranking models. Focus on two key papers: DIN (Alibaba, 2018) explains why attention mechanisms are used for sequence modeling, and DeepFM/DCN (Huawei/Google) explains why explicit feature crossing is needed. These two papers are the foundation for all subsequent work. If time is limited, just reading DIN and DCN v2 is enough.

**Level 2: Transformer Applications in Recommendations.** SASRec (2018) introduced self-attention into recommendation sequence modeling, and BERT4Rec (2019) experimented with bidirectional attention. These two papers addressed the paradigm upgrade of sequence modeling. Also read AutoInt (2019) to understand how Transformers perform feature interaction—this is the intellectual origin of OneTrans's unification of the two.

**Level 3: Scaling.** Wukong (ByteDance, KDD 2024) and LONGER (ByteDance, WWW 2025) are must-reads. Wukong proved that recommendation systems have a scaling law, and LONGER proved that longer sequences continuously yield gains. Understanding these two papers explains why OneTrans's unified scaling is more efficient than scaling each component separately.

**Level 4: Unified Architecture.** Only at this level should you read OneTrans (WWW 2026) and OneRec (Kuaishou, 2025). With the accumulation from the previous three levels, OneTrans's design motivations and technical choices will be crystal clear—every problem it solves can be traced to a corresponding limitation in the earlier papers.

### Supplementary Reading from an Engineering Perspective

If your role leans more toward engineering than algorithms, a few additional papers are worth reading:

- **UG-Sep** (ByteDance, CIKM 2025): Specifically discusses efficient serving for unified models, including user-side/item-side separate pre-computation, KV cache strategies, etc. Very helpful for understanding how to serve large models in recommendation systems.
- **GR4AD's LazyAR** (Kuaishou, 2026): Discusses optimization of inter-layer dependency asymmetry in Transformer inference, doubling QPS with only -0.15% revenue loss. Clean idea, low implementation cost.
- **vLLM / SGLang related documentation**: The KV caching strategies for unified recommendation models are highly similar to KV cache management in LLMs. Understanding concepts like PagedAttention and prefix caching directly helps with serving optimization for recommendation models.

### Final Thoughts

Recommendation systems are undergoing a paradigm shift similar to what NLP experienced: moving from assembling specialized modules toward unified Transformer architectures. OneTrans's 5.68% GMV lift and OneRec's 10.6% OPEX prove the commercial value of this direction. But more importantly, unified architectures open up space for scaling—for the first time, recommendation systems have the opportunity to achieve predictable performance improvements by continuously increasing model scale, just like LLMs.

For practitioners, the window of opportunity in this direction is narrowing. ByteDance and Kuaishou have already completed the full pipeline from paper to full-scale deployment. The next competitive battleground is not "whether to adopt a unified architecture," but "who can scale the model larger and serve it faster."
