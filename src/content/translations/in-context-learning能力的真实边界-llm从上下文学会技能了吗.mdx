"In-context learning" has become one of the core selling points of LLMs since 2022. The few-shot capabilities demonstrated in the GPT-3 paper—give the model a few examples and it can perform new tasks—led many to believe that LLMs can "learn from context." But this narrative has an underappreciated crack: when the context isn't a simple set of input-output example pairs but rather a 50-page technical specification or a complex set of business rules, can LLMs really "learn" how to execute from it?

Ctx2Skill (arXiv:2604.27660) confronts this question head-on. Its core finding is: simply stuffing long context into an LLM isn't enough—you need an explicit "skill extraction" process that transforms the implicit rules and procedures in the context into actionable natural-language skill descriptions. What's more interesting is that this skill extraction process itself requires no human annotation and can be accomplished automatically through multi-agent self-play.

## Problem Definition: Context Learning ≠ In-Context Learning

Let's first clear up a conceptual confusion. What the industry commonly calls "in-context learning" (ICL) usually refers to few-shot prompting: give the model a few examples, and the model infers the pattern and applies it to new inputs. But what Ctx2Skill addresses is a harder problem: **context learning**—learning the knowledge needed to solve problems from a long, complex context document.

<TechGraph src="/images/posts/in-context-learning能力的真实边界-llm从上下文学会技能了吗/icl-vs-context-learning.svg" title="ICL vs Context Learning" caption="Traditional few-shot ICL patterns are clear and inferable, while Context Learning requires extracting implicit rules from long documents" />

The distinction is: in few-shot ICL, the "context" consists of a few structured example pairs where the pattern is clear and inferable; in context learning, the "context" is an unstructured long document where rules are embedded in narrative and require multi-step reasoning to apply.

This is a core pain point in real-world scenarios. The typical challenge facing enterprise RAG systems is exactly this: the relevant documents are retrieved, but the LLM can't correctly extract and apply complex rules from them. It might miss a condition, confuse the order of operations, or "hallucinate" rules that don't exist in the document.

## Ctx2Skill's Core Approach: Inference-Time Skill Augmentation

Ctx2Skill's core idea is an intermediate step: instead of having the LLM answer questions directly from raw context, it first extracts "skills" from the context, then uses those skills to guide LLM reasoning.

"Skills" here are defined as: natural-language rules and procedural descriptions distilled from the context. For example, given a complex refund policy document, skills might be:

- "If the purchase date exceeds 30 days and the product is unopened, apply Policy A"
- "When calculating the refund amount, first deduct shipping costs, then prorate accordingly"
- "Customers with more than 3 consecutive refunds require manual review"

These skills make the rules implicit in long documents explicit and actionable.

But skill extraction faces two challenges:

1. **Annotation cost**: Manually annotating skills for long, complex documents is extremely expensive
2. **Lack of feedback**: There's no external oracle to tell you whether the extracted skills are correct and complete

Ctx2Skill's solution is a **multi-agent self-play loop**—requiring no human annotation or external feedback, the system discovers skills through self-play.

## Multi-Agent Self-Play: Self-Evolving Skill Discovery

<TechGraph src="/images/posts/in-context-learning能力的真实边界-llm从上下文学会技能了吗/self-play-loop.svg" title="Multi-Agent Self-Play Loop" caption="Challenger-Reasoner-Judge loop paired with Proposer-Generator skill evolution, Cross-time Replay prevents adversarial collapse" />

The self-play loop consists of three Agents:

**Challenger**: Generates probing tasks and scoring criteria. Its goal is to discover blind spots in the current skill set—if the Reasoner can easily pass all tasks, the Challenger isn't "hard" enough.

**Reasoner**: Uses the current skill set to guide reasoning and attempts to solve the tasks generated by the Challenger. Its goal is to apply skills to correctly complete tasks.

**Judge**: Provides binary feedback—whether the Reasoner's answer is right or wrong. It doesn't provide detailed error analysis (that's other Agents' job).

When the Reasoner fails, two auxiliary Agents step in:

**Proposer**: Analyzes failure cases and pinpoints the problem—is a skill missing? Is an existing skill description not precise enough? Are there conflicts between skills?

**Generator**: Based on the Proposer's analysis, synthesizes new skills or updates existing ones.

Key design: **Both the Challenger and Reasoner evolve through accumulated skills**. Skills on the Challenger's side teach it how to generate more discriminating questions; skills on the Reasoner's side teach it how to better solve problems. This isn't a simple "pose questions–answer questions" loop but a co-evolution of both sides.

## Cross-time Replay: Preventing Adversarial Collapse

Self-play systems have a known failure mode: **adversarial collapse**. The Challenger, trying to make the Reasoner fail, starts generating increasingly extreme questions; the Reasoner, trying to pass extreme questions, starts accumulating over-specialized skills. Eventually both sides drift away from the original task distribution—skills become precise but brittle, unable to generalize to normal tasks.

Ctx2Skill introduces a **Cross-time Replay** mechanism to prevent this degradation:

1. Retain "representative cases" from different points in time
2. Use these representative cases to back-test all historical versions of the skill set
3. Select the skill set that performs most balanced (rather than most extreme) on the representative cases as the Reasoner's final output

This is analogous to population-based training or early stopping in reinforcement learning—instead of selecting the model trained the longest, you select the one with the best generalization ability.

## Evaluation Results: General Capability Enhancement Rather Than Task-Specific Optimization

The paper evaluates Ctx2Skill on 4 context learning tasks from CL-bench, showing consistent improvements in solve rates across different backbone models.

Several noteworthy characteristics:

**Skills are transferable.** Skills generated by Ctx2Skill aren't tied to a specific LLM—extracted skills can be plugged into any language model to improve its context learning ability. This means skills are a model-independent knowledge representation.

**Automatic discovery vs. human annotation.** Without any human intervention, the system discovered effective skill sets through self-play. This demonstrates that skill discovery can be automated, but it also raises a question: how different are automatically discovered skills from those extracted by human experts? The paper doesn't deeply compare this point.

**Long context is the key source of difficulty.** The tasks involve "long, technically dense contexts." This is exactly the core challenge current RAG systems face in production—it's not that you can't find relevant documents, but that once found, you can't reason correctly from them.

## Implications for Engineering Practice

<TechGraph src="/images/posts/in-context-learning能力的真实边界-llm从上下文学会技能了吗/rag-enhanced-flow.svg" title="RAG Flow Comparison" caption="Traditional RAG directly concatenates context to generate answers; the Ctx2Skill-enhanced flow inserts a skill extraction step in between" />

**The value of a middle layer in RAG systems.** The current mainstream RAG pipeline is "retrieve → concatenate context → generate answer." Ctx2Skill points to a possible improvement: inserting a "skill extraction" step between retrieval and generation. Instead of directly feeding raw documents to the LLM, first extract actionable rules from the documents, then use those rules to guide reasoning. This could provide significant value for rule-intensive tasks (compliance checking, policy enforcement, technical specification adherence).

**Self-play as an evaluation generator.** Ctx2Skill's self-play loop is essentially an automatic evaluation generator—it continuously produces new test cases to expose system weaknesses. This approach can be borrowed for quality assurance in any LLM system: use one Agent to continuously generate edge cases, another Agent to judge the system's performance, and drive system improvements through failure cases.

**Skill set = auditable intermediate representation.** Unlike black-box ICL, the extracted skill set is readable natural language that can be audited and modified by humans. This has significant value for scenarios requiring explainability (finance, healthcare, legal)—you can inspect which rules the LLM has "learned," correct erroneous rules, and supplement missing ones.

## Limitations and Open Questions

**Choice of skill granularity.** The paper doesn't deeply discuss skill granularity—is each rule one skill, or is a group of related rules one skill? Too fine-grained increases the retrieval burden; too coarse-grained sacrifices precision. In engineering practice, the optimal granularity likely depends on the specific domain.

**Adaptation to dynamic context.** Ctx2Skill assumes context is relatively static—skill extraction from a document needs to happen only once. But if the context changes continuously (e.g., frequently updated policy documents), does the skill set need incremental updates or complete reconstruction?

**Relationship with long context windows.** As LLM context windows expand to 100K+, does "long-context reasoning" still require explicit skill extraction? Or can a sufficiently large window plus a sufficiently powerful model handle context learning directly? Ctx2Skill's implicit argument is "not enough"—even when the window is long enough, explicit skills still provide value. But this argument needs to be re-validated on stronger models (such as Claude 4, GPT-5).

---

Ctx2Skill's core contribution is not just a specific framework, but the clear articulation of a viewpoint: **ICL's "learning" doesn't happen automatically**. Stuffing context into an LLM doesn't mean the LLM has learned the knowledge in that context. For simple patterns (few-shot example pairs), inference is implicit and sufficient; but in complex scenarios (long documents, multi-step rules, domain-specific procedures), an explicit knowledge extraction and organization step is needed.

For engineers building RAG systems, this means: if your scenario involves applying complex rules rather than just information retrieval, a two-step "retrieve + generate" pipeline may not be enough. Consider adding a "skill extraction / rule extraction" step in between—whether through Ctx2Skill's automated approach or through manually curated structured prompts.
