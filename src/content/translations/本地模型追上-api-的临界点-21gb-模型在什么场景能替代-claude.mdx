On April 16, 2026, Simon Willison wrote on his blog that he had Qwen3.6-35B-A3B running on his laptop draw a pelican, and it came out better than Claude Opus 4.7's version.

This wasn't some carefully designed benchmark—just an SVG drawing task. But precisely because it wasn't a benchmark, it illustrated something more important: on certain tasks, local models have moved past "barely usable" to "genuinely good enough, or even better."

I'm a heavy Claude API user—Agent orchestration, code generation, and long-form writing all go through the API every day. At the same time, I've been running models locally for translation, data labeling, and privacy-sensitive experiments. Using both sides gives me a somewhat different perspective on the question of "can local models actually replace APIs." This article isn't trying to argue that "local models crush APIs"—the reality is far more nuanced. The more practical question I want to answer is: **as of April 2026, which tasks have already crossed the "good enough" line, and which haven't?**

## MoE: Making a 30B Model Run at 3B Speed

The core driving force behind local models catching up to APIs is the Mixture of Experts (MoE) architecture. In traditional dense models, every token passes through all parameters—a 7B model computes 7B operations per token, a 70B model computes 70B. The bigger the model, the slower the inference, and this scaling curve is unfriendly to local hardware.

MoE's approach is to place hundreds of "expert" sub-networks in the FFN layer, activating only a small number of them per token. Qwen3-30B-A3B has 128 experts and activates only 8 at a time, so total parameters are 30.5B but the actual computation per token is only 3.3B. Gemma 4's 26B-A4B version follows a similar idea—25.2B total parameters, 3.8B active parameters.

In other words, MoE decouples "knowledge capacity" from "inference cost." Your model has the knowledge reserves of 30B parameters but only needs the compute of 3B parameters to run.

This logic is very similar to the performance optimization approach I used when building RTB systems: keep only the lightest computation on the bidding decision path, but make sure the feature space behind the model is large enough to guarantee prediction quality. The MoE router is essentially a "hot path selector"—not all knowledge needs to be used on every inference pass; the key is applying the right knowledge to the right tokens.

Of course, MoE has a cost that can't be ignored: although the computation is smaller, all 30B parameters still need to be loaded into memory. Qwen3-30B-A3B quantized with Q4_K_M is about 21GB, which just barely fits within what a 32GB MacBook can run. That's where the "21GB model" label comes from—it's not that the model only has 21GB worth of knowledge, but rather the storage footprint after quantization.

## The Local Model Capability Landscape as of April 2026

Let's look at the data. The local MoE models worth paying attention to right now are mainly two families:

**Qwen3.6-35B-A3B** (Alibaba, April 2026)

The latest version in the Qwen 3 series, supporting seamless switching between "thinking mode" (CoT reasoning) and "non-thinking mode" (fast dialogue). 128 experts with 8 activated, native 32K context support, extendable to 128K via YaRN. In Simon Willison's tests, it outperformed Claude Opus 4.7 on SVG creation tasks. Multilingual capabilities and tool calling are also strong points.

**Gemma 4 26B-A4B** (Google DeepMind, April 2026)

Also an MoE architecture with 128 experts activating 8 plus 1 shared expert, supporting 256K context. The benchmark numbers are quite impressive:

| Benchmark | Gemma 4 26B-A4B | Gemma 3 27B (comparison) | Description |
| --- | --- | --- | --- |
| AIME 2026 | **88.3%** | 20.8% | Math competition reasoning |
| LiveCodeBench v6 | **77.1%** | 29.1% | Code generation |
| MMLU Pro | **82.6%** | 67.6% | Comprehensive knowledge |
| GPQA Diamond | **82.3%** | 42.4% | Graduate-level QA |

Gemma 4 26B-A4B scored 88.3% on AIME 2026—this is a model with only 3.8B active parameters performing at this level on a math competition. Last year's Gemma 3 27B (dense) managed only 20.8%. The cross-generational improvement exceeds 4×, with MoE architecture and thinking mode being the main contributors.

An even more extreme experiment comes from Dan Woods: he ran Qwen3.5-397B-A17B on a 48GB M3 Max MacBook Pro—a model with 397 billion parameters. The method was storing expert weights on the SSD and streaming active experts into memory on demand per token, while keeping the non-expert portion (5.5GB) resident in RAM. Speed was 5.5 tokens/s, dropping to 4.36 tokens/s with 4-bit quantization. Not fast, but the mere fact of running a 397B parameter model on a laptop was unimaginable a year ago.

## The "Hidden Costs" of Local Inference: Running Doesn't Mean Running Correctly

Georgi Gerganov, the author of llama.cpp, said something very important in March 2026:

> "The main issues people run into with local models today mostly revolve around subtle differences in harness and chat template. Sometimes it's purely inference bugs. From user input task to final output, there's a long chain of components in between, and this chain is not only fragile—it's developed by different teams independently. Integrating the full stack is hard, and the results you're currently observing most likely still contain subtle errors somewhere in the chain."
>

This passage gets at the most overlooked problem with local inference. When you call the Claude API, Anthropic handles all the tokenization, chat templates, sampling strategies, and system prompt processing for you. You send a request, get a result back, and all the complexity in between is encapsulated.

But local inference doesn't work that way. The chain from model file to final output is much longer:

1. **Model format**: Raw weights → GGUF quantization → loaded into the inference engine
2. **Chat Template**: Every model has its own special tokens and conversation format. A single `<|im_start|>` in the wrong place can make model behavior go haywire
3. **Sampling strategy**: The combination of temperature, top-p, and repetition penalty—different engines have different defaults
4. **Tool calling format**: There's no unified standard for tool calling in local models. Qwen, Gemma, and LLaMA each use their own format
5. **Frontend applications**: LM Studio, Ollama, and Open WebUI each have their own request handling and prompt injection

Every link in the chain can introduce bias. You might not notice it in a single generation, but in a multi-step Agent pipeline, these biases accumulate and amplify. A subtle chat template error won't cause problems for a translation task, but it can drop function calling success rate from 95% to 60%.

Quantization itself comes at a cost too. Q4_K_M (4-bit K-Quant Medium) is the most commonly used quantization level today, and in perplexity tests it's typically only 0.1–0.3 higher than full precision. This is virtually imperceptible for most generation tasks. But in scenarios requiring precise reasoning—mathematical proofs, complex logic chains—the noise introduced by quantization can cause wrong branches at critical steps. The smaller the model, the greater the impact of quantization.

To put it bluntly: **local models have caught up in single-output quality, but there's still a gap in engineering reliability.** If your use case is "generate some text and see how it looks," local models are fully capable. If your use case is "automatically run a 20-step Agent workflow where every step must be correct," API is still the safer choice.

## The Economics: When Do Local Models Make Financial Sense

Let's do some concrete math. API pricing falls into three tiers:

| Tier | Representative Models | Output Price (per million tokens) | Positioning |
| --- | --- | --- | --- |
| Flash | Gemini 2.5 Flash, MiniMax M2 | ~$1.2 | High throughput, low cost |
| Sonnet | Claude Sonnet 4.5 | ~$15 | Primary development |
| Opus | Claude Opus 4.7 | ~$75 | Strongest reasoning |

Local hardware: an M4 Max 128GB MacBook Pro costs roughly $5,000 and can run Qwen3-30B-A3B at 30–50 tokens/s with unlimited generation.

<Figure src="/images/posts/本地模型追上-api-的临界点-21gb-模型在什么场景能替代-claude/image 2.png" alt="Cost comparison between local inference and API pricing across monthly token volumes" />

The horizontal axis is monthly output token volume. The local solution's cost is a flat line—hardware amortization of about $140/month (calculated over 3 years), regardless of how much you use it. API costs grow linearly with usage.

Where's the crossover point? Compared to Flash-tier APIs, you need to hit 3–5M tokens/month before local starts paying off. Compared to Sonnet-tier, it's already worth it at 1M tokens/month—roughly a 2–3 month payback. Compared to Opus-tier... well, if you're making heavy daily Opus calls, the local solution pays for itself in the first month.

But this calculation ignores a critical factor: **local models can't replace all API calls, only a subset of them.** You're not going to move your Agent orchestration from Claude to local Qwen. The real decision isn't "go all local" versus "go all API," but rather "which calls can be offloaded to local."

## My Hybrid Strategy

After several months of experimentation, here's what my workflow looks like now:

**Tasks I run locally (Ollama + Qwen/Gemma):**

- Translation and summarization: Chinese-English translation quality is already quite good, responses are fast, no need to wait for API roundtrips
- Format conversion and data cleaning: Markdown formatting, JSON structure conversion, regex extraction—3B active parameters are more than enough for these tasks
- Privacy-sensitive data processing: Analysis and annotation of internal company documents, data never leaves the machine
- Batch labeling and classification: Tagging thousands of text entries—API costs would be too high, a local model can churn through them overnight
- Initial draft generation: First drafts for blog posts and documentation, then polished with Claude afterward

**Tasks I run via API (Claude Sonnet/Opus):**

- Agent orchestration: Claude Code's multi-step tool calling, sub-agent coordination—local models fall far short on reliability
- Long context analysis: 50,000-word codebase reviews, long document comprehension—local model performance degrades sharply at 64K+ context
- Complex reasoning and decision-making: Architecture design discussions, complex bug diagnosis—requires the highest quality reasoning capabilities
- Tasks requiring up-to-date knowledge: API models typically have more recent training data and a more mature tool-calling ecosystem

**The middle ground:**

- Use local models for the first pass of code generation, then have Claude review and correct
- Generate data analysis scripts locally, validate results via API
- Draft documentation locally, use API for final quality checks

The core principle behind this routing strategy is simple: **high reliability requirements go to API, high throughput requirements go local.** It's not a performance issue—it's risk management.

## Local Models Aren't a "Budget Alternative" to APIs—They're a Different Engineering Choice

Having written all this, there are a few conclusions I want to state explicitly.

First, the real value of local models isn't "saving money." Cost savings are just a byproduct. The core value is **control**—data never leaves your machine, no dependency on third-party service availability, no rate limit constraints, freedom to modify inference parameters and prompt formats. For privacy-sensitive scenarios and R&D workflows requiring extensive experimentation, the value of this control far exceeds any cost differential.

Second, the MoE + quantization + Apple Silicon pipeline will continue to close the gap with APIs over the next 12 months. Both Qwen and Gemma completed the leap from "interesting experiment" to "practically usable" within six months. ggml.ai joining Hugging Face means the inference toolchain will become further integrated. Google releasing an iOS-based Gemma runtime app (AI Edge Gallery) signals that on-device phone inference is on its way too.

Third, Agent reliability remains API providers' deepest moat. The "pipeline fragility" Gerganov described isn't something that can be solved in the short term—it requires the entire open-source ecosystem to reach consensus on chat templates, tool calling formats, and inference engines. This isn't just a technical problem; it's a coordination problem. And API providers have a natural advantage here, because they control the entire stack.

One last open question: when local models reach parity with APIs on more and more tasks, can API pricing models survive? Flash-tier APIs are already in a price war ($1.2/M output), but Sonnet- and Opus-tier pricing remains high. If local MoE models keep improving on code generation and reasoning, API pricing will either have to come down, or justify its premium through longer context, more reliable Agent toolchains, and better system prompt engineering.

This race is far from over. But for engineers, it's already time to seriously consider a hybrid strategy. Not "choose A or choose B," but "under what scenarios does A deliver the most value, and under what scenarios does B?" The answer will shift with every new generation of models—but the direction of that shift is increasingly favorable to local.
